# Spec 與 tickets：產品交付規劃

## 責任界線

Spec 定義產品行為與驗收；ticket 定義程式碼交付責任。沿用 grilling 的已確認決策、領域文件與研究證據，只補查缺口或變動。Glossary 定義詞彙、ADR 記重要取捨；同一結論引用權威來源。

實作 TODO 僅列交付所需的產品程式、測試、fixtures、migration 與可版本控制的設定／腳本變更。新增 migration 是交付；在本次環境執行 migration 是操作。產品要求的 runtime／資料庫版本、相容性與真實驗收邊界仍屬規格。

規劃完成後由 [implement-spec](implement-spec.md) 自動呼叫 `setup-testing` 確認環境並產生 `test.md`；環境放行後才開始產品派工、審查、合併與清理，執行狀態記入本機執行表。這些共用流程及開工前準備不寫進 spec、ticket TODO 或產品 AC，也不另附準備表作為規劃交付。執行規則直接讀取 `AGENTS.md`／skills；已有授權沿用來源，不轉錄為產品需求。

## 1. 定義 spec 與驗收

- 每項 AC 使用穩定識別碼，描述可觀察的正常／失敗／例外結果、產品權限與資料政策、相容性及必要品質要求。
- 記錄確認範圍、範圍外、公開契約、研究版本／限制及決策來源。新需求先確認，不從外部案例自行擴張。
- 確認測試邊界與層級：局部邏輯、元件、API／契約、真實 runtime／瀏覽器／目標平台各自證明什麼。選能證明行為的最小邊界；指定真實執行的 AC 保留實測要求，具體啟動與預檢指令由實作階段查 repo。
- 影響需求成立、架構、公開契約、依賴或驗收的未知，依 [grilling 的可行性門檻](grilling.md#規劃期可行性門檻) 完成必要研究及組合實驗。研究實驗的環境操作留在研究證據，不延伸為產品批次的開工準備計畫。

## 2. 拆成可驗收的完整交付

每張票以狹窄且完整的可驗收行為為單位，一位 owner 負責需要的產品、測試與 fixtures。可包含多輪內部 TDD；不按 Test／Green 角色或單一測試拆票，也不強迫每票修改所有技術層。

1. 建立「AC → 負責 tickets → 各票範圍 → 最終驗證者 → 證據／狀態」對照，涵蓋全部 AC；spec 不複製票內 TODO。
2. TODO 描述可判定完成的程式碼交付，驗收描述可觀察結果與證明方式；每項有唯一責任，跨票剩餘責任在承接票明列。
3. 每票明列負責模組／修改範圍、由別票負責的共用部分，以及需要的上游公開契約。檔案可作查證指標，不以路徑清單取代行為契約。
4. 共用介面、schema、設定或腳手架由唯一票交付；依下方「跨票互斥與平行判定」核對責任及交接，不能只以不同 worktree 宣稱可平行。
5. `Blocked by` 只列真正前置成果與驗收 ID。前置票含無關工作時切分到成果，必要時才拆票；不以整份 spec 完成作為單票前提。各票能獨立驗證自身交付，缺少上游時明列所需契約與驗收邊界，不把 mock 證據當整合通過。
6. 提早安排最薄的真實產品路徑；整合驗收票只負責跨票證據，不承接前置票尚未做好的基本接線。一般實作細節由 owner 決定。

### TODO 的獨立完成判定

- 每項 TODO 以本票明定的交付邊界與必要驗證判定；成果及證據已滿足就勾選，不等待下游票實作、消費或全 spec 驗收。TODO 勾選、本票驗收、審查／整合狀態與跨票 AC 分開追蹤。
- 下游接線與跨票端到端驗收由指定承接票負責，留在其 TODO／驗收及 AC 對照；不能把下游尚未完成當成上游 TODO 未完成。上游仍須交付自己負責的真實實作、基本接線與必要測試，只有 stub 或 mock 不算完成原定真實交付。
- 拆票時做反向依賴檢查：「下游尚未實作，上游能否證明本 TODO 完成？」若不能，先釐清是否把下游責任混入上游；重新劃界、調整依賴或合票，保留全部原要求及唯一驗證責任，避免 A 等 B 完成、B 又等 A 放行。
- 已勾項目只有出現證明本票契約未滿足的新缺陷或證據失效時才重開，記錄具體原因與受影響範圍；下游進度落後本身不是重開理由。原本包含未完成責任的項目須依責任移轉規則處理，不能直接改寫為已完成。

例如 T01 交付解析 API、T02 負責 UI 接線：T01 API 實作及本票契約驗證通過即可勾選；T02 UI 尚未完成只影響 T02 與跨票 AC。T01 的審查／整合仍按各自門檻進行，不用等待 T02。

### 跨票互斥與平行判定

互斥的是**實作責任與變更中的契約**，不是要求所有票使用不同檔案。依下列順序核對，結果留在既有 tickets 索引及各票責任欄，不另建一套規劃文件：

1. **行為唯一負責**：將 TODO 對照到可觀察行為、共用契約及接線位置。同一行為只由一票實作；消費票明列使用哪個已交付介面、負責哪段接線。跨票 AC 可共同驗證，但不能讓多票各自承諾完整實作同一能力。
2. **找出候選衝突**：按共用模組／符號、API／事件／資料格式、schema／migration、註冊入口、設定、相依鎖檔與共用 fixtures／runner 分組，對有交集或上下游關係的票兩兩推演。「A、B 同時開工，能否各自完成並合入，而不改動對方負責的行為或依賴其未交付契約？」不同檔案但改同一契約仍是衝突；同檔案互不影響的局部修改可平行，但須說明邊界。
3. **選擇處置**：共用能力交唯一票先完成，下游依精確成果解鎖；可獨立的修改明確劃界；無法形成穩定交接、必須反覆共同改動的行為合併成一張完整票。不要只為增加平行數拆票，也不把所有共用檔案都變成整票串行依賴。
4. **記錄交接**：有衝突的部分明列交付票、消費／承接票、交接成果與驗收 ID。上游交接後的剩餘工作須能避開已交出的修改範圍；若仍須共同修改，保留該範圍的先後關係。交接後再發現缺陷，依執行中責任調整指定唯一修正 owner。

Tickets 索引只記有交集的組合及可平行分組的判定依據，不輸出所有無關票對的矩陣：

| 票對／分組 | 交集或獨立依據 | 唯一修改責任／處置 | 解鎖成果與驗收 |
| --- | --- | --- | --- |
| A → B、C | A 提供共用安裝 API；B、C 各接不同消費入口 | API 由 A 交付；B、C 僅修改各自接線，可在交接後平行 | A 的 API 契約驗收 ID；執行時補已驗證 integration SHA |

產品依賴與修改順序寫入 `Blocked by` 並標明原因；執行容量、ports 或臨時共用資料的排程限制只進執行表。沒有查明邊界的組合標待釐清，不能列為可平行。

## 3. 獨立交付推演

由未參與 spec／tickets 撰寫的子代理直接讀取規劃、適用規則、決策與研究證據，唯讀審查。依 [session 生命週期](session-lifecycle.md) 新建首次 reviewer；修正複查 resume 原 reviewer，不可恢復時交接問題與責任。

核心問題：**每張票的程式碼交付、修改邊界、依賴與驗收是否明確，全部需求是否有人負責，且平行分組是否成立？** 環境是否已建立、測試憑證是否可用及執行操作授權不是本階段放行門檻。

逐票核對：

1. 交付的正常、失敗、權限與必要例外是否明確，所有 AC 是否有唯一責任及最終驗證者？
2. 實作 TODO 是否確實對應程式碼／測試／必要配置交付，是否混入共用流程或環境操作？
3. 依「跨票互斥與平行判定」核對有交集的票對：是否重複實作同一行為、共改契約或遺漏接線責任？聲稱可平行的分組是否有獨立依據，交接後上游剩餘工作是否仍會踩到下游範圍？
4. 依賴是否必要、無循環，且指向具體成果，而非整票無關工作或最終合併？
5. 每項驗收是否能證明公開行為，必要跨票接線是否有責任，是否誤把 mock 當真實驗收？上游 TODO 是否可在下游尚未實作時獨立判定完成，跨票 AC 是否被誤設為每張票的完成門檻？
6. 影響方案成立的未知是否已研究，產品決策是否已確認？一般內部設計留給 owner。

Reviewer 回報來源、問題、受影響交付與修正條件。主 agent 修正後複查影響範圍，直到規劃阻擋解決；未變且有效的證據沿用。記錄審查範圍、session、問題處置、最終版本（diff／hash）與結論。無法獨立審查時明記未完成，不以作者自查替代。

## 4. 確認、提交與交接

- 只要求 spec 時，完成範圍與 AC 審查，票級責任與依賴標待拆票；同時要求 spec／tickets 時，形成兩者後統一審查與確認。
- 通過最終審查後，以 `question` 確認提交或修改；已明確授權提交時沿用。實質修改需複查受影響部分，再核對 staged 版本。
- 依分流規則同步 Status、Blocked by。`ready-for-agent` 表示可交給實作流程承接，不代表環境已就緒或全部票能同時開工。
- 交接產品決策、研究來源、AC 對照、修改責任與依賴圖。規劃審查完成後進入 `implement-spec` 配置各 worktree 環境並實作；執行狀態留在本機執行表，環境就緒不倒過來阻擋拆票完成。
- Implement-spec 更新進度與維持原範圍的責任調整可直接提交，不再次啟動需求訪談。

## Ticket 內容格式

```md
# NN：交付名稱
Status: ready-for-agent
Blocked by: 無；或具體前置成果與驗收 ID

## 本票交付
使用者可觀察結果與範圍。

## 修改責任與依賴契約
本票唯一負責的行為與修改範圍；只消費／由別票修改的共用契約及接線分工。列出必要上游成果、驗收 ID，以及有交集票的修改順序／交接條件；引用 tickets 索引的票對判定。

## 行為契約與決策來源
輸入／輸出、錯誤／例外、產品權限／資料政策、相容性；引用 spec／ADR／研究。

## Spec AC 對應
AC ID、本票責任、跨票剩餘責任與最終驗證者。

## 實作 TODO
- [ ] T1：可判定完成的程式碼、測試或必要配置交付。

## 本票驗收條件
- [ ] V1：情境、公開入口、預期結果、測試層級與必要目標平台；證據待驗證。

## 後續承接
有則列承接票／AC、剩餘交付及完成條件；無則明寫無。
```

## 執行中責任調整

維持產品範圍的拆分／合併依 [implement-spec 的責任移轉](implement-spec.md#責任移轉) 記錄原 TODO／AC、原因、承接項目與完成條件，更新依賴圖。所有未完成部分仍在總表追蹤；需求與驗收變更先確認。臨時環境準備保持為執行動作；若需新增可版本控制的程式或設定，才由唯一 owner 承接相應交付並檢查跨票影響。
