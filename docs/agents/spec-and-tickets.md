# Spec 與 tickets：責任、驗收與確認流程

## 適用範圍

建立／修改 spec、拆分 tickets，以及整理既有 TODO、驗收責任與依賴時，均適用本文件。以下分層與格式補充通用 skill 的 ticket 範本。

需求規劃階段建立／修改 spec、tickets，須先完成獨立子代理審查、問題修正與最終版本複查，再依文末流程確認提交；單獨產出 spec 亦適用。`implement-spec` 依已確認需求更新 TODO、狀態、驗收證據、交接與 commit 指標，屬執行進度，可直接提交。

`implement-spec` 中維持原範圍／驗收的拆票、依賴調整、責任移轉，依 [implement-spec.md](implement-spec.md) 的跨票移轉流程記錄提交；不得縮減需求或降低標準。超出 spec 的決策依阻擋流程保留待決、繼續其他工作，不冒充進度更新。

## 分層與完成條件

| 層級 | 記錄內容 | 完成條件 |
| --- | --- | --- |
| Spec 驗收條件（AC） | 整體產品必須具備的可觀察行為與必要品質要求 | 該 AC 所需的各票及整合證據全部通過 |
| Ticket | 本票交付範圍、前置成果、本票驗收及後續承接責任 | 自身責任內的實作與驗收完成；正式移交依既有移轉流程處理 |
| 實作 TODO | 為完成本票交付而執行的工作步驟 | 該步驟確實完成；勾選本身不代表行為已驗收 |
| 本票驗收條件 | 本票交付的可觀察結果、驗證方式與通過標準 | 有符合指定範圍與環境的通過證據 |

Ticket 完成不代表 spec 完成；spec 尚未完成也不使已通過本票驗收的前置 ticket 持續受阻。Spec 中若有執行清單，與產品 AC 分開，透過 ticket 連結追蹤，避免維護兩份實作 TODO。

## 建立 spec 與拆票步驟

拆票、撰寫／修改 TODO 及獨立盤查前，先讀 [implement-spec.md](implement-spec.md) 的「分階段開工門檻」「研究票、實作票與驗收責任」「TDD 雙 subagent 流程」「依賴交接與統一合併」與收尾條件。這些是執行契約的唯一來源；規劃以它們推導責任與順序，讀取不代表啟動實作。若需求確實需要不同執行方式，先明確確認並修改適用流程，再產生相符 tickets，不在 TODO 中隱含覆寫。

1. **定義產品 AC**：給每項 AC 穩定識別碼，描述可觀察結果及必要的驗證環境。例如要求真實 runtime 的行為，明寫需要真實執行證據。
2. **切出可驗證交付**：先核對 [grilling 的規劃期可行性門檻](grilling.md#規劃期可行性門檻) 與研究證據；直接從需求開 spec 時也須補齊此門檻。每張產品票以可展示或驗證的垂直切片為優先，引用已驗證契約，列出自身責任與本票驗收；避免全部接線延至最後一票。已知關鍵未知先在規劃期解決，不用研究票把它延後至 implement-spec。
3. **建立 AC 責任對照**：在 spec 或其連結文件，逐項列出「AC → 負責 tickets → 各票涵蓋範圍 → 最終驗證者 → 證據／狀態」。跨票 AC 可分工，但每個必要部分與最終驗收都要有負責票；局部通過只更新局部證據。
4. **分開 TODO 與驗收**：使用下方格式，讓工作步驟與完成證據各自勾選。後續票負責的驗收寫入承接表，並在承接票建立未完成項目，不放成本票必須等待下游才能勾選的條件。
5. **檢查依賴圖**：`Blocked by` 只列本票開工所需、必須先完成驗收的前置票。每條依賴寫明下游使用的具體交付及其驗收條件；確認沒有循環。若前置票混有下游不需要、卻可能獨立受阻的驗收，重新切出可獨立驗收的交付與責任，保留全部產品 AC，不以略過前置驗收解鎖。最終整合驗收依賴前置交付，前置票不反向等待整合票。憑證、模型額度等外部條件另列阻擋原因、影響項目及解除條件。
6. **確認完整性後提請確認**：每項 AC 都有責任歸屬，每張票都能在前置完成後驗收自身範圍，每個後續承接連結都對應實際項目，才提出拆票結果讓使用者確認。
7. **建立 tickets 後盤點開工阻擋**：依下節查證目前環境，提前確認影響完整實作與驗收的事項，將結論回寫 spec／tickets，再進入提交確認。若盤點改變拆票或需求，先重新確認受影響內容。

### TODO 與執行契約對齊

- **可派工步驟**：TODO 寫明動作、交付物與可判定完成的條件；涉及跨票或環境時，另列必要輸入及其來源、執行角色、worktree／環境歸屬與時點。已在票頭或引用文件定義者直接引用；規劃階段不虛構 session ID、commit SHA 或已建好的環境。
- **角色邊界**：依 implement-spec 分配研究、Test、Green、整合與協調責任。產品 TODO 描述可逐行為驗證的交付，不要求同一實作者包辦測試與產品修改；主 agent 的協調／最終合併工作與 ticket 自身交付分開記錄。
- **共用交付**：每項共用實作指定唯一負責票，消費票以已驗收交付為前置；可由一張垂直切片提供，不必另建純基礎設施票。只在共用基線已可取得、介面已明確且修改責任互不重複時允許獨立平行；同檔案的不同修改不必然有依賴，但「各自重做共用能力，最後合併」不能作為獨立性的依據。
- **研究承接**：產品票引用規劃研究的證據、版本、契約與適用範圍。使用者單獨要求研究時，可建立獨立研究任務，正反結果皆可交付；研究結案不等於產品方案可行，完成選案及必要補驗後才產生相依的可實作產品批次。
- **整合時序**：依 implement-spec 的 ticket-to-ticket 交接推導整合票的工作位置與環境；整合票先在自身 worktree 取得已驗收前置成果。最終 integration 合併、合併後驗證及清理屬全票完成後的收尾責任，不寫成整合票結案前必須已完成的條件。共用驗收腳本可重用，但兩階段的執行位置與證據分別記錄。

## Tickets 建立後的開工阻擋盤點

此盤點在規劃階段完成，涵蓋整份 spec 從實作、真實整合驗收到交付的必要條件，不只檢查第一張票能否開工。既有 tickets 補做此盤點時採相同流程。

單獨產出 spec 時，先由未參與撰寫的子代理審查需求一致性、範圍、AC 可觀察性、技術未知與後續承接責任，並遵循下方修正／複查門檻；尚未拆票的票級依賴及完整開工盤點記為待拆票階段檢查，不虛構票號或宣稱已完成該盤點。

### 先查證，再詢問

#### 將待辦與阻擋分開

逐項判斷剩餘條件，記錄影響的是「準備」「實作」或「驗收」，以及負責人與下一個可執行動作：

| 類型 | 處理方式 |
| --- | --- |
| 已授權的 Agent 工作 | 建環境、準備 fixture、安裝依賴及查證能力等列為準備步驟，指派負責人；可開始準備，相關實測等環境備妥後執行 |
| 票級前置 | 以 `Blocked by` 連到必要交付；前置驗收前保留下游依賴，不阻止獨立票推進 |
| 技術未知 | 依 grilling 可行性門檻回到規劃研究，定義實驗與完成證據；受影響的產品方案暫不放行，獨立且已驗證部分可另行規劃 |
| 外部阻擋／使用者決策 | 指出 Agent 在目前授權內無法取得的條件、證據、影響工作與解除方式；只向使用者詢問必須由其處理的事項 |

依賴是否成立屬可查事實時，先查明並寫入依賴圖；須實驗才能判定時，在規劃階段指定研究角色及判定條件並完成實驗。獨立盤查須檢查關鍵研究是否真正完成，不能只因已安排未來研究責任就判定可進產品實作。

「尚未驗證」是證據狀態，不單獨構成停工理由。規劃時未能探測的事項保留待驗證與下一步；實作中確認不可取得才記錄實際阻擋。分流標籤依 [triage-labels.md](triage-labels.md)，與前置依賴、環境就緒及驗收完成分開判定。

盤點由**獨立子代理**執行：主 agent 負責整理輸入、審查證據與向使用者確認，不以自己對拆票的判斷取代盤查。選用未參與本次 spec／tickets 撰寫的全新子 session，避免作者自行認定規劃已足夠。

主 agent 提供 spec、全部 tickets、repo 規範（包含 implement-spec 的執行契約）、目前工作目錄、已確認決策／授權與證據位置，要求子代理直接讀取來源、核對目前環境，並主動尋找反例：哪些條件尚無證據、哪些驗收無法在預定環境執行、哪些依賴或授權會使後續停工。既有結論是待核對輸入，不是必須支持的答案。

子代理預設唯讀盤查，可執行已授權且低影響的檢查；需要異動、付費或新增權限的驗證，回報所需操作與影響，由主 agent 提前確認後才執行。子代理不自行修改 spec／tickets、不代替使用者決策。以下查證步驟由子代理執行，詢問與文件回寫由主 agent 負責。

1. 讀取 spec、全部 tickets 與專案執行設定，沿各票驗收方式找出所需條件。依實際範圍檢查：
   - **工具與執行環境**：必要版本、依賴取得、build／test 指令、Docker／runtime、網路、ports 與隔離環境可用性。
   - **外部服務與權限**：帳號、憑證設定、API／模型存取、可查證的額度與費用條件；安裝、部署或資源建立需要的權限。
   - **資料與驗收資源**：測試資料、固定版本第三方套件、測試帳號、真實 runtime／UI 驗收所需的服務與操作入口。
   - **操作邊界**：worktree／Docker／資料副本的來源與歸屬，是否需要停止共享服務、修改共享設定、遷移或清理資源，以及相應授權。
   - **需求與技術未決事項**：影響契約、驗收或交付的使用者決策，以及必須先用研究／原型回答的技術問題。
2. Agent 能從檔案、工具或已授權的低影響檢查取得的事實，先自行查證。記錄命令／來源、時間與結果；設定存在不等於服務可用，未測項標明「待驗證」。需付費、異動資源或額外權限的探測先確認授權；憑證只記設定位置與可用性，不記秘密值，也不要求使用者貼入對話。
3. 對必須由使用者決定或提供的事項，用 `question` 依決策依賴分輪詢問，說明影響哪些 tickets／AC、可選方案與建議。優先提前確認後段驗收也會用到的選擇，不把可查證事實交給使用者猜測。
   - 沿用現有授權與資源限制。提出新增用量上限或控制機制時，先說明必要性、可行的量測方式與額外工作成本；選擇足以遵守限制的最小做法，不預設每個功能都需要另建控制系統。使用者已確認的限制須落實，無法遵守時回報受影響操作。
4. 關鍵技術未知回到規劃研究，記錄實驗角色、通過／失敗條件與受影響方案；取得證據並完成選案後，再確認產品票可實作。需要使用者操作的事項記錄負責人、下一步與解除條件；決策確認不等於環境已備妥。

### 獨立盤查回報與複核

- 子代理逐項回報必要條件、受影響 tickets／AC、直接來源或檢查命令、觀察結果、已證實／未證實界線、阻擋與解除建議；沒有發現問題時也要列出覆蓋範圍與未能檢查的項目。
- 主 agent 對照原始證據與驗收要求審查，不以「子代理說可行」作為通過依據。結論矛盾或證據不足時交回補查；仍有歧見則派另一個未參與撰寫的子代理針對爭點獨立核對，未釐清前保留待驗證。
- 盤查與複核均須檢查阻擋分類：每項是否能由 Agent 在既有授權內解除、是否只影響後段驗收、是否誤擋無依賴工作。若判定「無可開工票」，須逐一說明無前置票連準備步驟也不能執行的證據；可執行的準備工作應明列，不使用「可完整開工」混合開始與完成門檻。
- 複核以實際下一步推演：對每張無前置票指出可立即執行的動作；對每條依賴核對必要交付；對研究的正反結果核對承接路徑；對新增限制核對執行方式與成本。只有欄位齊全或依賴無循環不足以通過。未定依賴、無負責人的準備工作及無法執行的控制要求，回寫為具體修正或待研究項目。
- 依「TODO 與執行契約對齊」推演從派工到最終收尾：核對共用交付唯一責任、角色修改邊界、前置成果取得方式，以及 worktree／合併／驗收／清理時序。除票級依賴外，也查「票等最終合併、最終合併又等票」等流程循環；回報具體 TODO 與衝突的執行規則，修正後才通過。
- 使用自動文件檢查時，先確認預期票數、唯一識別碼及必要欄位存在且格式合法；`Blocked by` 缺失或無法解析應失敗，只有明寫無前置才視為空依賴。再驗證連結與依賴圖；結構檢查不能替代上述責任與時序複核。
- **修正後必須複查**：子代理主動查找反例並列出問題、證據及影響；主 agent 修正 spec／tickets／相關紀錄後，必須再交原子代理直接讀取最終版本，逐項核對問題已解決且無新增矛盾。若仍有問題，重複修正與複查直到明確通過；「修正後即可通過」不等於修正後已複查通過，主 agent 不以自行確認取代。原代理不可用時，由另一未參與撰寫的子代理接手，提供完整問題清單與修正紀錄。
- 初查沒有發現問題時，可直接對當前版本明確判定通過，不為完成流程虛構問題。關鍵方案尚無可行證據時，判定受影響規劃未完成並回到研究，不以已指派研究責任取代通過。環境重建與易變條件另記準備責任、影響及解除條件，規劃通過不代表產品已驗收或執行環境已就緒。
- 使用者確認或文件修改影響需求、責任、依賴、驗收或授權時，重新複查受影響內容；記錄審查 session、範圍、問題處置、最終檔案版本（如 diff／內容 hash）、時間與明確結論，供提交及實作交接核對。
- 無法使用子代理時，明記「獨立盤查未完成」與原因；主 agent 可整理待查資料，但不得以自行盤點冒充本門檻已通過。

### 記錄與完成門檻

在 spec 的「開工準備」或其連結文件維護一份盤點表，各 ticket 引用受影響項目，避免重複維護：

| 識別碼 | 必要條件／待決事項 | 影響 tickets／AC | 查證證據與時間 | 狀態 | 已確認決策／授權範圍 | 負責人、下一步與解除條件 |
| --- | --- | --- | --- | --- | --- | --- |
| P01 | 真實模型呼叫可用 | 03／V1、07／AC09 | 檢查來源與結果 | 待驗證／待決策／受阻／已就緒 | 指定模型與可用預算 | 負責人與可檢查的解除條件 |

盤點完成須符合：所有實作與驗收路徑的必要條件均已檢查或明列待驗證原因；可提前回答的使用者決策已確認；剩餘項目都有責任歸屬、影響範圍及解除條件。回報分列「現在可執行的準備／票券」「等待前置或研究的工作」「需使用者處理的外部阻擋」；最後一項為空時明說目前不需使用者補充。環境是否就緒依實測證據另外記錄。

交給實作流程時附上盤點紀錄與已確認授權。實作開工只重驗易變條件（例如服務、額度、憑證有效性），以及新發現或已變動事項；原決策在範圍未變時直接沿用。已知受阻票保持受阻，不影響無相依關係的已就緒票推進。此盤點無法保證未來沒有新阻擋，但已知問題應在此階段揭露並提前處理。

## Ticket 內容格式

保留 tracker 規定的標題、`Status`、`Blocked by` 等欄位；內容採下列區分，不使用混合的「TODO 與驗收」清單。

```md
## 本票交付

本票使哪個行為成立，以及可供下游使用的成果。

## Spec AC 對應

| AC | 本票涵蓋範圍 | 後續承接／最終驗證票 |
| --- | --- | --- |
```

## 修正既有混合清單與循環依賴

逐項將原清單分類為實作步驟、本票驗收或後續承接，保留原識別碼／對照與證據。若一項必須等待後續票才能完成：

- **屬於後續行為或整體驗收**：明定承接票與驗收項目，原票依自身交付驗收。
- **確實是本票交付的必要前提**：將提供該成果的票列為前置並重新排序；互相依賴則重新切分或合併，使依賴圖無循環。
- **屬於本票但缺實作或證據**：維持未勾選並列出下一步；外部受阻也保留未完成，不以移到最後整合票取代功能交付。

執行中的責任移轉依 [implement-spec.md 的跨 ticket 移轉流程](implement-spec.md#跨-ticket-移轉未完成項目) 記錄，原票保留未完成移交紀錄與連結。只有正式移交項目可排除於原票完成判定；spec 仍追蹤全部剩餘責任。範圍或標準改變則走需求確認。

例如：03 交付安裝生命週期，05 使用它完成 Find Plugin 流程，07 驗收全流程。依賴應是「05 等 03；07 等 03、05 及其他必要票」，03 的後續承接表連到 05／07，但不把它們列為 blocker。03 自己承諾的真實 runtime 驗證若因額度不足尚未通過，仍是 03 的未完成驗收，不能因其餘 checkbox 已勾選而完成。
