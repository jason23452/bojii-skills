# Spec 與 tickets：責任、驗收與確認流程

## 適用範圍

建立／修改 spec、拆分 tickets，以及整理既有 TODO、驗收責任與依賴時，均適用本文件。以下分層與格式補充通用 skill 的 ticket 範本。

需求規劃階段建立／修改 spec、tickets，須依下節確認提交。`implement-spec` 依已確認需求更新 TODO、狀態、驗收證據、交接與 commit 指標，屬執行進度，可直接提交。

`implement-spec` 中維持原範圍／驗收的拆票、依賴調整、責任移轉，依 [implement-spec.md](implement-spec.md) 的跨票移轉流程記錄提交；不得縮減需求或降低標準。超出 spec 的決策依阻擋流程保留待決、繼續其他工作，不冒充進度更新。

## 分層與完成條件

| 層級 | 記錄內容 | 完成條件 |
| --- | --- | --- |
| Spec 驗收條件（AC） | 整體產品必須具備的可觀察行為與必要品質要求 | 該 AC 所需的各票及整合證據全部通過 |
| Ticket | 本票交付範圍、前置成果、本票驗收及後續承接責任 | 自身責任內的實作與驗收完成；正式移交依既有移轉流程處理 |
| 實作 TODO | 為完成本票交付而執行的工作步驟 | 該步驟確實完成；勾選本身不代表行為已驗收 |
| 本票驗收條件 | 本票交付的可觀察結果、驗證方式與通過標準 | 有符合指定範圍與環境的通過證據 |

Ticket 完成不代表 spec 完成；spec 尚未完成也不使已通過本票驗收的前置 ticket 持續受阻。Spec 中若有執行清單，與產品 AC 分開，透過 ticket 連結追蹤，避免維護兩份實作 TODO。

## 建立 spec 與拆票步驟

1. **定義產品 AC**：給每項 AC 穩定識別碼，描述可觀察結果及必要的驗證環境。例如要求真實 runtime 的行為，明寫需要真實執行證據。
2. **切出可驗證交付**：每張產品票以可展示或驗證的垂直切片為優先，列出自身責任與本票驗收。必要的研究／契約票明訂交付及承接票；避免全部接線延至最後一票。
3. **建立 AC 責任對照**：在 spec 或其連結文件，逐項列出「AC → 負責 tickets → 各票涵蓋範圍 → 最終驗證者 → 證據／狀態」。跨票 AC 可分工，但每個必要部分與最終驗收都要有負責票；局部通過只更新局部證據。
4. **分開 TODO 與驗收**：使用下方格式，讓工作步驟與完成證據各自勾選。後續票負責的驗收寫入承接表，並在承接票建立未完成項目，不放成本票必須等待下游才能勾選的條件。
5. **檢查依賴圖**：`Blocked by` 只列本票開工所需、必須先完成驗收的前置票。依真實依賴排序，確認沒有循環；最終整合驗收依賴前置交付，前置票不反向等待整合票。憑證、模型額度等外部條件另列阻擋原因、影響項目及解除條件。
6. **確認完整性後提請確認**：每項 AC 都有責任歸屬，每張票都能在前置完成後驗收自身範圍，每個後續承接連結都對應實際項目，才提出拆票結果讓使用者確認。
7. **建立 tickets 後盤點開工阻擋**：依下節查證目前環境，提前確認影響完整實作與驗收的事項，將結論回寫 spec／tickets，再進入提交確認。若盤點改變拆票或需求，先重新確認受影響內容。

## Tickets 建立後的開工阻擋盤點

此盤點在規劃階段完成，涵蓋整份 spec 從實作、真實整合驗收到交付的必要條件，不只檢查第一張票能否開工。既有 tickets 補做此盤點時採相同流程。

### 先查證，再詢問

盤點由**獨立子代理**執行：主 agent 負責整理輸入、審查證據與向使用者確認，不以自己對拆票的判斷取代盤查。選用未參與本次 spec／tickets 撰寫的全新子 session，避免作者自行認定規劃已足夠。

主 agent 提供 spec、全部 tickets、repo 規範、目前工作目錄、已確認決策／授權與證據位置，要求子代理直接讀取來源、核對目前環境，並主動尋找反例：哪些條件尚無證據、哪些驗收無法在預定環境執行、哪些依賴或授權會使後續停工。既有結論是待核對輸入，不是必須支持的答案。

子代理預設唯讀盤查，可執行已授權且低影響的檢查；需要異動、付費或新增權限的驗證，回報所需操作與影響，由主 agent 提前確認後才執行。子代理不自行修改 spec／tickets、不代替使用者決策。以下查證步驟由子代理執行，詢問與文件回寫由主 agent 負責。

1. 讀取 spec、全部 tickets 與專案執行設定，沿各票驗收方式找出所需條件。依實際範圍檢查：
   - **工具與執行環境**：必要版本、依賴取得、build／test 指令、Docker／runtime、網路、ports 與隔離環境可用性。
   - **外部服務與權限**：帳號、憑證設定、API／模型存取、可查證的額度與費用條件；安裝、部署或資源建立需要的權限。
   - **資料與驗收資源**：測試資料、固定版本第三方套件、測試帳號、真實 runtime／UI 驗收所需的服務與操作入口。
   - **操作邊界**：worktree／Docker／資料副本的來源與歸屬，是否需要停止共享服務、修改共享設定、遷移或清理資源，以及相應授權。
   - **需求與技術未決事項**：影響契約、驗收或交付的使用者決策，以及必須先用研究／原型回答的技術問題。
2. Agent 能從檔案、工具或已授權的低影響檢查取得的事實，先自行查證。記錄命令／來源、時間與結果；設定存在不等於服務可用，未測項標明「待驗證」。需付費、異動資源或額外權限的探測先確認授權；憑證只記設定位置與可用性，不記秘密值，也不要求使用者貼入對話。
3. 對必須由使用者決定或提供的事項，用 `question` 依決策依賴分輪詢問，說明影響哪些 tickets／AC、可選方案與建議。優先提前確認後段驗收也會用到的選擇，不把可查證事實交給使用者猜測。
4. 技術未知事項落到研究票，寫明通過／失敗條件及受阻產品票；需要使用者操作的事項記錄負責人、下一步與解除條件。決策確認不等於環境已備妥，取得實際證據後才更新可用狀態。

### 獨立盤查回報與複核

- 子代理逐項回報必要條件、受影響 tickets／AC、直接來源或檢查命令、觀察結果、已證實／未證實界線、阻擋與解除建議；沒有發現問題時也要列出覆蓋範圍與未能檢查的項目。
- 主 agent 對照原始證據與驗收要求審查，不以「子代理說可行」作為通過依據。結論矛盾或證據不足時交回補查；仍有歧見則派另一個未參與撰寫的子代理針對爭點獨立核對，未釐清前保留待驗證。
- 使用者確認或修正 tickets／環境後，主 agent 回寫紀錄，再交盤查子代理複核受影響項目；已確認但未實際驗證的事項維持待驗證。紀錄盤查 session、範圍、時間及證據，供實作交接追溯。
- 無法使用子代理時，明記「獨立盤查未完成」與原因；主 agent 可整理待查資料，但不得以自行盤點冒充本門檻已通過。

### 記錄與完成門檻

在 spec 的「開工準備」或其連結文件維護一份盤點表，各 ticket 引用受影響項目，避免重複維護：

| 識別碼 | 必要條件／待決事項 | 影響 tickets／AC | 查證證據與時間 | 狀態 | 已確認決策／授權範圍 | 負責人、下一步與解除條件 |
| --- | --- | --- | --- | --- | --- | --- |
| P01 | 真實模型呼叫可用 | 03／V1、07／AC09 | 檢查來源與結果 | 待驗證／待決策／受阻／已就緒 | 指定模型與可用預算 | 負責人與可檢查的解除條件 |

盤點完成須符合：所有實作與驗收路徑的必要條件均已檢查或明列待驗證原因；可提前回答的使用者決策已確認；剩餘項目都有責任歸屬、影響範圍及解除條件。回報時分別列出「目前可開工票」「受阻票」「研究後才能決定的事項」，不能把盤點完成宣稱為全部環境已就緒。

交給實作流程時附上盤點紀錄與已確認授權。實作開工只重驗易變條件（例如服務、額度、憑證有效性），以及新發現或已變動事項；原決策在範圍未變時直接沿用。已知受阻票保持受阻，不影響無相依關係的已就緒票推進。此盤點無法保證未來沒有新阻擋，但已知問題應在此階段揭露並提前處理。

## Ticket 內容格式

保留 tracker 規定的標題、`Status`、`Blocked by` 等欄位；內容採下列區分，不使用混合的「TODO 與驗收」清單。

```md
## 本票交付

本票使哪個行為成立，以及可供下游使用的成果。

## Spec AC 對應

| AC | 本票涵蓋範圍 | 後續承接／最終驗證票 |
| --- | --- | --- |
| ACxx | 本票可獨立驗證的部分 | Ticket NN：剩餘行為與驗收；或本票完整涵蓋 |

## 實作 TODO

- [ ] T1：完成具體工作步驟。

## 本票驗收條件

- [ ] V1：在指定情境下，透過公開入口觀察到預期結果。驗證方式：……；證據：待驗證。

## 後續承接

| 承接票／項目 | 剩餘責任 | 本票提供的成果 |
| --- | --- | --- |
| Ticket NN／V1 | 跨功能流程驗收 | 已驗收介面、契約與證據 |

## 外部阻擋

無；或記錄受影響的 T／V、原因、證據及解除條件。
```

無後續承接時可省略該節。整合驗收票可以只有驗證準備 TODO 與跨模組驗收條件；前置票仍負責自身功能與測試。Mock／契約測試的證據只涵蓋其邊界，本票明訂的真實執行驗收仍需保留並完成。

## 修正既有混合清單與循環依賴

逐項將原清單分類為實作步驟、本票驗收或後續承接，保留原識別碼／對照與證據。若一項必須等待後續票才能完成：

- **屬於後續行為或整體驗收**：明定承接票與驗收項目，原票依自身交付驗收。
- **確實是本票交付的必要前提**：將提供該成果的票列為前置並重新排序；互相依賴則重新切分或合併，使依賴圖無循環。
- **屬於本票但缺實作或證據**：維持未勾選並列出下一步；外部受阻也保留未完成，不以移到最後整合票取代功能交付。

執行中的責任移轉依 [implement-spec.md 的跨 ticket 移轉流程](implement-spec.md#跨-ticket-移轉未完成項目) 記錄，原票保留未完成移交紀錄與連結。只有正式移交項目可排除於原票完成判定；spec 仍追蹤全部剩餘責任。範圍或標準改變則走需求確認。

例如：03 交付安裝生命週期，05 使用它完成 Find Plugin 流程，07 驗收全流程。依賴應是「05 等 03；07 等 03、05 及其他必要票」，03 的後續承接表連到 05／07，但不把它們列為 blocker。03 自己承諾的真實 runtime 驗證若因額度不足尚未通過，仍是 03 的未完成驗收，不能因其餘 checkbox 已勾選而完成。

## 需求規劃階段的提交確認

- 產出完成後用 `question` 提供「直接 commit（建議）」「先修改」，不以一般文字確認。
- 選修改則用 `question` 收集方向，改完重問，直到明確選 commit；只提交本次 spec／tickets 變更，排除其他工作。
- 單獨產出 spec 或 tickets 時，完成即問；同流程產出兩者時，全部完成後問一次。
