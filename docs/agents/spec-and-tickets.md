# Spec 與 tickets：實作前完成決策與授權

## 規劃交付目標

產出可直接交給 `implement-spec` 自主完成的 tickets。需求、權限、影響方案的可行性與驗收邊界在本階段釐清；一般內部設計與程式細節留給 owner。執行契約的唯一來源為 [implement-spec](implement-spec.md)，派工依 [subagent](subagent.md)。

沿用 grilling 的已確認決策、領域文件與研究證據，只補查缺口或變動。Glossary 定義詞彙、ADR 記重要取捨、spec 定義產品行為、ticket 定義交付責任；同一結論引用權威來源，不重複維護。

## 1. 定義 spec 與驗收

- 每項 AC 使用穩定識別碼，描述可觀察的正常／失敗／例外結果、權限與資料政策、相容性及必要品質要求。
- 記錄確認範圍、範圍外、關鍵契約、研究版本／限制及決策來源。新需求先明確確認，不從外部案例自行擴張。
- 在規劃時確認測試邊界與層級：局部邏輯、元件、API／契約、真實 runtime／瀏覽器／目標環境各自證明什麼。選能證明行為的最小邊界；指定真實執行的 AC 必須保留實測要求。
- 影響需求成立、架構、公開契約、依賴或驗收的未知，依 [grilling 的可行性門檻](grilling.md#規劃期可行性門檻) 在規劃階段完成必要研究及組合實驗。未解的相關方案標規劃未完成，不把「實作時再決定」當已定案。

## 2. 拆成可驗收的完整交付

每張票以可操作或可驗證的行為為單位，指定一位 owner 自主完成需要的產品、測試與 fixtures。可包含多輪內部 TDD；不按 Test／Green 角色或單一測試拆票，也不強迫每票修改所有技術層。

1. 建立「AC → 負責 tickets → 各票範圍 → 最終驗證者 → 證據／狀態」對照，完整涵蓋全部 AC。
2. 分開實作 TODO 與驗收條件。TODO 描述完成交付所需工作，驗收描述可觀察結果與通過方式；每項有唯一責任，跨票剩餘責任在承接票明列。
3. `Blocked by` 只列真正開工前置，寫明需要的成果與驗收。前置票包含不相干且可能受阻的工作時，重新切分；保留所有驗收要求。
4. 共用介面／政策由唯一票交付；基線穩定、修改不衝突且可獨立驗收的工作才能平行。避免以「最後合併」掩蓋重複實作。
5. 提早安排最薄的真實產品路徑；整合驗收票負責跨票證據，不承接前置票尚未做好的基本接線。
6. 依逐票整合流程規劃：本票驗收／審查通過後合入 integration，受影響回歸通過才解鎖下游；最後整體驗收及收尾仍保留。

Ticket 完成不等於 spec 完成。Spec 不再複製票內 TODO；以責任對照與票券追蹤完整狀態。

## 3. 完成全範圍授權與準備計畫

在 spec 的「開工準備」或單一連結文件維護下表，各票引用受影響列：

| ID | 必要條件／操作 | 影響 TODO／AC | 決策與授權界線 | 實測證據／時間 | 狀態 | owner、下一步與使用時點 |
| --- | --- | --- | --- | --- | --- | --- |
| P01 | 目標 runtime 與測試環境 | 對應票與 AC | 可建立／重啟／清理範圍 | 命令及觀察結果 | 已就緒或待準備 | 負責角色、準備及預檢指令 |

沿整份 spec 的實作、驗收到收尾盤點：

- **工具與環境**：版本、依賴、build／test 指令、實際部署環境、endpoint、網路／ports、隔離與容量。
- **資料與服務**：fixtures、資料副本來源、帳號與憑證可用性、API／模型、費用範圍及可執行的用量限制。
- **操作授權**：worktree／Docker／外部資源的建立、修改、停止／重啟、部署／遷移、清理與失敗恢復。來源與歸屬明確，憑證只記位置與可用性。
- **已知例外**：部分成功、取消、重試、回復及驗收失敗的處理原則。不得把需使用者決定的行為留給實作者猜測。

### 狀態分類

| 狀態 | 規劃處理 |
| --- | --- |
| 已授權且方法明確的準備工作 | 建環境、fixture、安裝等列為 TODO，指定 owner、輸入、命令／方法、完成證據及使用時點；可交由實作自動執行 |
| 票級依賴 | 指向必要已驗收交付，不能阻塞無相依工作 |
| 技術未知 | 完成最小研究／實驗、選案及必要決策後才放行受影響方案 |
| 權限或產品決策缺口 | 規劃時用 `question` 釐清；未確認前不宣告可自主完成 |
| 必要外部資源不可取得 | 明列影響與解除條件；未解除前受影響票保持受阻 |

可查事實自行查；必須由使用者決定的事項依依賴分輪提問。已確認的範圍與授權直接沿用。需要付費或異動的探測先取得相應授權。

設定存在不等於服務可用，規劃通過不等於環境已就緒。已知且不可自動解除的外部條件應在開工前處理；可自動完成的準備必須具體可執行。實作僅重驗易變條件與新變動，驗收前以程序有效設定做預檢。

## 4. 獨立開工推演

由未參與 spec／tickets 撰寫的子代理直接讀取來源，唯讀盤查；主 agent 提供完整規劃、適用規則、既有決策與研究／環境證據。低影響且已授權的查證可直接執行。

核心問題：**現在交給 owner，他能否在既有決策與授權內完成整票，而不用再問使用者？**

逐票推演：

1. 第一個動作、必要輸入、介面契約與前置成果是否明確？
2. 正常、錯誤、權限與必要例外是否有預期結果，所有 AC 是否有責任歸屬？
3. 環境／資料能否取得或按已授權方法建立？後段驗收與清理需要的權限是否提前確認？
4. 每項驗收是否能在指定環境執行，能否觀察真實交付而非僅 mock 成功？
5. 依賴是否必要、有無循環、是否不當等待整份 spec 或最終合併？
6. 普通實作設計是否已授權 owner 決定，有無無人負責的準備／恢復工作？

Reviewer 回報問題、來源、影響與完成條件。主 agent 修正後，由原 reviewer 複查修正及其影響，直到阻擋問題解決；未改動且證據仍適用的部分沿用。沒有問題就明確通過，不為審查輪數虛構問題。

記錄審查範圍、session、問題處置、最終版本（diff／hash）及結論。結構檢查可驗證 ID、連結與依賴圖，但不能取代開工推演。無法完成獨立審查時明記未完成，不以作者自查替代。

## 5. 確認、提交與交接

- 使用者只要求 spec 時，完成其範圍與 AC 審查，票級依賴與開工推演標待拆票；不得宣稱已可啟動完整實作。
- 同時要求 spec 與 tickets 時，先形成兩者，再做一次完整規劃審查與提交確認；保留分開文件，不重做相同研究。
- 通過最終審查後，以 `question` 確認提交或修改；使用者在當前任務已明確授權提交時直接沿用。實質修改需複查受影響部分，再核對 staged 版本。
- 依分流規則同步 Status、Blocked by、readiness。`ready-for-agent` 表示可承接相應工作，不把受阻或待準備狀態冒充已就緒。
- 交接包含已確認決策／授權、研究版本／適用條件、AC 對照、任務圖、準備責任及驗收指令。implement-spec 更新進度與維持原範圍的責任調整可直接提交，不再次啟動需求訪談。

## Ticket 內容格式

```md
# NN：交付名稱
Status: ready-for-agent
Blocked by: 無；或具體前置票與交付

## 本票交付
使用者可觀察結果、範圍、唯一 owner 角色及所需前置成果。

## 行為契約與決策來源
輸入／輸出、錯誤／例外、權限／資料政策、相容性；引用 spec／ADR／研究。

## Spec AC 對應
AC ID、本票責任、跨票剩餘責任與最終驗證者。

## 環境、授權與準備
引用準備 ID，列必要 fixtures、有效設定預檢、可操作範圍及失敗恢復。

## 實作 TODO
- [ ] T1：可判定完成的工作；必要輸入及準備時點。

## 本票驗收條件
- [ ] V1：情境、公開入口、預期結果、測試層級／指令與指定環境；證據待驗證。

## 後續承接與阻擋
有則列承接票／AC、剩餘責任或外部條件、owner 及解除方法；無則明寫無。
```

## 執行中責任調整

維持產品範圍的拆分／合併依 [implement-spec 的責任移轉](implement-spec.md#責任移轉) 記錄原 TODO／AC、原因、承接項目與完成條件，更新依賴圖。所有未完成部分仍在總表追蹤，不能移交後消失或假勾；需求與驗收變更先確認。
