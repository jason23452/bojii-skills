# 命令與測試執行：時限、三次上限與停滯診斷

所有 agent 執行的 command／測試均適用，包含查詢、安裝、建置、環境準備、清理、研究 probe 及背景命令。失敗由負責者自主診斷並續作；本文件限制執行嘗試，不降低驗收，也不把第三次失敗當成整份任務結束。

## 共同執行上限

- 執行前決定基準時限 **T**：優先使用可信的既有耗時與必要啟動成本；沒有基線時預設 **120 秒**。已知長任務可選合理較大的 T，記錄依據；同輪開始後固定 T。
- 同一操作**每輪最多 3 次，包含首次**：第 1 次 T、第 2 次 2T、第 3 次 4T。例如 T=120 秒時，依序為 120／240／480 秒，該輪執行時限合計最多 7T。這是每次執行的逾時上限，不是失敗後 sleep 的時間；成功即結束該輪，明確不可重試時轉診斷，不必跑滿三次。
- **輪次辨識**：按驗證目的、受測內容／輸入、環境與失敗原因辨識操作，不按命令字串累計整個任務的終身次數。成功後因受影響程式、文件或設定變更而必要的重驗是新輪；輸入未變且成功證據仍適用時直接沿用。尚未解決的失敗則沿用原輪，只有符合下方實質修正／方法變更條件才能開新輪；無關 commit、換 owner 或文件更新不重置失敗預算。
- 非零退出、逾時或已開始執行的中斷均計一次。每次失敗先保存錯誤、查明部分副作用並確認前次程序已停止，再決定是否可重試；有副作用的操作先查結果，避免重複提交、發布或建立資源。已知程式／設定錯誤先修正，不只加時間掩蓋問題。
- 第三次失敗後停止原操作重跑，轉最小重現、根因修復或可驗證的替代方法。只有有實質修正或變更驗證方法，並記錄新假設與前輪結果後，才開新一輪；換 session、包裝命令、log 路徑或單純延長時間不重置次數。
- 新輪記錄原失敗、實質變更、要區分的假設及預期訊號，由負責 owner 在既有授權內自行執行；此為診斷判定，不是新增單次批准。實際使用者限次依 implement-spec「授權沿用」另行核對；預檢／cwd 錯誤仍記入操作嘗試，但是否耗用授權取決於使用者限制的操作範圍。
- 外層命令、wrapper 與 runner 的重跑共用同一操作預算，避免外層三次乘內層三次。先核對內建 retry；測試框架重試同一失敗案例也須納入其三次上限，保留首次失敗／flaky 證據。實際 HTTP 請求等獨立子操作若需重試，各自也最多三次，且不得超出外層剩餘期限。
- 每次明確設定工具 timeout 或 runner／wrapper deadline，覆蓋子程序及清理；不用 `timeout: 0` 或只依賴工具預設。背景命令不能只設啟動工具的 timeout，必須讓實際程序有期限與取消機制。長駐服務設定有限啟動期限及本次任務存活期限／清理責任，避免把服務常駐誤判成命令停滯。
- 沿用既有 log／執行表記錄操作、輪次、attempt 1–3、T／本次 deadline、退出結果與下一動作；主 agent 與 owner 交接同一份重試紀錄。單次成功的短命令由工具參數與結果留證即可，不另建報告。

例如 `git diff --check` 通過後又修改文件，應檢查新 diff，不能因歷史已有三次成功而禁止；相同 diff 已通過就沿用。上述輪次規則不改變使用者明確的總次數、費用或操作限制。

### 耗時基準的回饋

每輪結束將可信的實際耗時、測試範圍、平台／併發及 wrapper 版本記入既有證據。新輪開始先核對可比性，用已知正常耗時加啟動、波動與清理餘裕決定 T；不得明知完整測試約 369 秒，仍以 300 秒反覆製造首次逾時。只有 timeout 的結果是耗時下限，不是正常完成基準；異常變慢先診斷。失敗預算耗盡仍依新輪條件處理，不能僅提高 T 重置。

`test.md` 中記錄測試時限時，引用量測來源與適用條件；owner 回報新量測，由主 agent 在下一輪前核實修訂並同步快照，再交所有受影響執行者採用。同輪 T 維持固定，當輪必要重試按 2T／4T；使用者明確時限優先。

## 執行前

### 驗證期限與取消確實生效

首次採用 runner／wrapper、變更輸出／退出碼／取消機制，或發生退出碼缺失、程序殘留時，先用短且有限的本機子命令驗證：exit 0、指定非零退出碼、stdout／stderr 捕捉，以及適用的逾時／取消與父子程序收斂。沿用相同平台、版本及機制的有效證據即可。Probe 記錄預期／實際退出狀態、程序識別與自有 ports／資源釋放；只設 timeout 參數不能算驗證完成。工具層 timeout 若未涵蓋子程序，優先補既有 runner 的取消傳遞與 teardown，必要時加最薄的平台適用 wrapper。

正常退出、逾時及取消分別保留結果；實際使用哪條路徑就驗證哪條，背景模式須確認實際工作受 deadline 控制。服務本身的任務存活期限與測試命令分開記錄。失效時先修復並重驗，再放行依賴該機制的長任務；其他檢查可繼續。證據放既有驗證紀錄，無需建立通用執行平台。

Wrapper 曾漏掉 exit code 或破壞輸出時，先修復捕捉方式並通過上述短 probe，再重跑必要長測試；空白 exit code 不能由成功 summary 推定為 0。將已驗證方式修入 repo 既有入口並交接路徑／版本與證據；後續 owner、integration 與新輪共同引用，不再複製已知失效的臨時 shell。若既有工具已完整提供能力，直接使用，無需另建 wrapper。

### 每次執行準備

1. 讀取實際 package scripts 與 runner 設定，依 [可重現環境契約](environment-contract.md) 確認準備入口、有效目標及測試範圍。`test:unit`／`test:integration` 名稱不代表隔離；只使用該 runner 支援的選項。
2. 依「共同執行上限」決定 T、當前 attempt 與總 deadline，預留清理時間。未知耗時的測試可先跑代表性單檔取得量測；完整集合仍須在交付前完成。
3. 可用時同時設定案例時限與整個程序樹的外層時限。案例取消不保證底層工作停止，外層時限必須涵蓋 runner、子程序及 teardown；長駐測試服務另記錄啟閉責任。
4. 長測試的 stdout／stderr 持續寫入本機證據檔，記錄命令、工作目錄、版本、開始時間、時限及程序／工具 ID。輸出至少能辨認目前檔案或案例；證據避免包含憑證，對外回報先遮蔽秘密。

### 證據保存與編碼

- 每次 invocation 在執行前取得唯一 run ID／輸出位置，關聯操作輪次、attempt、受測版本及環境。預檢、正式驗收與重試各有獨立紀錄；同次 invocation 的階段可共用 run 目錄但分列結果。建立時核對不覆寫既有檔案；`latest` 只作指向已保存結果的索引，不能是唯一證據。預檢不得覆寫先前驗收結果。
- 生產端與捕捉端明確約定編碼，按實際編碼解碼並保存為 UTF-8；不依賴 PowerShell／平台預設。變更捕捉或轉碼時，以含繁體中文及非 ASCII 符號的短 probe 核對 stdout／stderr 讀回一致，連同退出碼測試後再跑長任務。
- 脫敏後核對關鍵斷言、退出狀態、結構化資料可解析且輸出無截斷／亂碼，讀回成功才定稿並計算 hash。Hash 只驗證檔案位元組一致，不證明解碼或內容完整。若已發生有損轉碼，保留已知限制並重取受影響證據，不從替代字元猜回原文。
- 原始敏感輸出優先在來源避免或以串流脫敏；確需暫存時依既有資料政策限制位置與存取，禁止提交／對外輸出。允許保留的暫存來源，在安全副本完整性確認後清理；若政策要求立即移除，先完成可保留的脫敏／完整性核對，無法保留者明記證據缺口，不為診斷突破資料限制。
- 定稿的 run 證據保持可追溯；補件另存並關聯原 run。發現敏感資料時優先依政策移除或遮蔽，記錄處理原因、受影響範圍與安全版本，不為維持原始 hash 保留秘密。保存不依賴每次人工備份固定檔名；既有 runner 缺此能力由 owner 在原入口修復。

### 可診斷的驗證入口

- 將準備、產品斷言、內層清理、證據轉換／保存及外層清理分開記錄結果；主要失敗與後續 cleanup／reporting 失敗均保留，後者不覆蓋前者。尚未執行的階段明記未執行，外層清理成功不代表 AC 通過。
- 失敗輸出至少保留穩定的階段／斷言 ID、安全錯誤分類，以及適用的欄位名稱、預期／實際型別和 HTTP status。秘密、原始 payload 與私人識別值仍遮蔽；只有 `Error` 或 `runtime=null` 屬診斷入口缺陷，由 owner 補足可定位訊號再驗證，不能據此直接判定無法自主排錯。
- 修正 runner／SDK 接線時，沿實際 producer → adapter → assertion／evidence projector → serializer／輸出消費端核對契約。以固定版本 schema 或脫敏真實回應建立 fixture，讓 regression 經過實際轉換鏈；只把手寫的理想結果直接餵給 projector，無法證明 producer 接線正確。離線檢查通過後仍須完成原本要求的真實驗收。
- 修改錯誤捕捉或 evidence 路徑時，注入對應的 assertion、cleanup 或 projection 失敗，驗證主要錯誤仍可辨識、次要錯誤分列、秘密不輸出且結果可保存；至少涵蓋本次實際故障邊界。成功路徑的 fixture 或型別檢查不能代替這項失敗路徑回歸。
- 驗證入口連續兩輪修正仍未取得原 AC 的有效結果時，依 [驗證入口的收斂](environment-contract.md#驗證入口的收斂) 重估最小路徑；不同階段接連出錯也計入，不以更換 finding 名稱重置停滯判定。

## 前置資源與跨環境驗證

- 測試使用的 URL、ports、資料根目錄及 runtime 位置由環境設定或 fixture 注入；測試邏輯不綁定某張票的 worktree 或既有服務。缺少必要設定時快速回報缺項，不默默連到 dev／正式環境。各環境的政策預期與測試適用條件須明確，不把政策差異當成所有環境都應有相同結果。
- Fixture 負責「建立 → 等待就緒 → 傳遞實際識別與路徑 → 使用 → 清理」。以唯一名稱建立本次 Project／資料，記錄所有權；需要既有外部資源時明列取得方式與前置檢查，不假設它存在。
- 驗收前端建立 Project 時從 UI 操作並確認就緒；測試其他行為時可透過產品 API 準備。使用產品回傳的 ID／路徑，不自行拼接固定專案路徑。建立失敗、逾時或 interrupted 時，受影響案例標前置準備失敗；重試前核對是否部分建立，避免重複建立或誤刪他人資源。
- 接手或換環境時，在新的隔離資料中驗證準備與清理可重跑。合入 integration 後使用 integration 的設定與資源重驗受影響路徑，不靠複製原環境的偶然殘留資料取得通過。來源資料副本僅依已確認開工契約使用。

## 逾時、停滯或工具中斷

首次逾時、進度超過預期仍未推進，或工具回報 interrupted 時，依序處理：

1. **保留證據**：記錄已耗時、最後進度、原始 exit code／timeout／interrupted 狀態與輸出路徑。Wrapper 必須保留子命令退出結果；空白 exit code、部分案例通過或工具本身成功均不算測試通過。
2. **核對並收斂程序**：依本次記錄的程序樹、命令列、啟動時間及資源歸屬，確認 runner、子程序、server、socket 與重試是否仍存活。先正常取消／關閉，超過清理時限才終止已確認屬於本次執行的程序樹；不以程序名稱批次停止共享服務。重跑前確認前次程序已退出、測試 ports 已釋放或仍由已記錄的共用測試服務持有。
3. **縮小重現**：由最後進度與 runner 證據定位候選檔案，以有限時限單檔／單案例重跑。平行 runner 的最後輸出不一定是卡點，必要時以逐檔診斷或事件報告定位；不直接重跑整套或只提高時限。
4. **診斷**：載入 `diagnosing-bugs`，用可重現訊號區分正常慢測試、外部等待、契約錯誤重試及 teardown／資源未釋放。記錄可驗證假設，逐項驗證。API／SDK 升級優先核對 fixture 的路徑、位置參數、回應格式及錯誤語意；HTTP 200 不等於契約正確。
5. **依證據續作**：仍可重試且尚未滿三次時，下一次時限按 2T／4T 執行；相同錯誤無新資訊則提前轉診斷，不任意提高上限。普通 fixture、runner 與清理問題由 owner 處理，只有必要外部條件才依 implement-spec 例外處理。

## 修復與重新驗證

- 重試須有總期限、取消傳遞及最後錯誤證據；已確認不可恢復的契約錯誤應快速失敗，不當成服務尚未就緒持續等待。
- 測試及 harness 的成功、失敗、逾時路徑都須清理自有資源。取消時中止請求、retry／timer、stream 與子程序，於 `finally`／teardown 關閉 server；外層 watchdog 是最後防線，不替代程式內清理。
- 有適當測試邊界時，回歸測試同時驗證預期行為、失敗／取消後的退出與資源釋放；不以強制退出或跳過案例隱藏洩漏。
- 先通過最小重現，再跑受影響範圍及原本要求的完整集合。分批時列出批次與原集合的完整覆蓋，每批都要有結果；單檔成功不能宣告全套通過。
- 完成條件：必要案例全部有有效結果、runner 正常退出、臨時診斷已清除，且本次不再需要的程序／資源已清理。未達條件保持未完成並記錄下一個診斷動作。
