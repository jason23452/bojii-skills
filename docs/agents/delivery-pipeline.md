# 候選版本、並行驗證與整合

適用於 `implement-spec` 的 owner 交付、票級審查與整合；主 agent、owner、reviewer 於交付派工時載入。沿用既有執行表，不新增角色審批或第二套完成清單。

## 1. 固定候選交付

Owner 完成實作與必要的快速檢查後，可回報「程式就緒、驗證中」，提早進入審查；此狀態不代表本票驗收完成。快速檢查依 repo 選擇語法／型別／核心 smoke 等低成本入口；明顯失敗先修，不帶已知無法運作的版本啟動昂貴審查。

每輪固定候選 head SHA H 與 diff base SHA B，記錄必要依賴基線、AC、驗證清單、已完成／待執行項、程序與環境歸屬。所有交付內容須已提交，owner 停止產品、測試與設定寫入。後續修改或同步基線產生新候選，不能繼續宣稱舊 H 的整輪結論有效。

## 2. 並行驗證與審查

- Owner 負責在 H 執行其餘必要驗證，保留背景程序 ID、有限期限與輸出證據。主 agent 同時派獨立 reviewer 唯讀檢查 H 對 B 的程式、需求、測試設計與已有證據；實際工具不支援並行或資源不足時採串行，回報原因。
- 測試不得改 tracked source、測試或設定。產生器／autofix 先完成再固定 H；測試資料、產物及 logs 使用已界定的獨立位置。若命令仍改 tracked 檔案，該輪標待重驗，整理變更後建立新候選。
- Reviewer 需重現時使用獨立資源或協調排程，不能與 owner 共用可變 DB、帳號、ports、browser profile。資源互斥時可先做靜態審查，再串行重現。背景測試與 reviewer 並存不代表轉移寫入權。
- Reviewer 先回報「靜態檢查完成、待驗證證據」或阻擋 findings；必要驗證未完成時不得標整票通過。主 agent 收齊兩邊結果後，交原 reviewer 核對最後證據與版本，才形成最終 verdict。
- 將同輪測試失敗與 review findings 依根因彙整，一次交原 owner 修正。若重大缺陷使候選或剩餘檢查前提失效，先取消受影響工作並清理，再修正；仍有效且有界的檢查可完成取證，不無限等待最慢項。
- 修正前結束／取消該候選的審查工作與會受寫入影響的程序，確認資源清理後恢復 owner 寫入；新候選重算受影響驗證，由原 reviewer 做修正複查。收斂依 `review-convergence.md`。

**票級放行**：同一候選的所有必要驗證成功、reviewer 已核對最終證據且無未解阻擋，才標「可整合」。單邊完成只更新狀態，主 agent 繼續其他可執行工作。

## 3. 基線漂移與整合排程

一輪候選內固定 B／H。Integration 前進時，主 agent 比對候選基線到最新已驗證 integration 的差異，核對共用契約、依賴、schema、lockfile、驗證設定及資源；不能僅以檔案沒有重疊就判定無影響。

- **有實際影響、合併衝突或無法證明相容**：讓原 owner 在安全斷點同步已驗證基線，建立新候選；重驗受影響部分並複查，不沿用舊版整輪通過。
- **有證據支持無影響**：保留該輪候選，記錄判定，不因每次 integration 前進就中斷、重啟驗證或要求 rebase。
- **準備整合**：唯一 merger 再核對當下 integration 與精確 H，串行合入；實際合併結果 M 執行受影響回歸與共用契約驗證。票級 Green 不能代替 M 的驗證，patch-id 相同也不能證明環境或依賴相同。
- Integration 回歸由有限時限背景工作執行時，主 agent 可繼續派工與處理其他回報；在 M 驗證完成或失敗已處置前，不讓下一次合併改動其工作樹。只有通過的 integration SHA 才解鎖下游；失敗依原整合修正流程處理。
- 排程沿用成果依賴圖；容量有限時，優先能解除關鍵下游等待的已就緒工作，並記錄依據。不為提高 agent 數量拆碎單一 owner 的內迴圈，也不重複佈建完整環境。

## 4. 證據與效益

驗證的影響範圍、快取及審查沿用依 `test` 的增量驗證指引，各自判定。沿用既有執行表記錄 B／H／M、程式就緒、驗證與審查起訖、可整合與整合完成時間、修正輪次，以及因候選失效而作廢的工作與原因。

觀察程式就緒到可整合、整合排隊、重跑耗時、實際計算／token 成本及整合後回歸。先以代表性票核對重疊是否有收益；資源競爭或作廢成本增加時縮小並行範圍。沒有實際紀錄時回報未知，不把並行設計當成已量測加速。
