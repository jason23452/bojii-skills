# Implement-spec 流程

## Repo 流程覆寫

本文件是 repo 對 `implement-spec` skill 的專屬覆寫；skill 的通用步驟與本文件不一致時，以本文件為準。主 agent 派工時須一併傳達適用覆寫：

- 通用步驟中的「每張 ticket 完成即合併」改為本文件的「依賴交接與統一合併」。下游票券依前置驗收成果解鎖，不以 integration 已合併為條件。
- 基底不符時先查 Git 歷史與既有變更，依依賴交接規則處理；不得直接 reset 丟棄工作。
- TDD 依本文件的雙 subagent 角色分工執行；PR 與 code review 依本文件的專屬條件執行，覆寫通用流程中的提前 draft PR 與自動 code review。

## Subagent 交接與續作

開工前閱讀 [subagent 交接流程](subagent.md)，並在每次派工時要求 subagent 遵循其回報格式。每輪結果都須由主 agent 依該流程驗收並實際接續派工；切片完成不等於 ticket 或 spec 完成。

## 開工前確認阻擋

- 開始實作前，先完整閱讀 spec 與所有 tickets，並檢查 repo、工具及目前可用的環境設定，確認整份 spec 是否有阻擋因素。
- 阻擋因素包括缺少必要的環境參數、憑證或存取權、依賴或工具、必要輸入資料，以及尚未決定且會影響實作方向的需求。
- 先自行調查可由程式碼、文件或環境查明的事項；需要使用者決定的需求、取捨、必要輸入與權限，統一在開工前透過互動式 `question` 工具確認。依決策依賴分輪釐清，直到所有影響完整實作的問題都已確認，並將結論記入 spec 或 tickets。
- 開工門檻：整份 spec 與所有 tickets 的範圍、驗收標準、依賴、環境及必要權限已確認，沒有待使用者決策的阻擋。門檻未通過時持續調查與確認，不先啟動部分 tickets 的實作，再把問題留到中途處理。
- 開工前也要確認整合、驗證與收尾所需條件，包括 worktree 與 Docker 資源的歸屬及清理範圍。不得猜測或以臨時假設掩蓋阻擋因素；憑證由使用者透過適當的環境設定提供，不要求在對話中貼出秘密。
- 每張 ticket 都必須指派 subagent 實作，不因 ticket 規模小、修改單純或預期耗時短而由主 agent 直接實作。主 agent 先提供 ticket、spec、驗收標準、相關脈絡與 worktree 要求，再等待 subagent 回報。

## 優先跑通最小端到端產品路徑

- 主 agent 在開工規劃中，選出能提早驗證關鍵整合風險的一條最小產品路徑，記錄使用者入口、必要模組／runtime、實際執行結果、驗證方式與負責 tickets。先取得可行性證據，再以這條路徑安排產品實作優先順序，而非先完成所有資料層或 adapter 才開始接線。
- 最小路徑必須經過真實產品組裝與公開入口，觀察使用者所需結果。例如選定一種 Plugin 來源，透過產品入口匯入、啟動隔離 runtime，並實際呼叫一項能力；不能用獨立 probe、mock launcher 或僅註冊成功冒充產品流程已通。
- 若既有 tickets 將所有接線延後到最後一票，主 agent 依「跨 ticket 移轉未完成項目」重整責任與依賴，安排可先交付的最小路徑。仍遵循逐行為 Test→Green 與前置票驗收門檻，不以提前合併 integration 或引用未驗收成果繞過依賴。
- 跨票路徑在指定的 ticket worktree 集合已驗收前置 commits 驗證；遇到接線缺口，由負責角色補齊後重驗。路徑通過後再擴充其他來源、能力與例外；不影響該路徑的獨立工作可平行推進。
- 最小路徑通過只是一個早期整合檢查點，不代表整份 spec 完成。其餘 AC、異常情境與最終整合驗收均保留；若純文件等工作沒有可執行產品路徑，記錄不適用理由與替代驗證方式。

## 研究票、實作票與驗收責任

- 開工前依每張票的實際交付區分「可行性研究」「產品實作」「整合驗收」，在 ticket 記錄交付範圍、完成證據及後續承接票。依賴圖應可執行：前置研究票不以後續尚未開工的產品功能為完成前提。
- 可行性研究票交付可重現實驗、適用版本、觀察結果、方案取捨、已證實與未證實界線，以及供實作使用的契約。Prototype 或獨立程序實驗只能證明其實際涵蓋的行為，不能宣稱產品接線、權限、重載或真實使用流程已完成。
- 產品實作票須交付其責任範圍內的產品接線與行為驗證。若只交付可注入 adapter 或資料層，必須事先明確定義邊界，並有其他 ticket 承接 production launcher／路由與實際執行驗收；不能因局部測試通過就臨時縮減本票責任。
- 整合驗收票負責前置能力串接後的跨模組證據，不代替前置票應完成的功能或自身測試。研究票通過可以解鎖實作，但 spec 的產品驗收仍保持未完成，直到取得相應產品證據。
- 研究中若方案無法成立，依阻擋流程處理；若發現循環依賴或拆票邊界不當，透過下方責任移轉修正任務圖，保留原 spec 的交付要求。

### 跨 ticket 移轉未完成項目

- Subagent 只能提出移轉建議；主 agent 確認這是責任重分配而非需求縮減後，才更新文件。改變已確認範圍或驗收標準的提案依阻擋流程處理。
- 在 spec 的驗收對照或其引用文件建立移轉紀錄：移轉識別碼、原 ticket／TODO／AC、未完成內容及目前證據、移轉理由、承接 ticket／TODO、所需輸入、完成條件與受影響依賴。
- 同時更新原票、承接票與依賴圖。原票保留「未完成，已移交至 ticket／TODO」及紀錄連結，不把該項勾成已驗收；承接票新增明確未完成 TODO，已 resolved 的承接票須重新開啟。檢查移轉沒有形成循環依賴。
- 主 agent 確認承接項目已落入票券、可執行且相關執行者已收到更新，才算交接完成。每個未完成 AC 必須能追溯到負責票券；一項 AC 跨多票時明定各自責任與最終驗證者。
- 原票只有在重新定義的自身範圍全部驗收且移轉紀錄完整後，才可標為完成；必須明示這不代表被移交工作或 spec AC 已完成。Spec AC 只有在全部承接工作及所需證據到齊後才可勾選。
- 原票完成檢查可排除已按上述流程完整移交的項目，但必須保留可追溯的移交狀態；這不是完成勾選。主 agent 的整體剩餘工作盤點仍須計入承接票的未完成項目，避免移轉後從驗收清單消失。

## TDD 雙 subagent 流程

- 每張 ticket 預設使用 `tdd` skill，將測試撰寫與 Red → Green 實作分派給兩個不同 session 的 subagent：test subagent 與 implementer subagent。同一個 subagent 不得兼任兩個角色；主 agent 負責分派、交接與驗證。
- 兩個 subagent 依序使用該 ticket 的 `<spec_name>-tickets-<number>` worktree，同一時間僅由一個角色修改。每次以一個可驗證行為推進測試 → Red → Green，完成後再進入下一個行為，不先一次寫完所有測試再實作。
- Test agent 開始撰寫與每次交接前，均須通過下方「測試品質與有效 Red」流程；主 agent 依該流程驗收後才派 Green agent。
1. **Test：** test subagent 依 spec 與驗收標準撰寫行為測試，執行並確認測試因預期的功能缺失而失敗，不修改產品實作。交接時提供測試變更、對應驗收項目、執行指令與實際 Red 證據；環境、依賴或測試本身的錯誤須先排除，不能作為有效 Red。
2. **Red → Green：** 主 agent 確認測試與 Red 證據後，將上述內容交給另一個 implementer subagent。implementer 先重跑並確認 Red，再以最小必要實作使測試通過，執行受影響的回歸測試；必要重構須維持 Green。回報實作 diff、驗證指令及結果。
3. **測試修改權限：** implementer（Green agent）只修改產品實作，禁止新增、修改、刪除或重新命名任何測試，包括既有與本輪新增的測試，以及 fixtures、snapshots、測試輔助程式與測試設定；此限制同樣適用於排錯與重構，不得透過工具自動更新上述內容。若發現測試有誤或需要補充，將原因與證據交回主 agent，由 test subagent 處理並重新驗證後交接，implementer 才繼續實作。
4. **完成檢查：** 主 agent 在每次交接時記錄測試相關檔案的基準狀態，驗收時比對 implementer 執行前後的 diff（含未追蹤檔案），確認沒有違反上述測試修改權限；有違規變更時退回處理，完成重新驗證前不接受 Green 結果。主 agent 檢查每輪的測試、Red/Green 證據與驗收對應，尚有未涵蓋行為時繼續下一輪。所有驗收項目完成且相關測試通過，才符合 ticket 的 TDD 完成門檻。符合預期的 Red 是交接狀態；非預期失敗依「自行排錯迴圈」處理，並維持上述角色分工。

- 純文件等沒有可執行行為測試的 ticket，由主 agent 在開工前記錄不適用 TDD 的理由與替代驗證方式，仍須指派 subagent 實作。

## 測試品質與有效 Red

### 寫測試前：契約與覆蓋規劃

1. Test agent 對照 spec、ticket、既有 public API／schema、呼叫端與相關測試，確認輸入、回傳形狀、錯誤語意及權限邊界，附來源路徑。既有實作是現況證據，不自動凌駕 spec；發現矛盾先交主 agent 判定，不以猜測或迎合目前實作決定斷言。
2. 尚未存在的 API 由 Test agent 提出符合 spec 與 repo 慣例的最小公開契約，主 agent 確認後才作為交接依據；不得把猜測的路由、模組名稱或資料形狀說成既有契約。超出已確認需求的決策依阻擋流程處理。
3. 在 ticket 或其引用的驗收證據文件中，建立「驗收項目 → 行為情境 → 驗證方式 → 目前狀態」對照。先盤點整張票的正常、必要例外、邊界及回歸情境，再逐一執行 Red→Green；規劃覆蓋不代表先一次寫完全部測試。
4. 斷言對準可觀察行為與契約，避免綁定私有 helper 或複製實作邏輯。Spec 要求真實 runtime／UI 證據時，mock 測試只證明其涵蓋的邊界，另外保留實際執行驗收項目。

### 交接前：證明是產品功能缺失

- Test agent 必須在指定 worktree 實際執行本輪測試，先確認 runner、依賴、fixture、必要服務的啟停與資料準備可用；未完成的 registry handler、錯誤的回傳形狀存取、語法或無關模組載入錯誤等，先由 Test agent 修正，不交給 Green agent 當產品缺陷。
- Red 證據須包含：執行命令與工作目錄、fixture／環境準備方式、實際失敗測試與位置、預期及實際結果，以及該失敗如何對應 spec 中尚未實作的行為。必要時執行相鄰既有測試或對照情境，排除環境故障。
- 新公開入口尚不存在造成的失敗，可在契約已確認、測試環境可用且後續行為斷言完整時視為功能缺失；不能只驗證模組不存在或回應 404 就宣稱測試已覆蓋功能。
- 測試尚未執行、環境未排除或失敗原因不明時，回報「未達 Red 交接門檻」並列下一個排查動作，繼續由 Test agent 處理。測試直接通過時先查明是否已有功能或斷言不足，不為製造 Red 改壞產品或測試。
- 主 agent 核對上述證據與契約後，才交接 Green agent；Green agent 仍需重現相同 Red。若結果不同，先查環境或基準差異，不直接開始修改產品。

### 修改測試：分類與重新驗證

既有測試需修改時，由 Test agent 在交接紀錄或 ticket Comments 記下分類、原因、契約依據、受影響驗收項目及修改前後的執行結果：

| 分類 | 處理方式 |
| --- | --- |
| 修正測試錯誤 | 說明原 fixture、斷言或契約理解何處有誤，依規格與查證證據修正 |
| 補驗收覆蓋 | 指出缺少的行為，更新對照表，逐一新增切片並驗證 |
| 需求／契約變更 | 附已確認的決策來源；未確認且超出 spec 時依阻擋流程處理，不自行改驗收標準 |

- Green agent 發現測試問題時，提供證據交主 agent，再由 Test agent 修改；主 agent 不得要求測試迎合錯誤實作、刪除必要斷言或降低驗收標準。
- 修改後重跑受影響測試與必要回歸，重新記錄測試基準再交接。若修正後產品已符合行為而測試通過，如實記錄 Green 與原因，不虛構 Red，也不派出多餘產品修改。

## Green 切片提交檢查點

- 每個切片 Green 經主 agent 驗收後，進入提交檢查點，再開啟下一個切片。檢查點是可由 Git 還原的完整狀態，包含本輪產品程式、對應測試／fixtures／必要測試設定及證據文件；可由多個 commits 組成，不要求混成單一 commit。
- Green agent 仍只提交自己負責的產品檔案，不修改或提交測試。主 agent 收回修改權並核對測試基準後，由 Test agent 提交測試資產，或由主 agent 僅 staging／提交已驗收的測試變更；這不授權主 agent 代寫測試或實作。
- 執行提交者逐檔核對 staged diff，只提交本輪已驗收檔案。未知 lockfile、使用者變更、秘密、本機設定與其他票券變更不得混入；無法分離時先查明並保留現況，不以全目錄 staging 或清理強行完成。
- 在 ticket／引用的驗收證據文件記錄切片、AC、產品與測試 commit SHA、驗證命令、結果及剩餘項目；相關紀錄也須提交，主 agent 再把最終檢查點 SHA 記入執行表。最後確認本輪必要檔案均已追蹤並提交，測試與產品內容相對於通過驗證時沒有變動。
- 提交前若內容改變，重跑受影響驗證；僅 staging／commit 不改內容時不必為了提交再重跑相同測試。恢復工作或交付下游時，核對檢查點與必要 fixture／環境準備指引，不能仰賴其他 worktree 未提交的檔案。
- 檢查點保存的是本輪進度，不代表 ticket 已完成，也不解鎖仍依賴完整 ticket 的下游。有效 Red 可暫留給同 worktree 的 Green 接手，但不能跨多個已完成 Green 切片持續累積未提交測試。

## 完整實作

- 目標是完成整份 spec 及其所有 tickets，不只完成部分票券或留下未實作項目。持續處理可解鎖的工作，直到整份 spec 完成；若仍有阻擋，清楚列出未完成項目及原因。
- Ticket 完成門檻：逐項完成所有 tickets 的 TODO list，依各項驗收標準驗證通過並更新勾選狀態後，才能結束實作。主 agent 與 implementer/subagent 都須檢查是否仍有未勾選項目；有剩餘項目時持續實作與自行排錯，不得僅完成主要功能就停止，也不得刪除、略過或直接勾選未完成項目。只有符合下方阻擋判定條件時，才可保留未完成項目，並依規定回報證據與解鎖條件。
- 執行流程必須從頭持續推進到完整實作、整合與驗證；不得因遇到第一個錯誤、失敗測試或阻擋就中止整體工作或只回報部分進度。
- 遇到錯誤、失敗測試、工具故障或整合衝突時，必須進入下方「自行排錯迴圈」，持續修正並驗證；一次失敗不構成放棄、跳過 ticket 或結束任務的理由。
- 通過開工門檻後，主 agent 與所有 implementer/subagent 持續依已確認的 spec 推進實作、整合、驗證及收尾；此階段不呼叫 `question`，也不以一般文字提問要求使用者再次決定。實作細節依已確認的需求、repo 慣例與查證結果自行處理。
- 若出現開工前未能發現的阻擋，同樣執行自行排錯迴圈，並完成其他不受影響的工作；只有符合下方阻擋判定條件，才可在最終回報保留未完成項目。不以提問中斷剩餘可行工作，也不虛構決策或宣稱完成。
- 存在尚未確認的阻擋時，不得宣稱整份 spec 已完成、建立或發送 PR，亦不得標註 PR 可合併。
- 實作、整合與驗證後，更新 spec、tickets 或專案既有 TODO/進度清單，反映已完成與仍待處理的項目；只有完成且驗證通過的項目才能標記完成，受阻項目須保留並註明原因。
- integration/合併 worktree 固定命名為 `<spec_name>-merge`；`<spec_name>` 使用 spec 的名稱，並轉成適合 worktree 名稱的格式。
- 每張 ticket 的實作 worktree 固定命名為 `<spec_name>-tickets-<number>`；`<number>` 使用 issue tracker 中該 ticket 的編號。
- Ticket 依賴交接、解鎖與 integration 合併遵循下方「依賴交接與統一合併」。
- 按專案慣例執行相關測試與驗證，並依 `implement-spec` 原有流程完成整合、票券收尾及回報。
- 全部 tickets 完成並確認變更已合併後，刪除各 ticket/implementer 使用的 worktree；只保留包含完整合併結果的 integration worktree。刪除前確認沒有未合併工作或使用者變更。
- 刪除 ticket worktree 時，同步清理專屬於該 worktree 隔離環境的 Docker 資源：停止並刪除容器、刪除專屬 volumes 與 images，並釋放容器所佔用的 ports。依開工前確認的清理範圍，用名稱、labels 或其他明確關聯查證資源歸屬；不得刪除其他 worktree、專案共用或使用者既有的資源。若仍無法確認資源是否專屬，保留並記錄為收尾阻擋，繼續其餘可行清理，不在此時再次詢問使用者。

## 依賴交接與統一合併

### 基底與平行派工

- 主 agent 依各 ticket 的 `Blocked by` 建立任務圖；有循環或缺少票券時先釐清。不同 ticket 的依賴已驗收且具備可取得的交付 commit，才可解鎖實作；沒有相依關係的已解鎖票券可平行派工。
- Integration branch 固定為本地 `<spec_name>-merge`。Ticket branch 從該分支建立，主 agent 記錄基底 commit；不要查找名為 `integration` 的遠端 ref，也不要以 reset 覆蓋既有工作。
- 每張前置 ticket 驗收後，主 agent 記錄其 branch、已驗收 commit SHA、對應測試／文件及證據位置。交付 commit 必須包含下游所需程式、測試與契約文件；只存在於前置 worktree 的未提交檔案不能作為可交接成果。

### 相依 ticket 取得前置成果

- 下游 ticket 保留從 integration 建立的基底，再於自己的 worktree 合併所有直接前置 ticket 的已驗收 commit；傳遞依賴由 Git 歷史帶入。這是 ticket-to-ticket 依賴交接，不是提前合併至 integration。
- 主 agent 在派工資料中列出前置 ticket、精確 commit SHA 與合併順序，並在下游 ticket 記錄實際採用的版本。接手者確認各 SHA 均為目前 HEAD 的祖先，執行必要的契約與回歸驗證後才開始新的切片。
- 合併前確認下游沒有其他角色正在寫入且工作目錄乾淨；有未提交工作時先由其負責角色整理成可驗證交付，不覆蓋或丟棄。相依分支有衝突時由主 agent 協調解決，涉及測試與產品修改仍維持角色分工。
- 前置 ticket 驗收後若新增修正，主 agent 記錄新的驗收 SHA，通知所有直接與間接受影響下游同步，重新驗證受影響契約及驗收項目。同步與重驗完成前，不把下游原先的完成狀態當成仍有效；不得靜默追蹤尚未驗收的 branch tip。

### 最終統一合併

- 所有 tickets 均完成各自範圍、通過驗證且經主 agent 確認，所有依賴版本已同步，才開始合併至 `<spec_name>-merge`。此門檻同樣適用於研究／契約票；前置文件也透過 ticket-to-ticket 交接，不因後續需要而提前合併。
- 主 agent 提供已驗收 SHA 清單，merger subagent 依依賴順序在 integration worktree 逐一合併。同一時間只有一個合併執行者；已包含的祖先 commit 直接核對，不重複 cherry-pick 或複製檔案。
- 整合票若需要前置功能一起存在，在自己的 ticket worktree 合併已驗收前置 commits 完成跨模組驗收；不以提前寫入 integration 作為整合票可開工的條件。
- 最終合併後執行整體整合驗證。若有失敗或衝突，依既有排錯流程與 Test／Green 分工派修，記錄修正與下游影響，重新驗收並合併必要修正後再重驗；全部通過才進入清理與 PR 收尾。

## 自行排錯迴圈

1. 保留失敗指令、錯誤輸出與相關環境，建立能重現問題的最小測試或驗證步驟，明確指出預期與實際結果。
2. 檢查相關程式碼、文件、依賴及設定，依證據提出可驗證的根因假設；每次針對一個假設修正或實驗，再重跑原本失敗的驗證。
3. 若修正無效，根據新證據調整假設，或嘗試符合已確認 spec 的替代實作、工具與執行方式。避免只重跑相同失敗指令；有可行調查方向時繼續排查，不以已嘗試固定次數為由結束。
4. implementer/subagent 回報失敗時，主 agent 必須審查其證據與已嘗試的方法，再要求補查或重新分派；subagent 的失敗回報不等於整體任務完成或可直接放棄。
5. 修正後重跑原始失敗情境與受影響的測試，確認通過才將該問題標記為解決；不得刪除必要測試、降低驗收標準或隱藏錯誤來取得通過結果。
6. 暫緩受阻 ticket 時，記錄下一個排查動作並繼續其他工作；相關依賴或環境問題解除後，主動回到該 ticket 完成實作與驗證。

主 agent 不得繞過 subagent 直接完成 ticket。收到實作結果後，主 agent 必須檢查 diff、測試與驗收標準；不符合時要求原 subagent 修正或重新分派另一個 subagent。主 agent 負責協調、審查、整合與驗證，不取代 ticket 的實作執行者。

阻擋判定：只有證據顯示問題依賴 agent 無法取得的外部條件（例如缺少權限、外部服務不可用或必要輸入不存在），或仍需超出已確認 spec 的使用者決策，且合理替代方案已實際驗證不可行，才可保留為未解阻擋。單純尚未找到根因、實作困難或測試失敗，不符合此條件。最終回報須列出失敗證據、已嘗試的方法與結果、未完成範圍及解鎖條件；在此之前完成所有仍可推進的實作、整合與驗證。

## PR HTML 文件

- 通過下方 PR 發送條件後，在最終合併的 `<spec_name>-merge` worktree 中建立 `pr/<識別碼>.html`，讓文件隨實作一起進入合併分支；不要只放在不會合併的 implementer worktree。
- `<識別碼>` 使用對應的 PR 編號；若尚未建立 PR，使用 spec 或主要 ticket 的識別碼，不要虛構編號。
- 使用 `pr` skill 的內容架構撰寫 HTML：Summary、Evidence、Merge Danger。摘要使用適合變更的視圖；Evidence 記錄實際的前後驗證結果；Merge Danger 說明可逆性與影響範圍。HTML 必須有效，不能只把 Markdown 原文存成 `.html`。
- 只填入已知且可驗證的內容；尚未取得的前後證據或資訊要明確標示，不得捏造。

## PR 發送條件

- 只有在所有 tickets 都已實作完成、變更都已合併至 `<spec_name>-merge`，且所有 ticket worktree 與其專屬隔離環境資源（containers、images、volumes、ports）都已清理後，才可建立或發送 PR；不得提前建立 draft PR。
- PR 建立後，確認平台的合併狀態、必要檢查與衝突狀態，再將 PR 標註為目前可以合併。若任何條件未通過或無法確認，明確回報阻擋原因，不得標註為可合併。
- 任何 worktree 或分支都不得由 agent 推送至遠端。若 PR 所需分支尚未由使用者推送，完成本地 PR HTML 文件並回報；等待使用者處理遠端分支後，才可繼續建立或發送 PR。

## Code review

`code-review` 僅由使用者明確要求時觸發，不屬於 `implement-spec` 的自動流程；執行 `implement-spec` 期間及完成後，均不得自動呼叫 `code-review`。
