# Implement-spec 流程

## Repo 流程覆寫

本文件優先於 `implement-spec` skill 的通用步驟。主 agent 派工須傳達適用覆寫：

- 依「依賴交接與統一合併」取代逐票合併；下游依前置驗收成果解鎖。
- 基底不符時先查 Git 歷史與既有變更，依依賴交接規則處理；不得直接 reset 丟棄工作。
- TDD 採雙 subagent 分工；PR 與 code review 依文末條件，取代提前 draft PR 與自動 code review。
- 進度提交依 [spec-and-tickets.md](spec-and-tickets.md) 的執行階段例外；環境建立依下方授權，不逐次要求使用者啟動 skill。

## Subagent 交接與續作

開工前讀取 [subagent.md](subagent.md)。每次派工、回報、驗收與續作均遵循其流程；切片完成不等於 ticket／spec 完成。

## 開工前確認阻擋

- 完整讀取 spec 與所有 tickets，檢查 repo／工具／環境，盤點範圍、驗收、依賴圖及阻擋：環境參數、憑證／權限、依賴／工具、輸入資料與未決需求。技術未知事項分派研究票，列出受阻產品票，依下方門檻解鎖，不預設研究結論。
- 可查事實自行查證；需求取捨、必要輸入與權限於開工前用 `question` 依決策依賴分輪確認，直到影響完整實作的問題均已釐清，結論記入 spec／tickets。
- 確認整合、驗證、收尾條件及 worktree／Docker 歸屬與清理範圍，不以猜測掩蓋阻擋。憑證由使用者透過環境設定提供，不要求在對話貼秘密。
- 每張 ticket 均派 subagent，不因規模小而由主 agent 代做。派工提供 spec、ticket、驗收、脈絡與 worktree 要求，等待回報後驗收。

### 分階段開工門檻

- **研究門檻**：問題、需求邊界、實驗範圍、可觀察的通過／失敗條件、所需資料／環境／權限與資源歸屬均已確認。可行性是研究輸出，不以產品已實作為前提。
- **產品門檻**：需求與驗收已確認、前置研究結論可追溯、交付已驗收、環境與權限具備。獨立於未決研究的票可平行推進，判定依據記入任務圖。
- 研究失敗不授權改需求；超出 spec 的決策依阻擋流程處理，繼續其他工作。整體完成仍須全部產品與整合驗收通過。

### Worktree 與隔離環境授權

- 明確啟動 `implement-spec` 即授權主 agent／委派角色，在開工前確認範圍內建立必要 integration、ticket、整合修正 worktrees／本地 branches、專屬 Docker 環境與 dev volume 副本；覆寫 worktree skill 的逐次手動呼叫限制。
- 開工前確認 dev volume 來源、複製方法、命名、清理範圍及暫停 dev／修改共享設定的需求。已確認的讀取、複製與專屬可覆寫設定可自動執行；停止／修改 dev、覆寫使用者資料或調整共享設定須事先明確同意。
- 研究票先確認實驗環境，產品票開工前再核對其環境是否在授權範圍。同範圍隔離實例與未占用 ports 由 agent 選定並記錄，不逐票詢問。
- 來源、所有權或操作超出確認範圍時，先查證、嘗試已授權替代方式；仍需新授權則暫緩該操作，依阻擋流程處理並繼續其他工作。此時不套用 worktree 即時詢問步驟，也不執行未授權操作。
- 僅覆寫啟動授權與詢問時機；主 repo `.worktree/`、唯一資源、來源保護及專屬清理仍適用。整合修正採本文件指定的 integration commit 基底。

## 優先跑通最小端到端產品路徑

- 開工規劃選出能提早驗證整合風險的最小路徑，記錄使用者入口、必要模組／runtime、驗證方式、負責 tickets 與實際結果。取得可行性證據後優先接通此路徑，不等所有資料層／adapter 完成。
- 必須經真實產品組裝、公開入口取得使用者所需結果；獨立 probe、mock launcher 或僅註冊成功不能替代。
- 接線若全在末票，依「跨 ticket 移轉未完成項目」重整責任／依賴。仍逐行為 Test→Green，遵守前置驗收，不提前合併 integration 或使用未驗收成果。
- 在指定 ticket worktree 合併已驗收前置 commits 驗證；接線缺口由負責角色補齊重驗。通過後擴充其他來源、能力與例外；無關獨立工作可平行。
- 此檢查點不取代其餘 AC、異常與最終整合驗收。純文件等無可執行路徑者記錄不適用理由及替代驗證。

## 研究票、實作票與驗收責任

- 開工前將票券按交付分類，記錄範圍、完成證據與承接票；研究前置不依賴尚未開工的產品功能。
  - **可行性研究**：可重現實驗、版本、觀察、取捨、已證實／未證實界線與實作契約。Prototype 證據不能冒充產品接線、權限、重載或真實流程已完成。
  - **產品實作**：責任範圍內的接線與行為驗證。只交付 adapter／資料層者，事先界定邊界並指定其他票承接 production launcher／路由／執行驗收，不因局部通過而縮減責任。
  - **整合驗收**：前置串接後的跨模組證據，不替代前置功能與測試。研究通過可解鎖實作，產品 AC 仍待產品證據。
- 研究按假設、對照、步驟與觀察驗收，正反結果均如實記錄；有 probe／fixture 也不要求先製造產品功能缺失的 Red。主 agent 記錄 TDD 不適用理由、角色、替代證據；開始修改產品行為的切片才走 Test→Green。
- 方案不成立依阻擋流程；循環依賴或拆票不當依下方責任移轉調整，保留 spec 交付要求。

### 跨 ticket 移轉未完成項目

- Subagent 提議，主 agent 確認只是責任重分配才更新；改變範圍／驗收的提案依阻擋流程。
- 在 spec 的驗收對照或其引用文件建立移轉紀錄：移轉識別碼、原 ticket／TODO／AC、未完成內容及目前證據、移轉理由、承接 ticket／TODO、所需輸入、完成條件與受影響依賴。
- 同步更新原票、承接票、依賴圖並排除循環。原票保留「未完成，已移交至 ticket／TODO」與紀錄連結，不勾完成；承接票新增未完成 TODO，已 resolved 者重開。
- 主 agent 確認承接項目已落票、可執行且執行者收到更新，才算移交。每項未完成 AC 都有責任票；跨票 AC 明定分工與最終驗證者。
- 原票自身範圍全驗收且移轉紀錄完整才可完成，明示不代表移交工作／spec AC 完成。原票檢查排除正式移交項目但保留追蹤；整體盤點仍計入承接工作，全部證據到齊才勾 spec AC。

## TDD 雙 subagent 流程

- 產品行為實作預設用 `tdd` skill，由不同 session 的 Test／Green subagent 分工，不兼任；主 agent 派工、交接、驗收。研究依實驗流程，純文件依下述替代驗證，不強制產品 Red。
- 同票共用 `<spec_name>-tickets-<number>` worktree、單一寫入者，逐行為 Test→Red→Green，不先批量寫完測試。Test 撰寫與交接均依下節「測試品質與有效 Red」。
1. **Test**：依 spec／驗收寫行為測試，不改產品；提供測試 diff、AC 對應、命令與有效 Red 證據。
2. **Green**：主 agent 驗收 Red 後派另一個 implementer，先重現 Red，再最小實作、受影響回歸；重構維持 Green。回報產品 diff、命令與結果。
3. **修改權限**：Green 只改產品，禁止新增／修改／刪除／重新命名任何既有或新增測試、fixtures、snapshots、測試輔助程式與測試設定，含排錯、重構及工具自動更新。測試需修補時附證據交主 agent，由 Test 修正重驗後再續作。
4. **驗收**：每次交接記錄測試基準，比對 Green 前後 diff（含未追蹤）；違規退回，重驗前不接受 Green。核對測試、Red／Green 證據與 AC；未覆蓋則續輪，全驗收且測試通過才完成。有效 Red 是交接，其他失敗依排錯流程且維持分工。

- 純文件等沒有可執行行為測試的 ticket，由主 agent 在開工前記錄不適用 TDD 的理由與替代驗證方式，仍須指派 subagent 實作。

## 測試品質與有效 Red

### 寫測試前：契約與覆蓋規劃

1. 對照 spec、ticket、public API／schema、呼叫端與測試，確認輸入、回傳形狀、錯誤語意、權限並附來源。實作不凌駕 spec；矛盾交主 agent 判定，不猜測或迎合實作。
2. 新 API 由 Test 提出符合 spec／repo 慣例的最小公開契約，主 agent 確認後交接；猜測的路由／模組／形狀不是既有契約。超出需求依阻擋流程。
3. 在 ticket／證據文件建立「AC → 情境 → 驗證方式 → 狀態」對照，先盤點全票正常、必要例外、邊界與回歸，再逐行為 Red→Green，不批量寫測試。
4. 斷言可觀察行為／契約，不綁私有 helper 或複製邏輯。Mock 只證明其邊界，spec 要求的真實 runtime／UI 驗收另保留。

### 交接前：證明是產品功能缺失

- Test 在指定 worktree 實跑，確認 runner、依賴、fixture、服務啟停與資料可用；測試／環境錯誤（如 handler 未完成、資料形狀誤用、語法或無關載入失敗）由 Test 排除，不交 Green 當產品缺陷。
- Red 證據須包含：執行命令與工作目錄、fixture／環境準備方式、實際失敗測試與位置、預期及實際結果，以及該失敗如何對應 spec 中尚未實作的行為。必要時執行相鄰既有測試或對照情境，排除環境故障。
- 新入口不存在可算 Red，前提是契約已確認、環境可用、後續行為斷言完整；僅斷言缺模組／404 不算功能覆蓋。
- 未跑、環境未排除或原因不明：回報「未達 Red 交接門檻」與下一步，由 Test 續查。直接通過則查既有功能／斷言不足，不改壞產品或測試製造 Red。
- 主 agent 核對證據／契約才派 Green；重現結果不同時先查環境／基準，不直接改產品。

### 修改測試：分類與重新驗證

既有測試需修改時，由 Test agent 在交接紀錄或 ticket Comments 記下分類、原因、契約依據、受影響驗收項目及修改前後的執行結果：

| 分類 | 處理方式 |
| --- | --- |
| 修正測試錯誤 | 說明原 fixture、斷言或契約理解何處有誤，依規格與查證證據修正 |
| 補驗收覆蓋 | 指出缺少的行為，更新對照表，逐一新增切片並驗證 |
| 需求／契約變更 | 附已確認的決策來源；未確認且超出 spec 時依阻擋流程處理，不自行改驗收標準 |

- 測試問題依 TDD 修改權限交回 Test；主 agent 不得要求迎合錯誤實作、刪必要斷言或降驗收標準。
- 修正後重跑受影響測試／必要回歸、更新基準再交接。若產品已符合而通過，記錄 Green 與原因，不造 Red 或派多餘產品修改。

## Green 切片提交檢查點

- 每輪 Green 經主 agent 驗收後，先提交可還原檢查點再開下輪，包含產品、測試／fixtures／必要設定與證據；可分多個 commits。
- Green 只提交自己負責的產品檔案。主 agent 收回修改權、核對測試基準後，由 Test 提交測試，或主 agent 僅 staging／提交已驗收測試，不代寫測試／產品。
- 逐檔核對 staged diff，排除未知 lockfile、使用者變更、秘密、本機設定與他票內容；無法分離先查明保留，不全目錄 staging 或強行清理。
- Ticket／證據文件記錄切片、AC、產品／測試 SHA、命令、結果與剩餘項目並提交，再將最終 SHA 記入執行表。確認必要檔案已追蹤提交、內容與驗證時一致。
- 內容變動須重驗；僅 staging／commit 不改內容免重跑。恢復／交付下游核對檢查點與 fixture／環境準備指引，不依賴他 worktree 未提交檔案。
- 檢查點不是 ticket 完成，不解鎖依賴整票的下游。有效 Red 可暫留同 worktree 交 Green，但不跨已完成切片累積未提交測試。

## 完整實作

- 持續完成整份 spec、所有 tickets、整合、驗證與收尾。錯誤、測試失敗、工具故障或合併衝突均進入下方排錯迴圈，不因單次失敗跳票、停工或只回報進度。
- **Ticket 完成**：自身責任 TODO／驗收全數通過並更新勾選；正式移交項目保留狀態與承接連結，不假勾。其餘未完成者續作，不刪除或略過；外部受阻保持未完成並回報。**Spec 完成**涵蓋全部承接票與 AC，不因移轉減少。
- 通過開工門檻後，所有角色依已確認需求、repo 慣例與查證結果自行推進；不呼叫 `question` 或以文字要求再次決策。新阻擋先排錯並完成其他可行工作，僅符合下方阻擋判定才可保留未完成項目；不虛構決策或完成。
- 更新 spec／tickets／既有進度清單，僅已驗收項目標完成，受阻者保留原因。阻擋尚未確認時，不宣稱 spec 完成、建立／發送 PR 或標示可合併。
- integration/合併 worktree 固定命名為 `<spec_name>-merge`；`<spec_name>` 使用 spec 的名稱，並轉成適合 worktree 名稱的格式。
- 每張 ticket 的實作 worktree 固定命名為 `<spec_name>-tickets-<number>`；`<number>` 使用 issue tracker 中該 ticket 的編號。
- Ticket 依賴交接、解鎖與 integration 合併遵循下方「依賴交接與統一合併」。
- 按專案慣例執行相關測試與驗證，並依 `implement-spec` 原有流程完成整合、票券收尾及回報。
- 全票完成且已合併後，確認無未合併工作／使用者變更，再刪 ticket worktrees，保留完整 integration。
- 同步清理其專屬 Docker：停刪容器、刪 volumes／images、釋放 ports。按開工前範圍以名稱／labels／明確關聯核對歸屬，不刪他 worktree、共用或使用者資源。歸屬不明則保留、記錄收尾阻擋，繼續可行清理，不再詢問。

## 依賴交接與統一合併

### 基底與平行派工

- 主 agent 依各 ticket 的 `Blocked by` 建立任務圖；有循環或缺少票券時先釐清。不同 ticket 的依賴已驗收且具備可取得的交付 commit，才可解鎖實作；沒有相依關係的已解鎖票券可平行派工。
- Integration branch 固定為本地 `<spec_name>-merge`。Ticket branch 從該分支建立，主 agent 記錄基底 commit；不要查找名為 `integration` 的遠端 ref，也不要以 reset 覆蓋既有工作。
- 每張前置 ticket 驗收後，主 agent 記錄其 branch、已驗收 commit SHA、對應測試／文件及證據位置。交付 commit 必須包含下游所需程式、測試與契約文件；只存在於前置 worktree 的未提交檔案不能作為可交接成果。

### 相依 ticket 取得前置成果

- 下游 ticket 保留從 integration 建立的基底，再於自己的 worktree 合併所有直接前置 ticket 的已驗收 commit；傳遞依賴由 Git 歷史帶入。這是 ticket-to-ticket 依賴交接，不是提前合併至 integration。
- 主 agent 在派工資料中列出前置 ticket、精確 commit SHA 與合併順序，並在下游 ticket 記錄實際採用的版本。接手者確認各 SHA 均為目前 HEAD 的祖先，執行必要的契約與回歸驗證後才開始新的切片。
- 合併前確認下游沒有其他角色正在寫入且工作目錄乾淨；有未提交工作時先由其負責角色整理成可驗證交付，不覆蓋或丟棄。相依分支有衝突時由主 agent 協調解決，涉及測試與產品修改仍維持角色分工。
- 前置 ticket 驗收後若新增修正，主 agent 記錄新的驗收 SHA，通知所有直接與間接受影響下游同步，重新驗證受影響契約及驗收項目。同步與重驗完成前，不把下游原先的完成狀態當成仍有效；不得靜默追蹤尚未驗收的 branch tip。

### 最終統一合併

- 所有 tickets 均完成各自範圍、通過驗證且經主 agent 確認，所有依賴版本已同步，才開始合併至 `<spec_name>-merge`。此門檻同樣適用於研究／契約票；前置文件也透過 ticket-to-ticket 交接，不因後續需要而提前合併。
- 主 agent 提供已驗收 SHA 清單，merger subagent 依依賴順序在 integration worktree 逐一合併。同一時間只有一個合併執行者；已包含的祖先 commit 直接核對，不重複 cherry-pick 或複製檔案。
- 整合票若需要前置功能一起存在，在自己的 ticket worktree 合併已驗收前置 commits 完成跨模組驗收；不以提前寫入 integration 作為整合票可開工的條件。
- 最終合併後執行整體整合驗證。若有失敗或衝突，依既有排錯流程與 Test／Green 分工派修，記錄修正與下游影響，重新驗收並合併必要修正後再重驗；全部通過才進入清理與 PR 收尾。

### 最終整合失敗的修正位置

- 已合併後的測試／執行失敗，以發生錯誤的 integration HEAD 作為修正基底，不直接回缺少其他票券變更的舊 worktree 修復。主 agent 保存失敗命令、環境與 commit，在執行表登記修正識別碼、對應 AC、負責角色與驗收條件。
- 從該 integration commit 建立本地 `<spec_name>-integration-fix-<number>` branch，worktree 固定於主 repo 的 `.worktree/<同名分支>`；明確指定 base，沿用 worktree 的路徑核對與 Docker 資源隔離要求。這是整合修正專用基底，不套用一般 ticket 從其他前置票取得成果的起點。
- Test／Green 使用不同 session，依序取得此修正 worktree 的修改權。Test agent 先重現原始整合失敗，必要時補回歸測試；Green agent 修改產品實作。已有有效測試時直接沿用，不為流程另造重複測試。驗收及提交遵循有效 Red 與 Green 檢查點規則。
- 修正完成後，由單一 merger 將已驗收修正 commit 合回 integration，再於 integration 重跑原始失敗情境與受影響的整合驗證。若 integration 已有新變更，先同步至修正 branch 並重驗；記錄新的驗收 SHA，不能只憑舊基底的通過結果收尾。
- Git merge 尚有未解衝突時，不把該半完成狀態當作可建立修正分支的基底。由 merger 持有 integration 修改權並記錄衝突；需要 Test／Green 處理內容時依序交接。若需隔離排查，保存診斷後確認無其他工作受影響，再中止本次 merge，從最後完整 integration commit 建立上述修正 worktree，重現相同來源合併並處理，完成後交 merger 整合。
- 整合驗證全數通過後，確認修正成果已合併且沒有未提交或使用者變更，再清理修正 worktree 及其專屬環境；更新執行表與驗收證據。清理範圍與 ticket worktree 相同，最終保留完整 integration 結果。

## 自行排錯迴圈

1. 保留失敗指令、錯誤輸出與相關環境，建立能重現問題的最小測試或驗證步驟，明確指出預期與實際結果。
2. 檢查相關程式碼、文件、依賴及設定，依證據提出可驗證的根因假設；每次針對一個假設修正或實驗，再重跑原本失敗的驗證。
3. 若修正無效，根據新證據調整假設，或嘗試符合已確認 spec 的替代實作、工具與執行方式。避免只重跑相同失敗指令；有可行調查方向時繼續排查，不以已嘗試固定次數為由結束。
4. implementer/subagent 回報失敗時，主 agent 必須審查其證據與已嘗試的方法，再要求補查或重新分派；subagent 的失敗回報不等於整體任務完成或可直接放棄。
5. 修正後重跑原始失敗情境與受影響的測試，確認通過才將該問題標記為解決；不得刪除必要測試、降低驗收標準或隱藏錯誤來取得通過結果。
6. 暫緩受阻 ticket 時，記錄下一個排查動作並繼續其他工作；相關依賴或環境問題解除後，主動回到該 ticket 完成實作與驗證。

主 agent 只協調、審查、整合、驗證，不代做 ticket。核對回報 diff／測試／驗收，不合格則派原 subagent 修正或另派。

**阻擋判定**：證據顯示依賴不可取得的外部條件（權限、服務、輸入等）或超出 spec 的使用者決策，且合理替代方案已實測不可行，才可保留未解。找不到根因、實作困難或測試失敗不算。先完成全部可推進的實作／整合／驗證，再回報失敗證據、已試方法／結果、未完成範圍與解鎖條件。

## PR HTML 文件

- 本地交付門檻為所有 tickets 與 spec AC 均已驗收、成果已合併至 `<spec_name>-merge`、最終整合驗證通過，且 ticket／整合修正 worktrees 與其專屬環境已完成清理。通過後，在保留的 integration worktree 建立並提交 `pr/<識別碼>.html`；此文件不依賴遠端分支已推送、PR 編號已存在或遠端檢查已通過。
- `<識別碼>` 使用對應的 PR 編號；若尚未建立 PR，使用 spec 或主要 ticket 的識別碼，不要虛構編號。
- 使用 `pr` skill 的內容架構撰寫 HTML：Summary、Evidence、Merge Danger。摘要使用適合變更的視圖；Evidence 記錄實際的前後驗證結果；Merge Danger 說明可逆性與影響範圍。HTML 必須有效，不能只把 Markdown 原文存成 `.html`。
- 只填入已知且可驗證的內容；尚未取得的前後證據或資訊要明確標示，不得捏造。

## PR 發送條件

- 遠端 PR 發送門檻為上述本地交付與 PR HTML 均已完成，且使用者已將包含完整交付與 HTML 的分支推送至遠端；確認遠端來源 commit 與預定交付一致後，才可建立或發送 PR。不得提前建立 draft PR。PR 建立後的合併狀態與必要檢查依下一條確認，不作為本地 HTML 的建立前提。
- PR 建立後，確認平台的合併狀態、必要檢查與衝突狀態，再將 PR 標註為目前可以合併。若任何條件未通過或無法確認，明確回報阻擋原因，不得標註為可合併。
- 任何 worktree 或分支都不得由 agent 推送至遠端。若 PR 所需分支尚未由使用者推送，完成本地 PR HTML 文件並回報；等待使用者處理遠端分支後，才可繼續建立或發送 PR。

## Code review

`code-review` 僅由使用者明確要求時觸發，不屬於 `implement-spec` 的自動流程；執行 `implement-spec` 期間及完成後，均不得自動呼叫 `code-review`。
