# Implement-spec：整票自主交付

## 執行契約與完成條件

本文件是 `implement-spec` 的執行權威，優先於通用 skill。以已確認的 spec、tickets、研究與授權為輸入，持續完成整份工作；**所有 tickets 的 TODO、本票驗收、跨票 AC、整合驗證及約定收尾均完成，才回報完成**。子代理回報、單票通過、時間／輪數預算或局部 Green 都是中間狀態。

- 主 agent 負責完整進度、環境盤點、排程、依賴、驗收與整合；每票新建一位實作 subagent owner，負責產品程式、測試、fixtures、排錯與驗證。同票續作 resume 原 owner，不以主 agent 逐票自行實作取代派工；工具無法建立子代理時回報執行阻擋。
- 每次 owner／reviewer 回報、背景工作完成或整合驗證結束，立即執行 [subagent 的排程迴圈](subagent.md#主-agent-的持續排程)，以實際工具動作推進下一狀態。
- 獨立 reviewer 在功能交付時審查。TDD 的 Red → Green → Refactor 在 owner 內部連續進行，不以每個測試作為跨代理交接點。
- 已確認範圍內自行推進；產品需求、權限政策與驗收決策由規劃確認。執行所需環境與操作授權於本流程盤點，已有決策與授權沿用，不重新訪談。
- 不以刪除 TODO、降低驗收、跳過失敗測試或把未完成移成範圍外取得完成。正式責任移轉仍計入整份 spec。

## 1. 開工契約核對

讀取全部 spec／tickets、[產品交付規劃](spec-and-tickets.md)、決策／研究及 [subagent 交接規則](subagent.md)。主 agent 一次建立完整任務圖，之後依變更更新；從實作 TODO／AC 推導環境需求，不要求規劃文件預先提供準備表。

接手既有成果、恢復中斷或將既有工作移至另一環境時，自動載入 [project-handoff](../../.opencode/skills/project-handoff/SKILL.md)，依其觸發判定核對續作基線及受影響的前置條件。從零開發、首次建環境及正常新票派工直接執行本文件的開工與環境就緒檢查；發現未記錄的遺留依賴時才針對該依賴啟動盤點。盤點結果納入既有執行表，有效證據沿用，不取代產品驗收。

開工前必須具備：

1. **需求已定案**：正常／失敗／例外、相容性、權限與資料政策、範圍及產品 AC 明確。
2. **方案有證據**：影響公開契約、架構、依賴或驗收的關鍵未知已依 [grilling](grilling.md#規劃期可行性門檻) 驗證；產品票引用版本、契約與限制。
3. **票券責任清楚**：每票具備程式碼交付、修改範圍、輸入／輸出／錯誤、具體前置契約、驗收方式及完成條件；共用部分有唯一 owner。
4. **獨立交付推演已通過**：產品決策、依賴與驗收責任已確認，平行分組與修改邊界一致。
5. **執行準備已盤點**：依下節建立本機執行表；在每項操作前確認其授權，放行依賴環境的工作前完成相應預檢。尚未建立環境不是規劃缺口，也不阻擋無相依工作。

只重驗服務狀態、有效設定、憑證／額度與版本等易變條件，以及新增或已變動部分。保留適用的研究與決策證據，不重新做整份調查。

若契約不完整，明記「規劃缺口」及受影響項目，在啟動其產品實作前補齊；不可假稱已完整開工。真正的新外部變化或規格矛盾走下方例外處理，不靠推測授權。

## 2. 準備環境與任務圖

### 依 TODO／AC 盤點與授權

Spec／tickets 完成後，主 agent 沿全部實作、驗收到收尾讀取 repo scripts、設定與適用規則，依 [可重現環境契約](environment-contract.md) 推導實際需要的工具、服務、資料與操作。結果只維護於 [本機執行表](subagent.md#執行表與唯一寫入者)，不回填產品 TODO／AC：

| 必要條件／操作 | 影響票與 TODO／AC | 方法與授權來源／界線 | owner 與使用時點 | 狀態、證據與下一動作 |
| --- | --- | --- | --- | --- |
| 由交付推導的 runtime、服務或隔離資源 | 具體依賴項 | repo 入口、允許操作及資料來源 | 主 agent 或指定 owner | 待準備／就緒／受阻與實測結果 |

- 核對 runtime／工具版本、安裝與驗證入口、目標平台、網路、ports、容量及隔離模式；fixtures、資料副本、帳號／憑證、API／模型與費用限制依實際需要盤點。
- 核對建立、修改、停止／重啟、部署／遷移、清理及失敗恢復的授權與資源歸屬，依下方「授權沿用」記錄來源及操作範圍。啟動 implement-spec 不自動授權未確認的外部費用或破壞既有資料。
- 環境準備與修復依 [環境自主處理](environment-contract.md#環境自主處理) 直接執行；方法不明時由 owner 調查並實驗，不等使用者提供操作方案。新增程式／設定／harness 由唯一 owner 實作並核對跨票修改範圍；只有可版本控制的交付變更才依責任移轉規則補入 ticket。
- 服務不可用、缺憑證或未授權的操作只阻擋實際依賴它的工作；記錄受影響項、解除方法與配置者，依「集中詢問與恢復」續作。待補測試憑證沿用 test 指引，不作整份開工門檻。
- 產品決策或方案成立的新缺口回到受影響需求釐清；本機準備與易變條件由執行流程處理。完成盤點不等於就緒，以實測證據放行各項工作。

### 授權沿用

- 以任務、目標資源、允許操作及費用／資料界線記錄授權。使用者自然語言明確要求的操作也是授權；「繼續」沿用已確認範圍，不要求特定口令，也不擴大到尚未授權的操作。
- 任務已包含「環境自主處理」的準備、診斷、實作、重驗及自有資源清理，新建任務專屬資源不另申請授權。普通測試失敗、候選 SHA 改變、review finding 或 session 恢復只觸發受影響條件重驗；只有超出該自主範圍的必要操作才確認差額。
- 一般開發驗證以完成任務所需的操作範圍確認；只有使用者明確限次、限時或另有限制時才按該限制執行。明確單次授權須記錄受限操作及實際執行證據：受限操作尚未開始，不因靜態審查或無副作用預檢失敗而宣告耗盡；若限制的是整個 runner，runner 已開始即按此界線計算。已達明確限制時保留剩餘工作，依集中詢問規則取得必要輸入。
- 從舊執行表恢復時，將「未授權／授權耗盡」回查使用者原始指示。Agent 或 reviewer 自加的限制由主 agent 校正；使用者已明確同意的限制仍有效，不能為續跑自行解除。

### 隔離與派工

- 主對話留在使用者的 `dev` 工作區協調；integration 與票級 worktrees 是執行位置，不是主對話的新位置。依 [Session 綁定](subagent.md#session-綁定) 指定工具工作目錄及子代理 session，續作時亦沿用此界線。
- 主 agent 自動載入 [worktree skill](../../.opencode/skills/worktree/SKILL.md)，建立本地 `<spec_name>-merge` integration 分支／worktree，以及 `.worktree/<spec_name>-tickets-<NN>` 票級 worktrees，並依契約配置各自的隔離環境；無需使用者另行呼叫。依該 skill 核對主 repo、路徑與基底，保留未知及使用者變更。
- 明確啟動 `implement-spec` 即包含本地 integration／票級 worktrees 與任務必要的隔離執行環境。先核對來源、歸屬與恢復方式，再依「環境自主處理」建立、啟動、診斷及修復，不逐項詢問 Docker／runtime／E2E 授權。
- 準備與恢復依 [可重現環境契約](environment-contract.md)，共用 repo 的可重跑入口。Owner 補齊當前任務需要的入口缺口；主 agent 交接入口與有效設定證據，不以每票臨時命令替代可重建環境。
- **環境就緒門檻**：Git worktree 建立完成後，依 worktree skill 實際完成適用的隔離設定、啟動與驗證。主 agent 在執行表記錄每個 worktree 的環境模式、程序／資源歸屬、ports／endpoint、資料位置與驗證證據，再放行依賴該環境的工作。需要 owner 建立 harness 的準備可先派工，產品驗收仍須等其就緒；純文件工作記錄無執行資源的依據。integration 在整合驗證前同樣通過此門檻。
- 續作時核對既有 worktree 與資源的實況，沿用仍有效的隔離環境並補齊缺項；建立目錄、宣告已授權或測試使用 mock 均不等於環境隔離已驗證。缺口依例外處理解除，已確認操作直接執行。
- 維護整份 TODO／AC 責任對照及執行表。每條依賴指向下游真正需要的已驗收成果；同一共用介面由唯一 owner 負責。
- 同時以背景 subagent 派出所有依賴已滿足、修改範圍互不衝突且環境容量足夠的票，每票獨立 session／worktree。必要環境準備可與不依賴它的工作平行；上游完成立即重算，不等待同批全部回報。可執行票未派出時，在執行表記錄具體依賴、修改衝突或容量證據，不以「單一 owner」將整批串行化。
- 預檢採可重跑的指令／腳本：核對實際程序的部署環境、runtime 版本、endpoint、必要服務、fixtures 與 provider 設定。記錄預期／實值及結果，秘密值不入證據。目標環境驗收前再執行；檔名或 container healthy 不代表政策設定正確。
- 執行前預檢及執行中發現測試 key 缺項時，使用 test 的 [Agent 測試憑證指引](../../.opencode/skills/test/references/test-env.md)。由指定配置者補 `.env.test` 空白欄位與配置清單，依集中詢問規則請使用者補值；不把測試憑證變成整份開工或應用部署門檻。
- 首先跑通最薄的真實產品路徑，提早發現 UI、API 與 runtime 接線問題。局部 probe 不替代產品驗收。

### 以真實先導票建立開發基線

接手盤點或開工預檢顯示本次開發路徑缺少可信的啟動、驗證或交付基線時，由主 agent 自主選擇先導票；已有適用證據則直接正常派工。首次接觸 repo 本身不是強制重建基礎的理由。

1. 從已確認且依賴可滿足的 tickets 中，優先選一張範圍小、能走過本次主要入口與必要接線的真實需求票，在既有執行表記錄選擇理由、待驗證阻力及下游。先導是排程標記，沿用原票 TODO／AC；需拆票或改責任時依規劃契約，不另造無產品成果的框架票。無合適票或尚無已確認任務時，只交付接手基線與缺口，不杜撰產品需求。
2. Owner 沿該票的實際呼叫、資料與驗證路徑做聚焦盤點，然後完成實作、驗證及獨立票級審查。環境與授權門檻照常適用；不以全庫 review 或清完歷史債務作為先導前提。
3. 開發中取得阻力或缺陷的證據後，依 [根因預防規則](review-prevention.md) 自主補齊最小入口、fixture、導覽／可信範例、共用能力或檢查。沿用同一 owner 與授權，在本票實際採用，與功能一起交付；審查時再驗證是否有效，無需等 review 才修已確認問題。
4. 只讓真正依賴新能力的票等待其已驗證 integration SHA；其他可開工票仍平行執行。必要準備先以明確 owner 完成，主 agent 依實際依賴排序，避免要求先導先通過才能建立它自己需要的環境。
5. 原票 AC、獨立審查及整合驗證通過，且必要基礎已實際接入、有可重跑命令與交接證據，即完成先導並恢復一般排程。已有局部通過成果可依部分交付規則解鎖下游；不因「還能改善」延長先導或放寬驗收。

以既有回報記錄首次有效驗證、返工、必要人工介入及新增檢查耗時。後續實際使用能力時核對適用性與成本，依根因預防規則調整；沒有使用情境就停止擴大，不為驗證重用而另派虛構需求。

## 3. Owner 自主完成整票

一次派工提供完整 ticket、範圍、依賴基線、授權、驗收與環境入口。owner 持續做到全部本票 TODO／驗收完成；普通測試失敗、fixture 修正、API 實作細節與局部 Green 由 owner 自行處理。遇到經診斷仍無法自主解除的阻擋時，依下方「局部受阻與部分交付」先交付可分離成果，並繼續本票其他可執行工作；部分交付不代表整票完成。

### TDD 與測試品質

- 使用 `tdd`，依已確認測試邊界列出必要情境，逐行為 Red → Green → Refactor。規劃已確認的 seams 直接沿用；不因 skill 的一般提示再次問使用者。
- Red 必須對應預期產品行為缺失；先排除 runner、語法、fixture 與服務錯誤。既有測試已涵蓋者重用，不故意製造 Red。
- owner 可修改產品、測試、fixtures 及必要設定。測試預期值來自 spec／已確認案例，不由實際輸出複製產生；禁止刪必要斷言、放寬授權、skip 失敗案例或改驗收來迎合實作。
- 既有測試修改記錄原因：測試錯誤修正、補覆蓋或已確認的契約變更。獨立 reviewer 檢查修改及其依據。
- 純文件或無可執行行為的變更記錄適當替代檢查，不套用產品 TDD。一般內部設計由 owner 決定，涉及需求或授權才升級。

### 分層驗證

使用 [test skill](../../.opencode/skills/test/SKILL.md) 選擇 repo 既有驗證工具與按需指引；執行前載入 [測試執行規則](test-execution.md)，設定有限時限與證據輸出。逾時、停滯或工具中斷依該文件診斷及清理後續作。

| 階段 | 必要證據 |
| --- | --- |
| 開發內迴圈 | 能抓住該問題的快速局部／元件／API 測試 |
| 接線及功能交付 | 契約整合、必要真實 runtime／UI 正反案例、受影響套件的既有 lint／typecheck／build |
| 合入 integration | 合併後受影響回歸、共用契約相容性 |
| 最終交付 | 全部 spec AC、跨票流程與指定環境驗收 |

選擇能證明行為的最小測試層級，但保留 spec 指定的真實 runtime／E2E 驗收。同一版本、同一環境且證據完整的結果可沿用；程式／測試或設定改動、merge、證據不足、flaky 疑慮時重跑受影響範圍。單純 staging／commit 不改內容免重跑。

候選修正、同步或整合時，載入 test 的 [增量驗證指引](../../.opencode/skills/test/references/incremental-verification.md)，分開判定影響範圍、結果快取與審查沿用；跨版本重用須有輸入等價及影響分析證據，未知則擴大檢查。固定候選後的長驗證可與審查並行，依 [交付管線](delivery-pipeline.md) 匯合放行。

### 提交與回報

在有意義且可還原的功能檢查點提交產品與測試，票完成或中斷交接時彙整 AC、命令、結果、環境及剩餘工作。每個小測試不另設主 agent 核准、分角色 commit 或 evidence commit 門檻。提交前核對 staged diff 與檔案歸屬。

## 4. 獨立票級審查與修正

owner 完成實作及必要快速檢查、停寫並固定候選 base／head 後，依 [交付管線](delivery-pipeline.md) 回報「程式就緒、驗證中」，可在剩餘必要驗證執行時開始審查。依 [session 生命週期](session-lifecycle.md) 新建未參與本票實作的 reviewer session 唯讀審查；最終 verdict 必須核對完整必要證據，後續區分修正複查與新視角審查：

- 逐項對照 TODO／AC 與實際產品接線，找出漏實作及未驗證行為。
- 依 [跨票 TODO 邊界](subagent.md#跨票-todo-邊界) 核對 diff 歸屬：是否夾帶別票實作、改寫或勾選別票 TODO／驗收；跨票變更須有主 agent 的責任移轉及受影響 owner 交接。只看本票測試通過不足以放行越界變更。
- 檢查正確性、權限／資料邊界、相容性及必要失敗案例。
- 檢查測試 diff、預期值來源、斷言是否弱化，核對證據版本、環境與指定驗收。
- 曾發生逾時／中斷時，核對停滯原因、取消與清理證據，以及原要求測試集合的重驗結果；不能以提高時限或局部成功結案。
- 依 [審查收斂的阻擋依據](review-convergence.md#每輪對照) 提供要求、證據與行為完成條件；主 agent 核對後整批派修，非必要建議另記。
- Reviewer 判定品質與證據，不核發操作授權。若某缺陷會使後續測試誤操作資源或失去有效性，指出具體因果及受影響測試；主 agent 暫停該部分並交 owner 修復，其餘有效驗證依交付管線繼續。操作授權依「授權沿用」獨立判定，不把每次測試變成額外審批。
- 發現具體缺陷時，依 [審查驅動的根因預防](review-prevention.md) 提供根因與共通證據；owner 修正時必須載入該規則，自主判定並建立、接入及驗證適用的共用能力、腳手架或檢查，不逐項詢問使用者。

主 agent 將阻擋問題一次交回原 owner 自主修正，連同根因預防判定與已採用措施一起交付；reviewer 針對修正及其影響複查。已通過且無新變更／疑慮的部分沿用結果；沒有問題就明確通過，不為增加輪次提出範圍外工作。

每輪修正與複查都依 [審查收斂規則](review-convergence.md) 對照 finding、版本與證據；同一問題無新證據反覆失敗、重開或要求矛盾時，主 agent 自主啟動診斷／爭點裁決，再交明確修正條件。輪數不取代驗收，也不因停滯重啟全量審查。

此為 `implement-spec` 必跑的票級交付審查；另行呼叫完整 `code-review` skill 仍由使用者明確要求，不重複啟動通用 skill 的自動全量 review。

## 5. 逐票整合與解鎖

1. 每票本身驗收與獨立審查通過後，由唯一 merger／主 agent 將精確交付 commit 合入 `<spec_name>-merge`，執行受影響回歸。局部受阻票可依下方部分交付門檻整合已通過的成果，保留整票未完成狀態。
2. 記錄 integration 通過的 SHA，才解鎖依賴該成果的下游。新票以所需的已驗證成果為基底；執行中的票依 [交付管線](delivery-pipeline.md) 評估基線漂移，有影響、衝突或無法證明相容時才同步並重驗。無影響證據支持時保留本輪候選，合入前仍核對當下 integration 並驗證實際合併結果。
   新增根因預防能力時，依 [共用預防規則](review-prevention.md) 協調唯一 owner、採用入口與跨票依賴，將已驗證成果交接後續票。
3. 合併／回歸失敗時保留證據，交原 owner 或明確的整合修正 owner 處理；暫不解鎖受影響依賴。其他無相依工作持續推進。
4. 整票已驗收、審查通過且 integration 回歸成功後，立即執行下方票級清理，不等待其他票或最終 spec 驗收。部分交付仍依部分交付規則保留續作所需資源。
5. 合併操作串行，產品實作可平行。修正以包含問題的 integration 版本為基底，不回到缺少其他票成果的舊分支猜修。
6. 全票完成後進行最終整合驗證；失敗轉成有 owner、AC 與完成條件的未完成修正項，繼續修到通過。已清理票需要修正時，從包含問題的已驗證 integration 基線重建票級環境，沿用原 owner 與交接紀錄。

### 票級即時清理

主 agent 在每張票整合回歸通過後立即負責清理；執行表區分「已整合、待清理」與「已清理」。清理完成才結束該票的執行生命週期，不把清理另寫成產品 TODO。

清理條件未滿足時，主 agent 自主排查並推進至可清理，不把「還不能清」當作停止點：

- **TODO 或部分交付未完成**：resume 原 owner 完成其餘可執行工作，依原門檻審查、整合與驗證；真正外部受阻時只保留續作必要資源並記錄解除條件，不為清理刪減驗收或假勾完成。
- **Review 通過但未整合，或合併回歸失敗**：立即安排整合；失敗由明確 owner 診斷、修正、重驗與必要複查，通過後接續清理。一般合併、程式或測試問題由 agent 自主處理。
- **證據未保存或程序仍在使用**：主 agent 保存並核對證據，協調 owner／reviewer 停止使用，依測試執行規則等待正常結束或取消、清理已確認歸屬的程序，再重驗清理條件。
- **未提交或未知成果**：先查 Git diff、程序與 session 紀錄，確認來源與責任；本次必要成果交 owner 完成提交、驗證與整合。保留使用者或其他任務成果，不強制刪除；查證後仍無法判定歸屬或需要額外授權時，才依集中詢問規則取得最小必要資訊。

每次修復或背景工作完成後立即重查上述條件，符合即清理；普通排錯不交回使用者決定。只有已確認的外部條件、授權或產品決策缺口才保留具體阻擋，其餘無相依工作繼續。

1. 核對整票 TODO／AC、審查及合併回歸證據，將必要 logs、報告與交接資料移至票級 worktree／volume 以外的持久證據位置，驗證可讀；保留精確交付 commit 與 integration SHA。
2. 確認 owner、reviewer 及本票背景測試／產生器已停止使用環境，沒有待提交或未知成果。下游只使用已驗證 integration 的程式碼與可重建 fixtures，不依賴本票存活的服務、ports 或資料卷；發現此依賴先修正交接，不能直接刪除仍被使用的資源。
3. 依執行表的資源歸屬，停止並移除本票 containers、自有程序、network、專屬 image tag／可安全移除的 image 及 volumes，釋放 host／E2E ports。保留 dev、integration、其他票與共用 image layers／build cache；使用精確識別清理，不執行全域 prune。
4. 核對工作樹乾淨、交付已整合及證據已移出後，移除本票 Git worktree。清理失敗時保留原因與剩餘資源 ID，立即排錯或記錄具體外部阻擋；不強制刪除未知成果，也不默默延至全票結束。
5. 重查 Git worktree 登錄、容器／network／image tag／volume 及本票程序已移除，ports 不再由本票占用；若 port 已由其他程序取得，不停止該程序。記錄清理結果與釋放容量，再重算可派工票。

Integration worktree 保留供後續合併與最終驗收，按整份收尾規則處理；票級清理不移除 integration。

已有執行中的舊版 Test／Green 配對或 ticket-to-ticket 分支時，先核對現況、已提交／未提交變更與執行程序，待原角色停寫後指定單一 owner 接手；保留既有成果與依賴歷史，不 reset 或重做已完成工作。

## 6. 排錯、例外與責任移轉

### 自主排錯

保留最小重現、命令、預期／實際與環境；提出可驗證假設，修正後重跑原失敗及受影響測試。無新資訊的重試改採診斷、既有證據核對或專項協助，不在同一失敗上盲目重跑。工具或程式難題不等於外部阻擋。

### 新發現的規劃缺口或外部變化

先查既有決策、授權及可行替代；已授權範圍內自行解除。Owner 在首次使用必要外部資源前做最小有效設定／連線／權限預檢；已提供 key 但注入錯誤由 owner 修復，缺少或無效的 key、權限或額度則保留遮蔽後證據。前置條件缺少標「前置受阻」，不當成產品斷言失敗或通過。

只有必要外部條件不可取得、授權不足或需要改變已確認產品契約時，才記為待使用者解除。發現時立即回報主 agent 並記錄，不立即發出阻塞式問題；先依下方規則完成本票與全局仍可自主推進的工作。相同失敗無新證據時停止盲目重試，保留診斷與下一步；單純遇到技術困難不能當作外部阻擋。

### 局部受阻與部分交付

1. 主 agent 將阻擋掛到具體 TODO／驗收 ID，記錄原因、已試方案、證據、原 owner、解除條件及下一動作。票可呈現「部分完成／部分受阻」，此為執行狀態，不新增 triage label。
2. 重算同票與跨票依賴，指向下游真正需要的成果及其驗收，而非僅指向整張票。維持原需求、授權與驗收的切分可自主更新票券及執行表；所有剩餘責任仍由原 owner 承接，正式移轉依責任移轉規則。
3. 部分交付須列出成果、對應 TODO／驗收、未涵蓋項及精確 commit。Owner 先整理出不夾帶受阻實作、可獨立整合的提交；不得直接合入包含未驗證相依變更的整條分支。無法安全分離時，相關成果保持未就緒，其他工作繼續。
4. 獨立 reviewer 核對成果的必要驗收已通過，且缺少受阻資源時仍可使用；特別檢查共用初始化、設定、schema 與啟動路徑。Mock 只支持其測試邊界，不能替代該成果必要的真實驗收。審查使用停寫的穩定交付，沿用唯一寫入者規則。
5. 唯一 merger 整合精確交付 commit，跑受影響回歸，記錄已驗證 integration SHA 及可供下游使用的成果，才解鎖相關工作。原票剩餘 TODO／驗收仍未完成；部分整合後保留 owner worktree 與必要資源，續作先同步已驗證基線，不重做或重複整合已交付內容。

### 集中詢問與恢復

主 agent 每次排程都先處理可執行的實作、診斷、部分交付、審查、整合及驗收。待這些工作已完成，且沒有仍可能產生可執行工作的背景任務，才集中使用 `question` 請使用者補充。等待期間受影響操作保持停止，不推測產品決策或越過授權。

問題清單依共用根因合併，列出必要 key／權限／配置或決策、遮蔽後證據、受影響 TODO／驗收、使用者最小操作、驗證方法及恢復動作；秘密值透過專案既有憑證入口配置，不要求貼入報告。取得部分或全部輸入後，先重驗已解除條件，立即恢復對應 owner 與下游，不等待其他無相依阻擋一併解除。

授權依本文件的「依 TODO／AC 盤點與授權」判定，包含使用者後續明確要求的操作；新增授權同步至本機執行表並續作。預檢若發現額外操作，將該差額列入集中問題，不重新確認整個已授權動作。

全部剩餘工作確實受上述外部條件阻擋、且沒有可推進工作時，回報「受阻、未完成」等待必要輸入；不得標完成或要求使用者重新啟動流程。取得輸入後沿現有狀態續作。規劃負責產品決策與方案可行性；執行授權、環境準備與待補測試憑證由本流程處理，不要求在其他無相依工作前先完成。

### 責任移轉

維持原範圍的拆票或責任調整由主 agent 記錄「原 TODO／AC、未完成內容、原因、承接票／owner、依賴、證據及完成條件」，同步兩側與總表。原票標示移交而非假勾完成；整份清單仍追蹤承接結果。需求／驗收變更需先確認。

## 7. 最終 integration review 與收尾

### PR 前的整合審查門檻

全部票整合後，主 agent 固定預定 PR 目標分支的 base SHA 與 integration head SHA，執行整份 spec AC／跨票整合驗證，並新建未參與本批實作或合併修正的獨立 reviewer session，審查實際整合版本及其相對目標分支的完整變更。這是必跑的最終 integration review，不能由票級審查或測試成功取代；不需使用者另行呼叫 `code-review`。

- Reviewer 直接核對 spec、各票責任、最終 diff 與驗證證據，重點檢查跨票介面、schema／migration、共用設定、初始化／接線、錯誤處理與相容性，以及合併解衝突是否遺失、覆蓋或重複交付。
- 審查期間固定候選、停止相關寫入；必要長驗證可依交付管線並行，reviewer 收齊同一版本的必要證據後才給最終結論。Integration worktree 與審查／驗證所需資源保留至本門檻通過，已清理的票級 worktree 無需為審查重建。
- 發現阻擋問題時，指定原 owner 或整合修正 owner，從包含問題的 integration 基線建立隔離修正環境，修正並整合；重跑受影響回歸及必要跨票驗收，由原最終 reviewer 複查新候選與影響範圍。修正環境仍依票級清理門檻處理。
- Reviewer 與修正 owner 載入 [根因預防](review-prevention.md) 及 [審查收斂](review-convergence.md)，沿用相同的預防措施、finding 追蹤與停滯裁決規則；最終審查不另開一套無界修正迴圈。
- 記錄 base／head SHA、reviewer session、findings 處置、驗證證據與 verdict。全部必要驗收成功且無未解阻擋，才產生可發布的 PR 交付報告或標示可合併。
- 發布 PR 前重核實際目標 base 與 head；任一改變都重新判定合併影響、驗證受影響範圍並交 reviewer 複查，不能沿用舊版本 verdict 宣告新版本通過。PR 更新提交也適用此門檻。

主 agent 核對所有 TODO、各票驗收、跨票 AC、審查問題及整合修正均有通過證據，實際交付與 integration HEAD 一致。各票 worktree 與專屬資源應已依票級即時清理移除；此處只核對清理紀錄與處理有明確原因的殘留，不首次集中清理全部票。確認沒有仍在執行的子代理／寫入程序或遺漏未提交成果，清理不再需要的 integration 執行資源；只處理已確認歸屬與授權的資源。

保留 integration 與證據，依 `pr` skill 架構產生 `pr/<識別碼>.html`（無 PR 編號用 spec／ticket 識別碼），包含 Summary、Evidence、Merge Danger；Evidence 引用最終 integration review 的 base／head、verdict 與跨票驗證結果。完成約定收尾後回報交付 SHA、驗收與狀態；不能以摘要代替剩餘實作。

本流程預設只提交本地，不自動推送遠端或建立 draft PR。使用者另行明確要求推送／發布時，依其授權核對目標分支、tag 與發布慣例後執行。PR 建立後核對平台必要檢查及衝突狀態，通過才標示可合併。
