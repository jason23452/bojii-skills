# 審查修正的停滯偵測與收斂

適用於 `implement-spec` 票級審查、最終 integration review，以及完整 `code-review` 已進入修正的迴圈。主 agent 負責收斂，owner 是唯一寫入者，reviewer 維持唯讀；單獨審查只回報 findings，不因此啟動實作。

## 每輪對照

沿用既有審查回報與執行表，以穩定 finding ID 記錄根因、位置、提出／複查 SHA，並提供以下阻擋依據；相同根因合併追蹤，不同根因另列：

- **要求**：違反的已確認契約／AC／repo 規範，或本次交付的具體正確性、資料／權限風險。
- **證據**：可重現情境或明確可達的程式路徑，以及預期／實際差異；不強制 reviewer 執行測試，也不接受只有「可能不安全／不夠完整」的結論。
- **完成條件**：可檢查的行為結果及受影響驗證，不把 reviewer 偏好的實作方式當成唯一解法。

主 agent 派修前核對這三項；缺依據者先交 reviewer 補證或列非阻擋建議，仍推進無相依工作。有可信但尚未釐清的嚴重風險時只暫停受影響操作，立即安排針對性取證；不能因欄位未齊就忽略風險，也不能把待查猜測直接擴成新需求。

Owner 回報修正 commit、對應驗證與剩餘問題。Reviewer 將各項標為已解決、未解決、因新證據重開或不成立，附判定證據；重開須指出新證據或原通過證據的缺陷。複查以修正及影響範圍為主，沿用同版本、同環境的有效證據。範圍外偶然發現的真實缺陷仍記錄並交主 agent 指派責任，只有影響本次驗收或交付安全的問題才阻擋本票；偏好與無共通證據的泛化建議不追加為必要工作。

## 停滯觸發

主 agent 每次收到複查結果即比對；以下任一情況改採診斷／裁決，不直接重送相同修正指令：

- 同一 finding 經一次修正仍以相同失敗重現，且沒有新定位或已排除假設的證據。
- 已通過的 finding 被重開，卻沒有新證據或原證據缺陷；或 reviewer 前後修正條件互相矛盾。
- 連續兩輪修正複查既未解除任何阻擋，也未取得可縮小根因的新證據；新引入的回歸另行追蹤，不能用關閉舊 ID 掩蓋。
- 預防措施持續擴大到無現有使用情境支持的抽象，或要求與已確認契約衝突。
- 驗證入口連續兩輪修正仍無法開始原定產品驗證，即使每輪關閉不同 finding，也須依 [驗證入口的收斂](environment-contract.md#驗證入口的收斂) 重估環境與 harness 方案，而非只繼續追加 guard。

輪數只觸發處理方式改變，不是自動通過、停止任務或更換 session 的理由。

## 自主收斂

1. 主 agent 核對同一穩定版本上的 finding、契約、修正 diff 與原始證據，區分產品缺陷、環境／驗證失敗、審查誤判與需求歧義。環境停滯依 `test-execution.md` 診斷、限時與清理；外部依賴受阻則依 `implement-spec.md` 繼續其他可推進工作。
2. 產品根因未明時，由原 owner 依 `diagnosing-bugs` 建立最小重現與可否證假設，先補證據再改碼。一般內部判定由主 agent 依契約裁決；證據仍互相衝突時，指派未參與產出的唯讀診斷／裁決代理，只檢查爭點，不重跑全量 review。這是爭點裁決，不算新一輪完整獨立審查。
3. 主 agent 一次交付裁決依據、仍有效的 findings、明確完成條件及下一個驗證動作給原 owner；不成立者附證據關閉。必要根因預防沿用 `review-prevention.md`，將超出證據的擴張縮回最小有效措施。
4. 修正後由原 reviewer 核對裁決條件、修正與新回歸；若仍持異議，提出反證回到爭點裁決，不要求 owner 在互斥方案間反覆切換。Session 校正與換新依 `session-lifecycle.md`，換新不清除 finding 與停滯紀錄。

已確認缺陷與已採用預防措施均有通過證據才放行。證據不足時保留未完成，記錄已排除假設與具體下一動作；只有必需外部條件或未定產品決策才循原流程集中詢問使用者，不以普通審查爭議要求使用者選修法。
