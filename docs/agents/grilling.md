# Grilling 互動提問

適用於 `grilling`、`grill-me` 與 `grill-with-docs`：

## 訪談前蒐集脈絡

- 先列出會改變本輪決策的未知；repo 或可靠來源可查明的事實自行調查。預設主 agent 聚焦查證，不固定開三路研究；簡單問題直接讀相關入口與既有決策即可。
- 下表是按需查證方向，不是每次必填清單。先搜尋定位，再讀相關段落；已有適用證據直接引用，不重新掃描整個 repo、歷史或重貼全文。

| 查證方向 | 需要時查明的內容 |
| --- | --- |
| Repo 現況 | 實際入口、呼叫流程、資料與測試；區分已實作、只有文件及尚未驗證的行為 |
| 歷史脈絡 | 相關 specs、tickets、ADR 與必要的提交紀錄；過往取捨、未完成事項、曾排除的方案及原因 |
| 使用情境與影響 | 現有操作流程、使用角色、上下游影響、例外情境，以及需求與既有行為的差異 |
| 外部方案與技術限制 | 官方文件、原始碼、相關工具及公開案例；替代方案、版本相容性、宿主限制與可驗證方式 |

- 只有可獨立且需要較多閱讀的問題才委派，通常一個研究 subagent 足夠；確有互不重疊的關鍵問題才增加。派工提供具體問題、查證範圍、既有證據與停止條件；同題續問 resume，只傳新增缺口。研究代理不自行決定需求或修改產品。
- 歷史規格依 [issue-tracker.md](issue-tracker.md) 定位；只查會影響當前決策的 specs／tickets／ADR。外部查證用於第三方契約、版本限制或有實質取捨的選型，優先官方來源；有足夠直接證據就停，不強制蒐集多個替代方案或逐項交叉驗證。
- **提問按依賴放行**：只等待該題需要的查證。其他已具備事實基礎的問題可先問；未完成研究保留未知，不提前宣稱方案可行。矛盾先針對性補查，不重新展開全套研究。

## 調查回報契約

### 規劃期可行性門檻

- 只深入會改變需求可行性、方案、公開契約、驗收或票券依賴的關鍵未知。一般實作細節與產品回歸留給 owner；研究結論足以支持本次決策與拆票就停止，不以窮舉所有情境為目標。
- 文件／原始碼不足以證明可行時，在規劃階段以最小隔離 probe 或原型取得證據。隔離實驗環境依 [環境自主處理](environment-contract.md#環境自主處理) 自行準備與修復；模型／付費服務及既有資料操作另核對其使用界線。規劃實驗可產生 probe、fixtures 與證據，不把原型當成已交付產品。
- 組合行為仍存在關鍵未知時，以一條代表性最薄路徑驗證，例如參數與授權是否能跨入口保留；由原查證者完成即可，不強制再開角色。已有相同版本與邊界的直接證據可沿用，不在規劃階段預做完整產品 E2E。
- 交付可重跑的命令／probe、版本與環境、預期／實際結果、選定契約、限制及受影響需求。模型實驗須先核對 parent／child 的模型解析與覆寫路徑，採可用的限制機制，執行後核對實際模型；發現偏差停止相關呼叫並先排錯。
- 關鍵方案未證實時，保留「規劃研究未完成」及下一步。需要環境或授權即在此階段處理；無法取得時回報具體缺口。可記錄需求草案或獨立研究任務，但不將未知轉成產品實作批次的前置研究票，亦不宣稱受影響方案已可實作。
- 完成標準：關鍵未知已有支持決策的直接證據（適用的官方契約、原始碼或實測），必要的組合未知已解；證據不足仍明記未完成。環境重建、易變條件與完整產品回歸由實作階段驗證，不重複研究已解問題。

調查回報使用短摘要：**結論 → 關鍵證據 → 剩餘未知／需決策事項**。通常 5–8 個重點內即可，必要矛盾與限制仍須明列。來源附檔案／行號或 URL／版本／查證日期，區分實測、來源宣稱與推論；長 log、原文及 probe 留檔引用，不重貼。只有會影響選擇時才比較替代方案，不另造一份重複 spec。

主 agent 依證據呈現重要方案差異與推薦理由。外部做法不是使用者需求；未驗證相容性不標為可行。

## 互動式提問

- 所有訪談、追問、補充與確認都用 `question`，不以一般文字提問。
- 依決策依賴分輪，一次問本輪所有可回答問題，收到回答才進下一輪。每輪重檢決策樹；新情境／依賴／假設先查證再問，不因已有推薦就略過替代方案與邊界。
- 每題推薦選項置首並標「（建議）」；自由回答用內建自由輸入，確實可複選才啟用多選。
- 用具體情境釐清正常流程、角色／時機、部分成功、失敗、重試、取消、修改、刪除、舊資料與上下游影響，說明選項後果。
- 確認保留行為、範圍外與可觀察驗收。單題同意不代表未問情境已達共識。

## 需求對齊完成門檻

- 依需求／決策覆蓋收尾，不以輪數、題數、人數或時間判定；影響範圍／驗收的重要未知須繼續查問。
- 確認本次相關的主要情境／例外、歷史衝突、取捨、範圍與驗收已對齊；沒有實質影響的分支直接略過，不逐項寫「不適用」或追問假想情境。
- 依上方可行性門檻核對未驗證事項；影響方案與拆票的假設未解時繼續規劃研究，不以使用者同意未來驗證取代完成。僅不影響選定方案的易變條件，記錄實作時的重驗方式與失敗處理。
- 彙整需求、選擇理由、保留行為與未驗證事項處理方式，經 `question` 確認共識才更新領域文件。
- 交接 spec／tickets 時，提供產品決策、研究版本與適用條件；已確認授權保留在來源供後續沿用。依 `spec-and-tickets.md` 推演程式碼交付、修改邊界、依賴與驗收；產品批次的環境盤點及準備由實作入口根據 TODO／AC 推導。規劃實驗與實作採相同的環境自主範圍。

## 訪談後更新領域文件

- 共識確認後，自動更新已解決概念與決策的領域文件，不只提出建議。
- 將已釐清的領域詞彙記入 glossary。只有決策同時具備難以逆轉、未來讀者難以理解其原因、且涉及真實取捨時，才新增 ADR。
- 不補寫未確認事項；沒有新概念或合適 ADR 時，不建空文件或無實質更新。
- `grill-with-docs` 更新後依 repo 慣例自動 commit，僅包含本次訪談的領域文件變更，排除無關及使用者未提交修改。
