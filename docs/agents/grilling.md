# Grilling 互動提問

適用於 `grilling`、`grill-me` 與 `grill-with-docs`：

## 訪談前蒐集脈絡

- 在開始 grilling 前，先根據使用者問題判斷需要哪些背景事實；不得把可由專案或可靠外部來源查明的事實直接當成問題丟給使用者。
- 主 agent 先拆分調查範圍，再平行派出至少 2 個 subagent；通常依下表分成 3～4 路，獨立領域更多時增加人數，範圍單純時可合併角色。每路提供使用者原始需求、相關文件指標、具體調查問題及預期證據，避免只要求泛泛探索 repo。

| 調查角色 | 必須查明的內容 |
| --- | --- |
| Repo 現況 | 實際入口、呼叫流程、資料與測試；區分已實作、只有文件及尚未驗證的行為 |
| 歷史脈絡 | 相關 specs、tickets、ADR 與必要的提交紀錄；過往取捨、未完成事項、曾排除的方案及原因 |
| 使用情境與影響 | 現有操作流程、使用角色、上下游影響、例外情境，以及需求與既有行為的差異 |
| 外部方案與技術限制 | 官方文件、原始碼、相關工具及公開案例；替代方案、版本相容性、宿主限制與可驗證方式 |

- 調查 subagent 使用下方「調查回報契約」，不套用 `subagent.md` 的 implement-spec 實作交接格式。Subagent 只負責查證與建議；需求決策由主 agent 彙整後向使用者確認。
- 依 `docs/agents/issue-tracker.md` 尋找與本次問題相關的既有 `spec.md` 和 tickets；閱讀已完成項目的描述與決策，並在必要時對照程式碼或提交紀錄，了解先前如何實作。只讀取相關資料，不把歷史方案直接假設為目前仍適用。
- 涉及技術選型、第三方整合、架構取捨或可借鏡的使用流程時，派出外部調查 subagent 搜尋並比較相關方案，不能只沿著 repo 既有實作推導需求。優先查官方文件、原始碼與其他一手來源，記錄 URL、適用版本／revision 及查證日期；公開案例僅作其已證實範圍的參考。外部研究對本題無實質幫助時，說明原因並聚焦 repo。
- 提問前，必須等待本輪派出的所有 subagent 完成調查並回傳結果，包含後續追加的調查；主 agent 收齊結果前不得開始提問。等待期間可進行獨立查證或提供進度摘要。
- 主 agent 收齊結果後，交叉核對 repo 現況、歷史規格與外部方案。調查結果互相矛盾或缺少關鍵證據時，追加針對性調查；可查證的缺口先補查，完成後再建立決策樹，僅將需要使用者判斷的事項轉為問題。調查以能改變需求或方案選擇的問題為範圍，不做無關的廣泛研究。
- 每輪提問的完成門檻：所有 subagent 結果已收齊，且主 agent 已完成彙整。若調查失敗或受阻，先重試或由主 agent 接手完成；未回傳結果不視為調查完成。訪談中若新增調查，下一輪提問也須通過相同門檻。

## 調查回報契約

每個調查 subagent 必須回傳：

1. **調查範圍與結論**：回答被指派的問題，區分已驗證事實、來源宣稱與推論。
2. **證據與來源**：本地檔案路徑、行號、測試或提交；外部來源附 URL、版本與查證日期。文件宣稱與實際程式行為不同時，兩者並列。
3. **需求差異與衝突**：目前行為、歷史決策、使用者目標及外部方案之間的差異，以及受影響範圍。
4. **選項與取捨**：可行選項、適用條件、優缺點、相容性、遷移成本與驗證缺口。存在實質替代方案時比較多個選項，包含沿用／調整現有架構；不為湊數加入不相關方案。
5. **未知事項與下一步查證**：列出尚未確認的假設、可行查證方法；無法取得資料時說明限制，不以推測填補。
6. **建議深入追問**：列出需使用者決定的情境、邊界與取捨，說明不同答案會如何改變需求或設計。

主 agent 依證據整理方案比較，對重要取捨向使用者呈現差異與推薦理由。外部做法是決策參考，不直接當成使用者需求；未驗證的相容性不標為可行結論。

## 互動式提問

- 凡是向使用者提出的問題，一律透過 OpenCode 的互動式 `question` 工具提出；禁止以一般文字提問。此規則涵蓋訪談、追問、補充資訊與確認問題。
- 依決策依賴關係分輪提問；每輪一次提出目前所有可回答的問題，收到使用者回答後再提出下一輪。
- 每輪回答後重新檢查決策樹。回答引入新的使用情境、依賴或技術假設時，先調查受影響部分，再提出依賴該結果的問題；不因第一輪已有推薦方向就跳過替代方案與邊界。
- 每題提供建議答案，並將建議選項放在第一個選項且標示「（建議）」。需要自由回答時，使用工具提供的自由輸入選項；只有題目確實允許複選時才啟用多選。
- 以具體使用情境釐清正常流程、角色與操作時機，以及相關的部分成功、失敗、重試、取消、修改、刪除、舊資料銜接與上下游影響；說明各選項的實際後果，不只問是否同意推薦方案。
- 明確確認必須保留的行為、範圍外事項與可觀察的驗收方式。使用者同意單題只代表該決策已確認，不代表未問及的情境也已達成共識。
- `grill-me` 遵循 `grilling` 的互動訪談流程。

## 需求對齊完成門檻

- 以需求與決策覆蓋程度決定是否完成，不以固定輪數、題數、調查人數或已花時間收尾。仍有會影響範圍或驗收的重要未知事項時，繼續針對性調查與訪談。
- 收尾前逐項確認：主要使用情境與相關例外、既有行為與歷史決策衝突、重要方案取捨、範圍內外及驗收方式都已對齊。對不適用的面向說明理由，不機械式追問所有可能情境。
- 尚無法驗證的技術假設，須明確列出驗證方式、通過條件與失敗時需重開的決策，並由使用者確認此處理方式；不能把同意進行驗證寫成技術已可行。
- 主 agent 彙整已確認需求、選擇理由、保留行為及未驗證事項的處理方式，透過 `question` 確認共識後，才進入領域文件更新。

## 訪談後更新領域文件

- 每次使用 `grilling`、`grill-me` 或 `grill-with-docs` 完成訪談並與使用者確認達成共識後，都必須依訪談中已解決的概念與決策，自動更新相關領域文件；不得只提出更新建議而不執行。
- 將已釐清的領域詞彙記入 glossary。只有決策同時具備難以逆轉、未來讀者難以理解其原因、且涉及真實取捨時，才新增 ADR。
- 不得自行補完或記錄尚未達成共識的事項。若沒有任何新的領域概念或符合 ADR 條件的決策，不建立空文件或無實質內容的更新。
- `grill-with-docs` 遵循上述流程，並在領域文件更新完成後自動建立 git commit，遵循 repo 既有的 commit 慣例。commit 僅包含本次訪談產生的領域文件變更，不得納入其他無關或使用者尚未提交的修改。
