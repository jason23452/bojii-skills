# 審查驅動的根因預防

票級審查、最終 integration review 與完整 `code-review` 共用此規則；[真實先導票](implement-spec.md#以真實先導票建立開發基線) 開發中已取得證據的阻力與缺陷也適用。從實際問題長出最小預防能力，降低後續實作與修正成本；首次實作沿用既有能力，依實際發現再演進。

## 自動化品質防線優先

本流程的 code-review 由 agent 自動執行，既有 CI 檢查由工具執行，均不以使用者人工讀碼或人工審查作為放行條件。使用者實際操作後發現並回報 bug，是觸發缺陷修復與防線演進的入口；agent／測試自行發現的具體缺陷也直接處理。

**被動觸發、持續防禦**：一般開發沿用 repo 既有自動檢查。新增或擴充 CI 防線由實際缺陷觸發，例如使用者回報某功能在特定情境 crash，經重現或證據確認是某種寫法造成後，在該次修復中補上能攔截同類錯誤的最小檢查，讓後續 agent 持續遵循。測試或 review 已證實的缺陷亦適用；僅缺少某工具或規則，不構成新增防線的理由。使用者明確要求建立品質工具時依該任務範圍處理。

先確認出錯情境與根因、修復產品，再以既有或新增檢查證明原問題可被捕捉、修正及合法寫法可通過，接入既有 CI。可靜態辨識的錯誤模式用 lint／型別規則攔截；依賴執行情境的問題用回歸測試。以下是缺陷修復時的選型參考，不是每次開發必須補齊的工具清單。Agent review 聚焦工具未覆蓋的產品行為、跨模組契約與證據缺口。

| 要防禦的問題 | 最小適用防線 |
| --- | --- |
| 格式、語法、可靜態判定的錯誤寫法 | 既有 formatter／linter，例如 Ruff、ESLint；有成熟規則先配置，不先寫自訂掃描器 |
| 型別、空值及介面使用錯誤 | 語言／專案適用的編譯器、型別檢查或靜態分析；只宣稱工具實際涵蓋的條件 |
| Crash、例外、取消、併發或資源未釋放 | 經過真實失敗路徑的回歸測試，驗證退出狀態、錯誤處理及資源收斂；必要時用執行期分析工具 |
| 效能退化 | 先量測定位，再以代表性負載、可比環境及有依據的門檻建立 benchmark 或效能回歸；可靜態判定的模式才交 linter |

自動檢查沿用同一個版本化命令，供 owner 本機快檢及 CI 使用；失敗回原 owner 修復。Lint 通過不代表無 crash 或效能問題，review 也不能用印象宣稱效能不佳。已有具體缺陷且可可靠自動捕捉時，依下節建立最小防線；沒有證據的假想問題不擴成新工具專案，無法穩定自動化時保留限制，由 agent 依契約與工具實測判斷。

Owner 自我檢查時，使用既有 CI 的適用命令或沿用對本次候選仍有效的結果，判斷是否再次出現過去已納入防線的錯誤寫法。確認規則已啟用、涵蓋修改範圍且通過後，該類檢查即完成；不另啟 code-review 或逐行重查同一類問題。只有檢查失敗、覆蓋缺口或新的具體缺陷證據才深入調查。既定獨立交付審查核對這些結果，將 agent 判斷集中在本次 TODO／AC、接線與工具未涵蓋的契約；不為已由 CI 證明的事項追加審查輪次。

### 根因模式的通用防線

使用者回報 bug 或執行中發現具體缺陷時，由修正 owner 使用 `diagnosing-bugs` 定位根因；reviewer 維持唯讀，將缺陷與證據交回 owner。一般 code-review 沿用既有檢查，不為尋找假想 bug 啟動診斷流程。

1. **定義模式**：從已證實根因寫出觸發條件、違反的契約及合法例外，例如未等待非同步操作就釋放其資源。模式描述不綁原始檔名、變數名稱或單一輸入，也不將某種語法一律視為錯誤。
2. **選擇防線**：優先配置能辨識該模式的既有 lint／型別規則；不足時才建立小型 AST／語意規則。依賴執行狀態的模式採共用契約測試、參數化回歸或具固定 seed 的性質測試，實際涵蓋適用入口，不用文字比對冒充語意判斷。
3. **驗證可泛用性**：原缺陷案例須能失敗、修正後通過；以等價錯誤寫法及合法近似寫法確認攔截與誤報邊界。檢查範圍包含相關既有程式及後續新增檔案，沿用 repo 的 CI 觸發與掃描設定。只攔原事故的單一測試不得宣稱已涵蓋所有同類寫法。
4. **交接與沿用**：在既有規則設定、測試及交付紀錄留下「根因模式 → 檢查入口 → 適用範圍／例外 → 驗證結果」，供後續 owner 與 code-review 採用，不另建一套追蹤系統。無法可靠泛化時，保留原情境回歸並明記未覆蓋範圍，不為泛化擴建框架或阻擋已充分修復的交付。

通用性是攔截同一根因的等價錯誤，不是猜測 agent 的想法或禁止所有相似程式碼；範圍以可驗證的模式與合法例外為準。

## 審查與判定

Reviewer 維持唯讀。先核對適用自動檢查的版本、掃描範圍與結果，不逐行重做工具已覆蓋的格式／風格判斷；既有必要檢查未掃到，或具體缺陷證實規則不足／漏報時指出該缺口。對工具未覆蓋的具體缺陷附上根因、其他相同使用情境的證據及可行的預防方向；證據不足時標示待 owner 驗證。設計偏好與啟發式 code smell 先確認是否構成缺陷，再進入預防流程。

Owner 處理每項已確認缺陷或先導阻力時，先取得重現或實際操作證據，再檢查現有共用入口、規則與相同使用端，選擇最小有效措施：

| 根因 | 優先措施 |
| --- | --- |
| 已有預防能力，但未執行或未接入 | 修復執行入口、掃描範圍或使用端接線 |
| 工具已有明確規則 | 啟用或配置既有 lint／型別檢查 |
| 多個使用情境反覆手寫同一正確性條件 | 集中到共用模組或受約束介面 |
| 新增模組容易遺漏固定接線、設定或測試 | 建立腳手架／生成模板，優先引用共用能力 |
| 可機械判定的專案慣例，現有規則不足 | 建立小型自訂規則及正反案例 |
| 行為契約或個別錯誤 | 加入必要回歸測試並修正實作 |

通用化須有現有使用端或已確認下游需求支持，且合法例外可界定；一次缺陷也可觸發，不必等到再次犯錯。只有單一情境或抽象成本高於可證明收益時，採局部修正與必要驗證，回報一句判定理由。局部修正與既有／新增回歸已能消除本次根因時，即滿足預防責任，不再要求共用框架、腳手架或額外規則。非原交付必要的改善另列建議；已明確納入原 AC 的工作仍須完成。以消除根因為完成標準，不以新增腳手架數量為目標。

## 自主實作與責任

在 `implement-spec` 中，符合上述條件的內部重構、共用能力、腳手架、規則與必要指引更新屬預設實作授權：owner 自主建立、接入並驗證，不逐項詢問使用者，也不只回報建議等待下一輪指令。若需要改變已確認產品契約、額外外部權限或無法由既有需求判定的產品決策，正式實作期間依「不使用 question 工具」規則記錄並回報、暫停受影響操作；不得擴張授權或替使用者推定決策。

本地驗證工具依 [環境自主處理](environment-contract.md#環境自主處理)：既有工具無法涵蓋已確認根因時，owner 自主新增必要工具與開發依賴，記錄選型理由、依賴影響、版本及驗證結果，接入 repo 既有驗證入口；仍優先重用現有工具。

跨票共用能力由主 agent 依根因合併處理，指定唯一 owner、修改範圍與依賴，沿用既有執行表追蹤至完成；需要調整票券責任時依 `spec-and-tickets.md`。其他 owner 沿用該成果，避免平行建立同義入口。一般內部協調不升級為使用者核准。

單獨執行 `code-review` 時只回報問題與預防候選；已有實作 owner／修正授權時交回該流程執行。審查請求本身不授權 reviewer 修改產品。

## 驗證、接入與交付

1. 使用 `test` 與適用的 `tdd` 流程，證明原缺陷、修正結果及受影響合法情境；純文件改動使用適當替代檢查。
2. 當前使用端實際採用新增能力；生成模板須驗證代表性生成結果可執行且符合其契約。自訂規則涵蓋違規、合法及易誤判案例，先試掃裁決命中與既有債務，再接入阻擋檢查。自動修正另驗證輸出及行為影響。
3. 更新 repo 既有生成入口、實作指引或驗證命令，讓後續 owner 能找到並預設採用。自動防線接入既有 CI，確認實際觸發與掃描範圍；若 repo 尚無 CI 或平台權限不可取得，將可重跑檢查接入既有本機驗證入口，明記 CI 接線缺口與責任。後續 owner 交付適用變更時執行該入口或沿用有效結果，reviewer 核對證據；不能只有孤立腳本或待辦。既有交付紀錄分列「原 bug 修復／回歸結果」與「防線本機接入／CI 接入狀態」，本機通過不宣稱已受 CI 保護，也不無故擴建整套平台。沿用局部快檢與交付驗證，記錄新增檢查耗時；既有使用端遷移範圍與相容性須明確。
4. Owner 在既有交付回報附「finding／先導阻力與根因 → 措施與採用位置 → 驗證證據」，局部修正附判定理由。Reviewer 複查原問題、共通契約、實際接入、合法例外與受影響相容性；已確認採用的預防工作須完成才通過，無共通證據的泛化建議不阻擋交付。
5. 主 agent 整合並驗證後，以 integration SHA 與能力入口交接下游；適用的新票直接沿用，執行中的票依 [交付管線](delivery-pipeline.md) 判斷依賴與影響，需要採用新能力或受其影響時同步並重驗。已有無影響證據的固定候選不強制重啟。只針對新增修改與影響範圍複查，沿用仍有效的證據。

利用既有回報觀察同類 finding 是否再現、修正輪次、檢查與總交付耗時、誤報及維護成本。收益未經量測時標為預期；持續增加成本或誤報的措施由 owner 縮小、修正或移除，保留有效的缺陷驗證。
