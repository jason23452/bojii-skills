# 審查驅動的根因預防

票級審查、最終 integration review 與完整 `code-review` 共用此規則；[真實先導票](implement-spec.md#以真實先導票建立開發基線) 開發中已取得證據的阻力與缺陷也適用。從實際問題長出最小預防能力，降低後續實作與修正成本；首次實作沿用既有能力，依實際發現再演進。

## 審查與判定

Reviewer 維持唯讀。對具體缺陷附上根因、其他相同使用情境的證據及可行的預防方向；證據不足時標示待 owner 驗證。設計偏好與啟發式 code smell 先確認是否構成缺陷，再進入預防流程。

Owner 處理每項已確認缺陷或先導阻力時，先取得重現或實際操作證據，再檢查現有共用入口、規則與相同使用端，選擇最小有效措施：

| 根因 | 優先措施 |
| --- | --- |
| 已有預防能力，但未執行或未接入 | 修復執行入口、掃描範圍或使用端接線 |
| 工具已有明確規則 | 啟用或配置既有 lint／型別檢查 |
| 多個使用情境反覆手寫同一正確性條件 | 集中到共用模組或受約束介面 |
| 新增模組容易遺漏固定接線、設定或測試 | 建立腳手架／生成模板，優先引用共用能力 |
| 可機械判定的專案慣例，現有規則不足 | 建立小型自訂規則及正反案例 |
| 行為契約或個別錯誤 | 加入必要回歸測試並修正實作 |

通用化須有現有使用端或已確認下游需求支持，且合法例外可界定；一次缺陷也可觸發，不必等到再次犯錯。只有單一情境或抽象成本高於可證明收益時，採局部修正與必要驗證，回報一句判定理由。以消除根因為完成標準，不以新增腳手架數量為目標。

## 自主實作與責任

在 `implement-spec` 中，符合上述條件的內部重構、共用能力、腳手架、規則與必要指引更新屬預設實作授權：owner 自主建立、接入並驗證，不逐項詢問使用者，也不只回報建議等待下一輪指令。只有需要改變已確認產品契約、額外外部權限或無法由既有需求判定的產品決策，才循原流程處理必要輸入。

本地驗證工具授權：既有工具無法涵蓋已確認根因時，owner 可自主新增必要的本地驗證工具與開發依賴，記錄選型理由、依賴影響、版本及驗證結果，接入 repo 既有驗證入口；此授權適用於 `test` 的新增工具確認條款。仍優先重用現有工具；需新增外部服務、付費或權限的部分沿用既有授權與必要輸入流程。

跨票共用能力由主 agent 依根因合併處理，指定唯一 owner、修改範圍與依賴，沿用既有執行表追蹤至完成；需要調整票券責任時依 `spec-and-tickets.md`。其他 owner 沿用該成果，避免平行建立同義入口。一般內部協調不升級為使用者核准。

單獨執行 `code-review` 時只回報問題與預防候選；已有實作 owner／修正授權時交回該流程執行。審查請求本身不授權 reviewer 修改產品。

## 驗證、接入與交付

1. 使用 `test` 與適用的 `tdd` 流程，證明原缺陷、修正結果及受影響合法情境；純文件改動使用適當替代檢查。
2. 當前使用端實際採用新增能力；生成模板須驗證代表性生成結果可執行且符合其契約。自訂規則涵蓋違規、合法及易誤判案例，先試掃裁決命中與既有債務，再接入阻擋檢查。自動修正另驗證輸出及行為影響。
3. 更新 repo 既有生成入口、實作指引或驗證命令，讓後續 owner 能找到並預設採用。沿用局部快檢與交付驗證，記錄新增檢查耗時；既有使用端遷移範圍與相容性須明確。
4. Owner 在既有交付回報附「finding／先導阻力與根因 → 措施與採用位置 → 驗證證據」，局部修正附判定理由。Reviewer 複查原問題、共通契約、實際接入、合法例外與受影響相容性；已確認採用的預防工作須完成才通過，無共通證據的泛化建議不阻擋交付。
5. 主 agent 整合並驗證後，以 integration SHA 與能力入口交接下游；適用的新票直接沿用，執行中的票依 [交付管線](delivery-pipeline.md) 判斷依賴與影響，需要採用新能力或受其影響時同步並重驗。已有無影響證據的固定候選不強制重啟。只針對新增修改與影響範圍複查，沿用仍有效的證據。

利用既有回報觀察同類 finding 是否再現、修正輪次、檢查與總交付耗時、誤報及維護成本。收益未經量測時標為預期；持續增加成本或誤報的措施由 owner 縮小、修正或移除，保留有效的缺陷驗證。
