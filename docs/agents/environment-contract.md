# 可重現環境契約

適用於新專案開工、worktree 隔離、接手續作及測試。目標是讓不同 owner 使用同一套可重跑入口，避免每次重新猜測指令或依賴前次執行留下的資料。

設計參考 pstack 的專案驗證生命週期與共享狀態原則；來源及適用限制見 [研究紀錄](../research/pstack-environment-testing.md)。本文件是本 repo 的執行政策，不表示已有通用環境佈建器或 runtime 強制機制。

## 單一環境入口

### 流程版本同步

更新流程或派工／續作時，以本次已選定的版本為基準，核對主目錄、integration 與本次活躍票級 worktrees 的 `AGENTS.md`、適用 skills 及其引用文件；使用 `git worktree list --porcelain` 與執行表定位，不以主目錄更新成功代表全部生效。只補查相關文件的版本／內容差異。

- 主 agent 協調受影響 owner 在安全交接點停止相關寫入，沿專案更新入口同步同一版本。保留本地客製與未提交成果；有衝突時先在暫存目錄取得同版本公開套件，再比對合併，不能用整份覆寫或重設分支消除差異。
- 在既有執行表記錄 worktree、來源版本、適用文件內容識別、保留的客製差異與同步狀態。新建 worktree 同樣核對，避免從舊 integration 基底再次帶入舊規則。
- 同步後將變更指標交給 owner，要求從其實際工作目錄重新讀取並回報採用的規則及下一動作；已載入的 skill 內容若仍舊，須重新載入或以新 session 交接。進入 `project-handoff` 時一律整理文件交由新接手者採用目前 skills，不 resume 舊 session。檔案更新與代理採用分別確認；未完成者只暫停依賴新規則的操作，不宣稱全體已生效。

### 環境自主處理

使用者交付開發、測試、規劃實驗或環境配置任務，即包含完成該任務必要的隔離執行環境準備與修復。Agent 自行查明方法、實作、執行及驗證，不另詢問環境操作授權，也不設「單次試跑」門檻。

- 自主範圍包含安裝必要本地工具／依賴、下載公開測試依賴或映像、建立及重建任務專屬容器／網路／資料卷／程序、調整 ports／設定／fixtures、修正 runner／啟動與清理腳本，以及重跑必要的真實 runtime／瀏覽器驗證。
- 遇到不相容、啟動失敗或 guard 誤判，先取得實際錯誤與最小重現，再修正入口或選用滿足原驗收的較簡單環境；修復後自行重驗並回到產品交付。方法尚未查明是診斷工作，不是要求使用者決定能否繼續的理由。
- 所有權不明時先查證；port 被占用可另選專屬 port，既有服務不便修改可另建隔離實例。只有確實無法自行取得的憑證／主機權限、額外外部費用、必須改動非本任務資源或產品契約時，才提出具體必要輸入。工具層權限與使用者明確限制照常遵循。
- 以「已診斷原因 → 修復或替代方法 → 真實驗證結果 → 下一個交付動作」回報。環境修正與驗證由同一 owner 連續完成；必要獨立審查仍在交付時進行，不把普通修復拆成逐步批准。

### 依檢查的實際依賴分流

- 每項檢查列出必要工具鏈、設定、服務與資料，以實際 script／設定為準；lint、typecheck、build 等名稱本身不保證沒有服務依賴。
- 無服務依賴的檢查完成工具鏈及必要設定預檢即可執行，無需建立資料庫、Project 或啟動產品。其證據只支持該項檢查。
- 需要服務或外部資源的檢查，僅準備並驗證它所依賴的資源。某項產品環境未就緒時，其他無相依檢查持續執行，分別記錄狀態。
- 從零開發尚無可操作產品時，可先完成工具鏈、設定及 harness 實作；產品路徑保持待驗證，於可操作後補跑，避免以產品驗收作為開始建立產品的前提。

### 測試執行模式

**最小必要測試環境優先**：以本次選取的測試及其驗收邊界為單位，只準備必要工具鏈、程序、服務及最少 fixtures。先滿足驗收真實性、可重現及可靠隔離，再選擇資源與準備成本較低的方案；需要更多依賴的檢查開始前才擴充。最小化的是環境，不是刪減原定必要測試或降低驗收。

按檢查群組分別選擇 runner、受測應用與依賴服務的位置，不以 repo 有 Docker 或部署使用容器決定全部測試的模式。優先沿用既有入口的選取／配置能力；入口固定啟動整套環境且包含無關服務時，在已授權範圍內補上最小啟動路徑，保留完整驗收入口，不另建重複 runner。

- 純邏輯測試從 runner 與必要工具鏈開始；整合測試按實際邊界加入真實依賴，E2E 僅啟動該 journey 涉及的應用與服務。
- Fixtures 使用足以觸發目標行為的最少資料；只有案例需要既有資料特性時才使用已授權副本，不為一般測試複製整份 dev 資料。
- 替身只用於驗收邊界允許的依賴；資料庫語意、跨服務整合及容器行為等必要真實驗收，仍使用對應真實資源。記錄每個啟用資源服務哪些測試，無相依資源不納入本次啟動。

| 條件 | 優先方式 |
| --- | --- |
| 工具鏈在本機可重現，無服務依賴 | 本機 runner；lint、typecheck、build 與單元測試仍須核對實際依賴 |
| 需要資料庫等服務，本機可執行 runner／應用 | 混合模式：本機 runner／適用應用＋必要容器服務 |
| 需特定 OS／原生依賴、本機無法可靠重現，或驗收容器行為 | 對相關群組使用容器；記錄必要性及涵蓋範圍 |

本機與混合模式仍須隔離可變資料、ports、程序及 fixtures。容器專屬行為與 CI 指定驗收保留原門檻，不用本機替代結果放行；Docker 不可用時，記錄具體受阻檢查並繼續無相依工作。選擇與配置使用 test 的 [測試方式配置](../../.opencode/skills/test/references/test-setup.md)，將驗證過的模式與理由記入既有入口紀錄。

### 可重跑入口的責任

資源隔離與外連政策分開判定：專屬 network 用於區分本次資源，不自動要求禁止網際網路存取。只有產品驗收、既有安全政策或使用者明確限制要求時，才加入斷網、allowlist 或 proxy；記錄依據與必要目的地，並從實際 runner／應用位置驗證連線。既有外連限制仍須保留，不能為測通自行解除。

先查 repo 現有 scripts、Compose、fixtures 與 CI。沿用已能完成下列責任的入口；缺口由當前任務 owner 在既有授權內補齊可版本控制的腳本／fixture，不另建功能重複的工具。名稱由 repo 決定，下列是責任而非預設存在的命令：

| 責任 | 行為與完成證據 |
| --- | --- |
| 準備 | 依鎖檔／已確認版本建立相依、專屬設定及資源；可重跑，部分完成可辨識並續作 |
| 預檢 | 唯讀核對有效設定、環境身分與必要服務；缺項快速失敗，回報具體修復入口 |
| 最薄驗證 | 實際跑過必要的 fixture 建立、產品邊界及清理，證明可進入正式測試 |
| 驗證 | 依統一 test skill 執行指定檢查，保留原始結果、輸出與有限時限 |
| 證據 | 捕捉操作、結果與必要副作用，綁定程式及環境；存放在清理排除的路徑 |
| 清理 | 只停止／移除本次已確認歸屬的資源，重跑不誤刪其他工作 |

在實作階段的本機執行表維護入口的精簡索引：命令、工作目錄、必要設定名稱、適用平台、通過條件及 owner。腳本為操作權威，索引不複製實作；環境操作不寫入 spec／ticket TODO。可重用腳本與配置的新增／修改才屬程式碼交付，與本次執行的本機資源值分開。

需要產品環境而尚無可用入口時，使用 test skill 的專案專屬驗證指引建立 Launch／Doctor／Drive／Evidence／Cleanup 紀錄。先建立目標 worktree 與隔離設定，再於其中補齊入口並實跑一輪；有準備腳本不等於已證明可用。Readiness 須涵蓋該路徑適用的 migration、seed、前置資料與 auth，資料庫存活不能替代業務可操作。

### 驗證入口的收斂

- 新的網路、proxy、容器或跨 OS 拓樸，先在實際目標平台以最小隔離實驗驗證必要連線、資料掛載及自有資源清理，再擴充完整 runner。沿用有效證據；健康檢查之外仍須完成上述最薄產品路徑。
- Harness 的必要能力以當前驗收、已確認操作界線及實際故障為依據；優先配置既有工具。每項新增 guard 或抽象須指出保護的具體資源／契約與失敗情境，假想風險或未來可能重用不單獨構成阻擋需求。
- 準備或 runner 修正反覆阻擋產品驗證時，主 agent 依 [審查收斂](review-convergence.md) 區分產品、環境與入口缺陷，重估最小可行模式。能保持原驗收及授權界線的較簡單方案由 owner 自主採用；需要改變界線才確認差額。已有真實缺陷仍須修復，不以改名或切換方案略過。
- 入口能在指定平台完成必要路徑、保存可信證據並清理自有資源，即回到產品驗收；額外通用化不延長放行。必要的故障／取消案例依實際操作與 spec 驗證，不為所有假設狀態建立另一套平台。

## 預檢與環境身分

執行前盤點與執行中發現測試憑證缺項時，使用 [Agent 測試憑證指引](../../.opencode/skills/test/references/test-env.md)。`.env.test` 提供測試用 key，`.env.test.example` 為無秘密模板；先補空白欄位並繼續可做工作，集中回報取得及填值方式。測試依產品既有流程配置 key，不新增應用啟動／部署要求；缺值只阻擋相關真實測試，跨 worktree 傳遞與補值續作沿用該指引。

- 使用實際程序設定核對 worktree／版本、lockfile、runtime／API 版本、資料根目錄、URL、ports 與資源歸屬；不要只靠 `.env` 檔名、健康狀態或端口可連線判定正確。
- 啟動成功後記錄程序 ID 與啟動時間、實際 ports／URL、資料與 Compose 識別。Port 檢查有競爭窗口；以真正 bind／啟動結果為準，衝突時只重新分配本次資源，不停止未知占用者。
- UI、BFF、runtime、fixture 與清理入口讀取同一份本次環境設定。指定目標不符或必要值缺少時，在寫入資料前失敗；不偷偷改用 dev、其他 worktree 或正式服務。
- SDK／API 版本變動時，先跑最小契約驗證，核對方法、路徑、位置參數、回應結構及失敗語意。測試替身對未處理請求明確失敗；不以通用 HTTP 200 隱藏契約不相容。
- 秘密值留在本機或既有憑證入口，證據只記設定名稱、來源與可用性。跨平台使用 repo 支援的執行方式，不把某一 shell 的環境變數、程序清理或路徑語法當成通用方案。

## 自動恢復與結果有效性

- 快取重用依 lockfile、套件管理器／runtime 版本、平台與架構判定，並以必要相依與最薄驗證確認健全性；不因 `node_modules` 存在就跳過檢查。使用既有 frozen／locked 安裝方式；共享快取可沿用，每個工作樹的可變安裝狀態分開，同一目錄的安裝須串行。
- 可變狀態優先拆成每個 run／worker 專屬的資料、帳號、profile 與輸出檔。真正共用的 UI 或狀態由單一操作者或既有鎖機制控制；共享檔案由唯一寫入者彙整，不讓多個 worker 同時更新同一份 JSON。只有 worktree 不代表程序及資料已隔離。
- 同一 owner、版本、有效設定與存活資源的環境可重用；重跑前做必要預檢，不每次重裝或重建。程序／設定／版本改變及異常中斷後，重新確認受影響條件。
- 新建或已清理的隔離環境必須能靠上述入口重建。若只能手動建立 Project、複製未記錄的本機檔案或修補測試 URL 才能通過，視為準備入口缺陷，由 owner 修復。
- 啟動、fixtures、行為斷言與 teardown 的結果分開呈現；準備失敗時不繼續下游案例。重試前確認部分建立與所有權，取消與停滯依 [測試執行規則](test-execution.md) 處理。
- 環境或 UI 結果異常先 Doctor，再分類環境失效、驗證入口過期與產品缺陷。已證實暫態問題依 [共同執行上限](test-execution.md#共同執行上限) 重啟受影響部分並重驗；相同失敗無新資訊即轉診斷，不將自動重試當修復。其他無相依工作持續推進。
- 記錄證據對應的程式版本／未提交 diff、環境設定識別及命令。先前 Green 只支持相同適用條件；修改、合併或切換環境後重驗受影響範圍，不把舊結果套到新交付。
- 本機準備、fixture、設定與驗證入口修復依「環境自主處理」持續完成；回報受阻須附實際診斷、已嘗試方法及無法自行取得的具體條件。
- `implement-spec` 執行中發現上述缺項時，先停止受影響操作並回報主 agent；詢問時機依 [集中詢問與恢復](implement-spec.md#集中詢問與恢復)，其餘可執行工作繼續。各工具指引中的「詢問」沿用此排程，不要求 owner 立即中斷整份流程。

## 開工完成條件

逐項依上述依賴分流放行檢查。產品環境須入口可重跑、身分可確認、最薄路徑與清理已有成功證據，且清理後證據仍可讀，才放行依賴它的驗收。首次採用共同 harness 時先由一位 owner 跑通這個完整迴圈，再將其用於多票平行驗收；不需等待整張產品票完成。純文件工作記錄無需執行資源；從零開發依此準備即可，無需額外進入 project-handoff。
