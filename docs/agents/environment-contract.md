# 可重現環境契約

適用於新專案開工、worktree 隔離、接手續作及測試。目標是讓不同 owner 使用同一套可重跑入口，避免每次重新猜測指令或依賴前次執行留下的資料。

設計參考 pstack 的專案驗證生命週期與共享狀態原則；來源及適用限制見 [研究紀錄](../research/pstack-environment-testing.md)。本文件是本 repo 的執行政策，不表示已有通用環境佈建器或 runtime 強制機制。

## 單一環境入口

### 流程版本同步

更新流程或派工／續作時，以本次已選定的版本為基準，核對主目錄、integration 與本次活躍票級 worktrees 的 `AGENTS.md`、適用 skills 及其引用文件；使用 `git worktree list --porcelain` 與執行表定位，不以主目錄更新成功代表全部生效。只補查相關文件的版本／內容差異。

- 主 agent 協調受影響 owner 在安全交接點停止相關寫入，沿專案更新入口同步同一版本。保留本地客製與未提交成果；有衝突時先在暫存目錄取得同版本公開套件，再比對合併，不能用整份覆寫或重設分支消除差異。
- 在既有執行表記錄 worktree、來源版本、適用文件內容識別、保留的客製差異與同步狀態。新建 worktree 同樣核對，避免從舊 integration 基底再次帶入舊規則。
- 同步後將變更指標交給 owner，要求從其實際工作目錄重新讀取並回報採用的規則及下一動作；已載入的 skill 內容若仍舊，須重新載入或以新 session 交接。進入 `project-handoff` 時一律整理文件交由新接手者採用目前 skills，不 resume 舊 session。檔案更新與代理採用分別確認；未完成者只暫停依賴新規則的操作，不宣稱全體已生效。

### 實作階段以 test.md 為準

`setup-testing` 完成初始配置後，`test.md` 是本次 spec／tickets 測試環境的單一執行依據；其引用的 scripts 與共用文件屬同一入口。主 agent 與 owner 僅依其中定義的目標、設定來源、參數化規則、準備／預檢／測試／恢復／清理步驟執行，不重新選模式、替換服務或自行另建測試流程。新 worktree 的專屬 ports、資料與資源名稱依文件規則產生，不視為另選環境。

實作期間的 `test.md` 執行權威位於主 repo，由主 agent 在主工作區唯一維護；票級與 integration worktree 唯讀使用，不修改副本或以合併結果覆蓋權威檔。派工提供權威檔絕對路徑及內容 hash／版本；Owner 只能回報缺口與證據，測試結果寫入各自證據檔，由主 agent 更新執行表。權威檔若需修訂，主 agent 先核實差異與受影響驗收、在主工作區修訂及驗證，再通知相關 owner 重新讀取新版本；有版本差異時暫停受影響測試，不能各自在 worktree 修文件來取得通過。

`test.md` 同時是可交付文件。所有程式整合完成、最終受測版本與證據已同步至主 repo 權威檔後，主 agent 必須在最終 integration review 前，將同一版本同步至 `<spec_name>-merge` integration worktree 的相同 repo-relative 路徑，核對內容 hash 後提交到該 integration branch。這份提交版本是交付快照，不是第二個執行權威；owner 與 reviewer 不得編輯。Reviewer 唯讀檢查 integration branch 中已提交的快照及其 hash／受測版本。後續若需改 `test.md`，先更新並驗證主 repo 權威檔，再重新同步、提交及複查。交付檔放在 repo 內原有路徑（例如 `.scratch/<feature>/test.md` 或 `docs/testing/<feature>/test.md`），不可放進被忽略的 `.worktree/` 目錄。

初始配置須對每條測試路徑核對「觸發入口 → 處理與依賴 → 最終結果／副作用 → 清理」，並明列命令工作目錄、程式根目錄、設定來源、資料／輸出位置、目標 endpoint、必要參數與預期結果。區分主 repo 的唯讀契約／設定來源與 worktree 的受測程式及可變資料；以明確根目錄解析相對路徑，不能因從主 repo 讀文件而測到主 repo 的程式。既有入口須在代表性隔離 worktree 實跑相關最薄路徑；尚未存在的產品入口明列責任票與契約，先實測可用前置條件，產品建立後再驗證完整路徑。首次派工及新 worktree 使用時按文件檢查解析結果，錯誤路徑不得放行。

執行失敗仍依文件診斷與恢復，不設「環境失敗轉交另一套配置流程」分支。若已確認文件缺少必要步驟或與實況不符，owner 回報具體差異，主 agent 作為唯一維護者先核實並更新 `test.md` 及必要引用腳本，完成受影響驗證後再執行；需要使用者確認的目標／操作範圍仍先詢問。其他符合文件的工作可繼續，不能先繞過文件測通再補記。下方通用自主配置規則用於初始配置或獨立環境任務；產品實作期間受本節約束。

### Smoke test 放行門檻

`setup-testing` 先將最小測試路徑寫入主 repo 的 `test.md` 草稿，再實跑 **準備 → 就緒 → 一個代表性真實操作 → 可觀察結果斷言 → 清理**；全部成功且證據可讀，才標記環境可用並放行實作。操作應走現有產品入口與該路徑必要依賴；僅連線、程序存活或 health check 只能證明前置條件。互不相同的必要環境路徑各有最小 smoke，共用部分沿用，不提前跑完整回歸。

產品入口尚待實作時，先用既有工具對必要真實依賴執行最小操作並驗證結果／清理，明列「前置環境 smoke」及未涵蓋的產品路徑；產品入口建立後，owner 須先完成文件指定的「產品 smoke」再跑依賴它的完整測試。不得為前置 smoke 提前代做產品 TODO，也不能以它宣稱產品已驗收。

新 worktree 或會影響路徑的程式／環境變更後，owner 依權威 `test.md` 重跑受影響 smoke，再執行相關完整測試；同版本、同有效環境的成功證據可沿用。Smoke 失敗先按文件診斷與恢復，保持該路徑未就緒；文件有缺口仍由主 agent 在主工作區修訂，owner 不改副本或降低斷言。

### 暫停或關機後的恢復

使用者要求繼續既有任務時，依權威 `test.md` 恢復原測試環境，無需另請使用者啟動服務，也不重新選環境或要求再觸發 `setup-testing`。此為既有環境的恢復操作；尚在暫停／取消狀態時不自行啟動。

1. 先唯讀核對程式／文件版本、worktree、設定來源、資料與資源歸屬，以及必要服務的實際狀態。舊 PID、工具「執行中」紀錄或先前 smoke 通過均不證明現在仍可用；先確認原寫入者已停止，再交接續作。
2. 依文件的依賴順序、啟動命令與有限就緒期限，只啟動缺少的任務自有服務；已健康且身分相符者沿用。必要執行引擎未啟動時，使用文件記錄且現有權限允許的啟動方式。保留持久資料、未提交成果及既有測試資源，不以重建或清空全部資料代替啟動。
3. 核對恢復後的實際 endpoint、設定載入與資料位置，依文件重跑受影響 smoke 並保存新證據；通過後接續剩餘 TODO／驗收，不重做已完成交付。前次中斷操作先查明部分副作用，避免重複建立或發布。
4. 啟動失敗按共同時限與重試規則診斷及恢復。文件沒有必要啟動步驟時，由主 agent 先核實並補權威文件再執行；需要無法取得的權限、憑證或外部服務恢復時才回報具體缺項。未知 port 占用不直接終止；依文件的參數規則處理或回報差異。

`test.md` 必須記錄服務／引擎的狀態檢查、依賴順序、啟動／恢復命令、就緒條件、資料保留及 smoke 入口。初始配置在任務專屬資源上驗證一次「停止 → 依記錄重新啟動 → smoke」或沿用同條件有效證據；不必真的關機，不操作無關共享服務。新的程序與資源狀態寫入執行表，worktree 不修改權威文件。

### 環境自主處理

使用者交付開發、測試、規劃實驗或環境配置任務，即包含完成該任務必要的隔離執行環境準備與修復。先依下方「測試邊界與環境決策」確認目標與操作範圍；已有決策後，Agent 自行查明方法、實作、執行及驗證，不逐次重問環境操作授權，也不設「單次試跑」門檻。

- 自主範圍包含安裝必要本地工具／依賴、下載公開測試依賴或映像、建立及重建任務專屬容器／網路／資料卷／程序、調整 ports／設定／fixtures、修正 runner／啟動與清理腳本，以及重跑必要的真實 runtime／瀏覽器驗證。
- 遇到不相容、啟動失敗或 guard 誤判，先取得實際錯誤與最小重現，再修正入口或選用滿足原驗收的較簡單環境；修復後自行重驗並回到產品交付。方法尚未查明是診斷工作，不是要求使用者決定能否繼續的理由。
- 所有權不明時先查證；port 被占用可另選專屬 port，既有服務不便修改可在已確認範圍另建隔離實例。初次環境決策缺口依下節詢問；決策後只有無法自行取得的憑證／主機權限、額外外部費用、必須改動非本任務資源或產品契約時，才提出具體必要輸入。工具層權限與使用者明確限制照常遵循。
- 以「已診斷原因 → 修復或替代方法 → 真實驗證結果 → 下一個交付動作」回報。環境修正與驗證由同一 owner 連續完成；必要獨立審查仍在交付時進行，不把普通修復拆成逐步批准。

### 測試邊界與環境決策

`implement-spec` 啟動後自動將環境確認交給 `setup-testing`；該 skill 使用 `test` 完成配置、前置實測與 `test.md`，初始環境門檻通過後才開始產品實作。本文件提供共同政策，不另建立平行的確認流程；實作後的產品驗收不能由環境 probe 取代。環境不等於 repo 或容器，須由 agent 主動追查本次行為真正經過的邊界：

1. 從每個 TODO／驗收的可觀察結果反推輸入、觸發入口、處理流程、副作用及輸出消費端；對照程式呼叫、設定來源、既有測試及自動化流程。未實作部分依已確認契約追查，未知處明列，不把尚無程式視為沒有依賴。
2. 遇到流程跨越程序、資料、權限、系統或平台邊界時，追到實際負責者與目的端，確認資料從哪裡來、由誰處理、結果在哪裡被使用。每個新發現的相依項繼續追查，直到足以判斷該驗收的前置條件與結果；不以 repo 邊界或既有測試範圍作為停止點。
3. 對發現的邊界查明執行位置、版本限制、身分／權限、可用目標、必要狀態與資料、連線方向、建立及清理方式。專案資訊不足時按需查官方契約或做最小 probe；可查事實自行查，只有仍缺少的使用者決策與外部資訊才詢問。
4. 為每個結果選能直接證明它的最小測試組合，明列替身可覆蓋部分與必須真實執行的邊界。按實際契約推導成功、失敗及中斷後狀態，不固定套用案例清單或窮舉無關平台。整合型交付須有真實邊界證據，mock、dry-run、health check 或本機測試不能單獨證明外部串接成功；難以穩定製造的失敗可在允許邊界用受控替身驗證，保留未實測限制。

完成追查的判準是：每項驗收的必要邊界均有對應測試與環境，或具體未知、owner 及解除方法；能說明證據如何支持最終可觀察結果，而不只是某個中間操作成功。已有有效證據直接引用，只補缺口，不全庫泛查。

- **先查證再確認**：環境未定義、沒有可用目標且無已確認建立方式，或目標／設定來源／歸屬仍不清楚時，提出受影響 ID、已查事實及推薦方案，用 `question` 請使用者補充或確認。外部寫入須明確知道可用帳號與測試資源、允許的建立／發布／刪除範圍及費用條件；既有確認直接沿用。使用者可選由 agent 建立環境，不必自己建好。
- **確認後自主執行**：一般安裝、fixtures、資源建立、修復及重測沿用決策，不逐次詢問。外部服務沒有 sandbox 時可使用已確認的專用測試資源；不能默認改用正式 repository、正式 Release 或真實使用者資料。只有 token 存在不等於目標與操作範圍已確認。
- **外部資源也要隔離**：記錄實際遠端 ID、版本／URL、run 專屬名稱及清理責任；共享測試帳號的可變資源依 run 隔離或串行。從實際 runner 驗證網路、必要權限與可觀察副作用；非同步發布／回呼使用有期限的就緒判定，重試前查明是否已部分建立。限流與服務暫態錯誤依共同執行上限處理。

在既有驗證文件維護精簡對照：「TODO／驗收 ID → 行為與測試層級 → 本機及外部目標／必要資料 → 替身與真實邊界 → 命令／證據 → 狀態、owner 與下一步」。共用環境合併列示 ID，不複製票內 TODO。可重用模式、設定名稱、操作範圍與命令留驗證文件；秘密留憑證入口，當次程序、ports、遠端資源 ID 與執行狀態留本機執行表。

### 依檢查的實際依賴分流

- 每項檢查列出必要工具鏈、設定、服務與資料，以實際 script／設定為準；lint、typecheck、build 等名稱本身不保證沒有服務依賴。
- 無服務依賴的檢查完成工具鏈及必要設定預檢即可執行，無需建立資料庫、Project 或啟動產品。其證據只支持該項檢查。
- 需要服務或外部資源的檢查，僅準備並驗證它所依賴的資源。某項產品環境未就緒時，其他無相依檢查持續執行，分別記錄狀態。
- 從零開發尚無可操作產品時，可先完成工具鏈、設定及 harness 實作；產品路徑保持待驗證，於可操作後補跑，避免以產品驗收作為開始建立產品的前提。

### 測試執行模式

**最小必要測試環境優先**：以本次選取的測試及其驗收邊界為單位，只準備必要工具鏈、程序、服務及最少 fixtures。先滿足驗收真實性、可重現及可靠隔離，再選擇資源與準備成本較低的方案；需要更多依賴的檢查開始前才擴充。最小化的是環境，不是刪減原定必要測試或降低驗收。

按檢查群組分別選擇 runner、受測應用與依賴服務的位置，不以 repo 有 Docker 或部署使用容器決定全部測試的模式。優先沿用既有入口的選取／配置能力；入口固定啟動整套環境且包含無關服務時，在已授權範圍內補上最小啟動路徑，保留完整驗收入口，不另建重複 runner。

- 純邏輯測試從 runner 與必要工具鏈開始；整合測試按實際邊界加入真實依賴，E2E 僅啟動該 journey 涉及的應用與服務。
- Fixtures 使用足以觸發目標行為的最少資料；只有案例需要既有資料特性時才使用已授權副本，不為一般測試複製整份 dev 資料。
- 替身只用於驗收邊界允許的依賴；資料庫語意、跨服務整合及容器行為等必要真實驗收，仍使用對應真實資源。記錄每個啟用資源服務哪些測試，無相依資源不納入本次啟動。

| 條件 | 優先方式 |
| --- | --- |
| 工具鏈在本機可重現，無服務依賴 | 本機 runner；lint、typecheck、build 與單元測試仍須核對實際依賴 |
| 需要資料庫等服務，本機可執行 runner／應用 | 混合模式：本機 runner／適用應用＋必要容器服務 |
| 需特定 OS／原生依賴、本機無法可靠重現，或驗收容器行為 | 對相關群組使用容器；記錄必要性及涵蓋範圍 |
| 涉及外部服務或遠端發布／更新 | 本機或容器 runner ＋已確認外部測試目標；外部依賴與 runner 位置分開選擇，可與上述模式並用 |

本機與混合模式仍須隔離可變資料、ports、程序及 fixtures。容器專屬行為與 CI 指定驗收保留原門檻，不用本機替代結果放行；Docker 不可用時，記錄具體受阻檢查並繼續無相依工作。選擇與配置使用 test 的 [測試方式配置](../../.opencode/skills/test/references/test-setup.md)，將驗證過的模式與理由記入既有入口紀錄。

### 可重跑入口的責任

資源隔離與外連政策分開判定：專屬 network 用於區分本次資源，不自動要求禁止網際網路存取。只有產品驗收、既有安全政策或使用者明確限制要求時，才加入斷網、allowlist 或 proxy；記錄依據與必要目的地，並從實際 runner／應用位置驗證連線。既有外連限制仍須保留，不能為測通自行解除。

先查 repo 現有 scripts、Compose、fixtures 與 CI。沿用已能完成下列責任的入口；缺口由當前任務 owner 在既有授權內補齊可版本控制的腳本／fixture，不另建功能重複的工具。名稱由 repo 決定，下列是責任而非預設存在的命令：

| 責任 | 行為與完成證據 |
| --- | --- |
| 準備 | 依鎖檔／已確認版本建立相依、專屬設定及資源；可重跑，部分完成可辨識並續作 |
| 預檢 | 唯讀核對有效設定、環境身分與必要服務；缺項快速失敗，回報具體修復入口 |
| 最薄驗證 | 實際跑過必要的 fixture 建立、產品邊界及清理，證明可進入正式測試 |
| 驗證 | 依統一 test skill 執行指定檢查，保留原始結果、輸出與有限時限 |
| 證據 | 捕捉操作、結果與必要副作用，綁定程式及環境；存放在清理排除的路徑 |
| 清理 | 只停止／移除本次已確認歸屬的資源，重跑不誤刪其他工作 |

配置階段在既有驗證文件維護入口索引：命令、工作目錄、必要設定名稱、適用平台、通過條件及 owner；實作階段的本機執行表引用索引並記錄當次資源與結果。腳本為操作權威，索引不複製實作；環境操作不寫入 spec／ticket TODO。可重用腳本與配置的新增／修改才屬程式碼交付，與本次資源值分開。

需要產品環境而尚無可用入口時，使用 test skill 的專案專屬驗證指引建立 Launch／Doctor／Drive／Evidence／Cleanup 紀錄。在已確認工作目錄與隔離資源中補齊入口並實跑；實作票依 worktree 規則執行，外部服務沿用相同生命週期，不必為遠端服務另造本地 server。有準備腳本不等於可用；readiness 須涵蓋適用的 migration、seed、前置資料及 auth，服務存活不能替代業務可操作。

### 驗證入口的收斂

- 新的網路、proxy、容器或跨 OS 拓樸，先在實際目標平台以最小隔離實驗驗證必要連線、資料掛載及自有資源清理，再擴充完整 runner。沿用有效證據；健康檢查之外仍須完成上述最薄產品路徑。
- Harness 的必要能力以當前驗收、已確認操作界線及實際故障為依據；優先配置既有工具。每項新增 guard 或抽象須指出保護的具體資源／契約與失敗情境，假想風險或未來可能重用不單獨構成阻擋需求。
- 準備或 runner 修正反覆阻擋產品驗證時，主 agent 依 [審查收斂](review-convergence.md) 區分產品、環境與入口缺陷，重估最小可行模式。能保持原驗收及授權界線的較簡單方案由 owner 自主採用；需要改變界線才確認差額。已有真實缺陷仍須修復，不以改名或切換方案略過。
- 入口能在指定平台完成必要路徑、保存可信證據並清理自有資源，即回到產品驗收；額外通用化不延長放行。必要的故障／取消案例依實際操作與 spec 驗證，不為所有假設狀態建立另一套平台。

## 預檢與環境身分

執行前盤點與執行中發現測試憑證缺項時，使用 [Agent 測試憑證指引](../../.opencode/skills/test/references/test-env.md)。`.env.test` 提供測試用 key，`.env.test.example` 為無秘密模板；先補空白欄位並繼續可做工作，集中回報取得及填值方式。測試依產品既有流程配置 key，不新增應用啟動／部署要求；缺值只阻擋相關真實測試，跨 worktree 傳遞與補值續作沿用該指引。

- 使用實際程序設定核對 worktree／版本、lockfile、runtime／API 版本、資料根目錄、URL、ports 與資源歸屬；不要只靠 `.env` 檔名、健康狀態或端口可連線判定正確。
- 啟動成功後記錄程序 ID 與啟動時間、實際 ports／URL、資料與 Compose 識別。Port 檢查有競爭窗口；以真正 bind／啟動結果為準，衝突時只重新分配本次資源，不停止未知占用者。
- UI、BFF、runtime、fixture 與清理入口讀取同一份本次環境設定。指定目標不符或必要值缺少時，在寫入資料前失敗；不偷偷改用 dev、其他 worktree 或正式服務。
- SDK／API 版本變動時，先跑最小契約驗證，核對方法、路徑、位置參數、回應結構及失敗語意。測試替身對未處理請求明確失敗；不以通用 HTTP 200 隱藏契約不相容。
- 秘密值留在本機或既有憑證入口，證據只記設定名稱、來源與可用性。跨平台使用 repo 支援的執行方式，不把某一 shell 的環境變數、程序清理或路徑語法當成通用方案。

## 自動恢復與結果有效性

- 快取重用依 lockfile、套件管理器／runtime 版本、平台與架構判定，並以必要相依與最薄驗證確認健全性；不因 `node_modules` 存在就跳過檢查。使用既有 frozen／locked 安裝方式；共享快取可沿用，每個工作樹的可變安裝狀態分開，同一目錄的安裝須串行。
- 可變狀態優先拆成每個 run／worker 專屬的資料、帳號、profile 與輸出檔。真正共用的 UI 或狀態由單一操作者或既有鎖機制控制；共享檔案由唯一寫入者彙整，不讓多個 worker 同時更新同一份 JSON。只有 worktree 不代表程序及資料已隔離。
- 同一 owner、版本、有效設定與存活資源的環境可重用；重跑前做必要預檢，不每次重裝或重建。程序／設定／版本改變及異常中斷後，重新確認受影響條件。
- 新建或已清理的隔離環境必須能靠上述入口重建。若只能手動建立 Project、複製未記錄的本機檔案或修補測試 URL 才能通過，視為準備入口缺陷，由 owner 修復。
- 啟動、fixtures、行為斷言與 teardown 的結果分開呈現；準備失敗時不繼續下游案例。重試前確認部分建立與所有權，取消與停滯依 [測試執行規則](test-execution.md) 處理。
- 環境或 UI 結果異常先 Doctor，再分類環境失效、驗證入口過期與產品缺陷。已證實暫態問題依 [共同執行上限](test-execution.md#共同執行上限) 重啟受影響部分並重驗；相同失敗無新資訊即轉診斷，不將自動重試當修復。其他無相依工作持續推進。
- 記錄證據對應的程式版本／未提交 diff、環境設定識別及命令。先前 Green 只支持相同適用條件；修改、合併或切換環境後重驗受影響範圍，不把舊結果套到新交付。
- 本機準備、fixture、設定與驗證入口修復依「環境自主處理」持續完成；回報受阻須附實際診斷、已嘗試方法及無法自行取得的具體條件。
- `implement-spec` 執行中發現上述缺項時，先停止受影響操作並回報主 agent；詢問時機依 [集中詢問與恢復](implement-spec.md#集中詢問與恢復)，其餘可執行工作繼續。各工具指引中的「詢問」沿用此排程，不要求 owner 立即中斷整份流程。

## 開工完成條件

在 `implement-spec` 中，首次產品實作以 `setup-testing` 的整體環境放行為前置；下列逐項分流適用於環境準備及放行後的執行。初始缺項不阻擋其他環境查證／修復，但不提前派產品實作。尚未存在的產品路徑以已確認目標及可獨立驗證的前置條件放行，實際產品驗收留給 owner。

配置交接分為「已驗證可用」「待使用者補充」「待產品實作後驗證」「環境故障待修復」，均附受影響 ID 與下一步。已確認環境但產品尚未實作時，可放行對應 owner 建立產品／fixtures；未定目標只阻擋相關環境操作及驗收，其他工作繼續。配置文件完成、某群組就緒與整份產品驗收完成是不同狀態，不能互相代替。

逐項依上述依賴分流放行檢查。產品環境須入口可重跑、身分可確認、最薄路徑與清理已有成功證據，且清理後證據仍可讀，才放行依賴它的驗收。首次採用共同 harness 時先由一位 owner 跑通這個完整迴圈，再將其用於多票平行驗收；不需等待整張產品票完成。純文件工作記錄無需執行資源；從零開發依此準備即可，無需額外進入 project-handoff。
