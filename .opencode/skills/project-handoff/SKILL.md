# 專案接手盤點

目標是讓當前任務在已確認的基線與環境上續作。以實際 Git、程序、設定與測試證據核對歷史摘要；保留有效成果，找出會影響本次工作的隱藏依賴。

## 觸發判定

先依本次工作判斷，不以 repo 年齡、已有 Git commit 或新建 worktree 作為接手依據：

| 情境 | 執行流程 |
| --- | --- |
| 從零開發，尚無待承接的實作、執行狀態或環境依賴 | 沿用需求釐清、規劃與一般開工流程；本 skill 到此結束，不產生空盤點報告 |
| 首次建立隔離環境，或按已驗證基線正常派發新票 | 使用 worktree、環境就緒及測試前置資源規則；不額外執行接手盤點 |
| 接手他人／其他 Agent 的未完成成果，或恢復中斷任務 | 執行下方盤點，核對成果、所有權及遺留執行狀態 |
| 將已有工作搬到另一環境，需沿用既有設定、資料或測試證據 | 盤點受影響的環境依賴，重新確認就緒條件 |
| 正常開工時發現未記錄的既有資料、程序或前置操作依賴 | 對該依賴執行盤點，其他無相依工作依原流程推進 |

新專案之後也可能需要接手；舊 repo 的新票不必然需要盤點。直接呼叫本 skill 仍先做上述判定，已有適用證據則只補查變動。

## 1. 確認接手範圍與所有權

- 讀取專案 `AGENTS.md`、適用領域文件、當前任務與既有交接／執行紀錄。使用者未指定下一個任務時，聚焦建置、測試與環境入口，先產出接手結果；產品決策缺口才詢問。
- 核對主 repo、目前 worktree／branch／HEAD、未提交與未追蹤檔案、仍在執行的 owner／程序。既有修改先確認歸屬；接手前取得原 owner 停寫的交接，不 reset、覆蓋或清理未知成果。
- 接手盤點不移動主對話。`implement-spec` 的 session 綁定與唯一寫入者遵循 `docs/agents/subagent.md`；建立或修復隔離環境使用 `worktree` skill。
- 先唯讀盤點；沿用當前任務已確認的修復與操作授權。單獨要求盤點不代表授權修改共享資料、重啟服務或重做全部專案。

## 2. 建立可信的續作基線

沿本次任務的實際入口，將下列事實與歷史宣稱逐項核對：

| 項目 | 核對內容 |
| --- | --- |
| 已有成果 | 交付 commit／未提交成果、未完成項目、審查與驗收證據；局部成功不當成整票完成 |
| 執行環境 | 工具及鎖檔版本、有效設定、服務 endpoint、工作目錄、ports、資料與資源歸屬 |
| 測試入口 | 實際 runner／scripts、fixtures、前置 Project／帳號／檔案、準備與清理方法、有限時限 |
| 歷史問題 | 已知失敗、逾時、中斷與當時下一步；核對是否修復及其證據是否適用目前版本 |
| 跨環境依賴 | 固定本機路徑、舊 worktree URL、沿用 volume／Project、手動建資料，以及 SDK／API 升級後未更新的 fixture |

只擴查會改變本次可執行性或驗收結論的依賴。相同版本、環境與完整證據直接引用；環境、版本或所有權變動時只重驗受影響部分，不每次子代理回報都重新盤查全專案。

## 3. 驗證環境與測試自足性

- 使用 `test` 選擇 repo 既有驗證入口，依 `docs/agents/environment-contract.md` 核對可重跑的準備／預檢／清理，再依 `docs/agents/test-execution.md` 從隔離資料跑最薄測試路徑。已具備權限的方法直接執行；缺少權限或外部資源時記錄具體阻擋。
- 分別記錄「程式成果可沿用」與「目前環境已就緒」。原 worktree 通過不能代替新環境的準備與驗證；缺少測試 Project 不直接判為產品缺陷或機器故障。
- 新環境無法重建前置資源時，將建立、等待就緒與清理的缺口交給明確 owner；受影響驗收保持未就緒，其他無相依工作可繼續。
- 發生失敗／停滯時使用 `diagnosing-bugs` 與測試執行規則，縮小重現、定位契約或資源生命週期問題。只有舊版本證據或可比基線支持時才標「既有問題」；否則記錄「來源待確認」，不以歷史問題為由略過本次必要驗收。

## 4. 處置與交回執行

| 發現 | 處置 |
| --- | --- |
| 當前任務內、已有授權的準備或缺陷 | 指定 owner 修復並驗證後續作；沿用原 ticket，不額外要求使用者啟動 |
| 需要新授權、外部條件或產品決策 | 列證據、影響、解除條件及下一步；只阻擋受影響工作 |
| 無關歷史債務 | 記錄影響與建議承接者，不擴張成當前任務的全面清理 |

在 `implement-spec` 中，owner 將盤點結果與證據回報主 agent，由主 agent 作為唯一寫入者更新共享執行表；owner 需要落檔時使用票級 worktree 內的交接紀錄。獨立盤點則由本次 owner 寫入其負責的既有交接紀錄；無紀錄時使用本地 `.scratch/project-handoff/handoff.md`，先確認該檔無其他寫入者。不含 secrets，不另複製整份 spec 或 ticket TODO；若需建立正式 tickets，遵循專案規劃規則。

最小紀錄格式：

| 項目 | 觀察與證據（版本／環境／時間） | 影響工作 | 狀態 | owner／下一動作／解除條件 |
| --- | --- | --- | --- | --- |
| 具體成果或前置條件 | 實測結果或來源；未驗證明列 | 對應任務或驗收 | 已驗證／待準備／受阻 | 可執行動作及責任 |

**完成門檻**：本次依賴的成果與環境已核對、未解項目有責任與下一步、可執行與受阻工作可區分。盤點完成不等於所有問題修復；只有前置條件已驗證的工作才放行。`implement-spec` 取得結果後按原任務圖實際續作；單獨盤點則回報基線、遺留問題與建議執行順序。
