# To Tickets

先讀專案 `AGENTS.md`、tracker 與 `docs/agents/spec-and-tickets.md`（存在時），以其規劃契約為準。沿用對話、spec、領域文件與研究證據；只探索缺口或變動。

## 1. 建立交付與依賴圖

- 每票交付狹窄但完整的可驗收行為，涵蓋實際需要的層，不強迫每票都修改 schema、API 與 UI。
- 每票由單一 owner 自主完成產品、測試、fixtures 與驗收。可有多輪內部 TDD，不按 Test／Green 或單個測試拆票。
- 依規劃契約的「TODO 的獨立完成判定」檢查反向依賴：上游 TODO 須能在下游尚未實作時判定完成；消費接線與跨票驗收交明確承接票，不讓下游進度阻止上游勾選。
- 每條 `Blocked by` 寫明真正需要的前置成果。前置票混有無關工作時重新切分，不以整份 spec 完成作為單票前提。
- 依 `docs/agents/spec-and-tickets.md`「跨票互斥與平行判定」確認行為唯一負責，對有交集的票兩兩推演；共用部分先交接、獨立部分可平行、無法穩定切分則合票。判定留在既有 tickets 索引，不展開全票對矩陣。
- 大範圍機械重構採 expand–contract：先新增相容形式，再分批遷移使用者，最後移除舊形式。每批具備驗證，不把明知不相容的中間狀態當成已驗收基線。

## 2. 補齊交付契約

對每票明列：

1. 可觀察交付、範圍及 spec AC 責任。
2. 輸入／輸出、錯誤／例外、權限／資料政策與相容性；引用已確認來源。
3. 唯一負責行為／修改範圍、只消費的共用契約與接線分工、前置成果及有交集票的修改順序／交接條件。
4. 實作 TODO：產品程式、測試、fixtures、migration 或必要配置／腳本的交付。
5. 分開列出的驗收情境、預期結果、測試層級與必要目標平台。
6. 跨票承接的責任、AC 與完成條件。

產品決策在此階段用 `question` 釐清，關鍵可行性先完成研究，一般內部設計留給 owner。環境配置、各 worktree 準備及共用執行流程由實作入口承接；不列入 spec、ticket TODO 或產品驗收。

## 3. 確認與獨立推演

向使用者呈現交付與依賴，確認範圍、粒度及必要決策；已確認內容直接沿用。由未參與撰寫的 reviewer 推演所有票的交付、修改邊界、依賴與驗收，並交叉核對票對判定：排除重複實作、契約衝突及交接後的修改重疊。修正後只複查受影響票與關係，規劃阻擋解決才交接；環境就緒不是拆票門檻。

同時要求 spec／tickets 時可形成兩者後統一審查與提交確認。只建立 tickets 時，仍核對所引用 spec 的決策與研究。

## 4. 發布到 tracker

- **本地**：依依賴順序建立 `.scratch/<feature>/issues/<NN>-<slug>.md`，一票一檔；保留 tracker 規定的 Status、Blocked by 及 TODO／驗收格式。
- **遠端 tracker**：每票一個 issue，以原生 blocking 關係或明確文字記錄依賴；若源自 parent issue，依 tracker 慣例建立關聯。
- 狀態按產品決策與責任完整性判定；保留票級依賴。規劃完成不表示環境就緒，建立票券不等於父 spec 已完成。
- 建票、獨立規劃審查與必要修正完成後，交接 spec／tickets 路徑並提示下一步 `/implement-spec <spec 或 feature 路徑>`；環境配置由實作流程處理，不作拆票完成門檻。

## 票券摘要

```md
# NN：可驗收交付
Status: 依實際狀態判定
Blocked by: 無；或前置票及需要的成果

## 本票交付與 AC
使用者結果、範圍、AC ID 與後續承接。

## 行為契約
輸入／輸出、正常／失敗／例外、權限及決策／研究來源。

## 修改責任與依賴契約
本票唯一負責行為／修改範圍、只消費的共用契約與接線分工、前置成果／驗收 ID、有交集票的修改順序／交接條件；引用 tickets 索引。

## 實作 TODO
- [ ] T1：可判定完成的程式碼、測試或必要配置交付。

## 本票驗收
- [ ] V1：情境、預期結果、測試邊界與必要目標平台；證據待驗證。

## 後續承接
無；或承接票／AC、剩餘交付與完成條件。
```

具體檔案位置可作查證與交接指標，公開契約才是驗收權威；原型只保留能精準表達已確認決策的必要片段。
