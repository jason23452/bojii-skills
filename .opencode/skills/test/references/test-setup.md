# 測試方式配置

使用者要求配置測試、首次選擇執行環境，或現有方式有容器開銷／相容性／隔離問題時使用。選擇政策以 [環境契約](../../../../docs/agents/environment-contract.md#測試執行模式) 為準；本指引將決策落實到專案既有入口。

## 1. 盤點並選擇

- 讀取 scripts、鎖檔、runner 設定、fixtures、Compose、CI 與既有驗證紀錄，按測試群組列出工具鏈、服務、資料及平台需求。
- 分別確認 runner、受測應用及依賴服務的位置。比較方案的準備／啟動、重建、排錯與清理成本；未量測數字標為估計。
- 依環境契約選能滿足驗收的最小必要環境，再決定本機、混合或容器模式。列出「測試群組 → 必要程序／服務 → 最少 fixtures」，記錄擴充條件、選擇理由及與 CI／部署環境的差異。已驗證決策仍符合本次依賴時沿用；既有入口啟動無關資源時，優先補齊其選取／配置能力。

## 2. 配置可重跑入口

- 沿用 repo 的套件管理器、runner 與 scripts，依鎖檔及支援的平台配置工具鏈。新增工具與操作授權沿用 `test` 主入口規則。
- 僅啟動選取測試需要的應用及服務；設定 readiness、migration／seed、fixtures 與正常／失敗清理。容器服務使用明確的服務選取及相依範圍，避免啟動無關整套環境。
- 各 worktree／worker 隔離 ports、資料庫／資料目錄、帳號、瀏覽器 profile 及輸出；記錄程序與資源所有權。本機模式同樣受隔離契約約束。
- 混合模式核對 host port、容器內服務位址與 runner 實際 endpoint，由同一份本次設定傳遞。測試憑證依 [test-env.md](test-env.md) 配置，不能因改成本機就連到 dev 資料或服務。
- 模式切換保留必要的 CI 與容器專屬驗收入口；本機結果只證明其適用範圍。可重用腳本與配置版本控制，secrets 及本次資源值留本機。

## 3. 驗證並記錄

- 無服務依賴的群組實跑代表性檢查並確認正常退出；需要服務的模式依 [專案專屬驗證入口](project-verification.md) 跑通 Launch → Doctor → Drive → Evidence → Cleanup。
- 涉及多種模式時各驗證相關入口，確認程式來源、有效 endpoint、fixtures 與清理後資源狀態；用可重建資料再跑必要路徑，證明不依賴偶然殘留。
- 在既有驗證文件記錄群組、模式、選擇理由、工具版本來源、指令／工作目錄、設定名稱、隔離／清理入口與證據；沒有既定位置時用 `docs/testing/verification.md`。指令引用既有 scripts，不另維護重複實作。
- 實際 ports、程序與資源 ID 放本機執行紀錄。未實跑者標草稿／受阻；代表性測試通過只表示配置可用，完整交付仍跑原定必要集合。
