# 專案專屬驗證入口

參考 pstack 的 create／maintain verification 流程；查證版本與移植限制見 `docs/research/pstack-environment-testing.md`。本指引由統一 `test` 入口使用，不要求每個專案另安裝一組測試 skills。

## 何時建立或維護

- Repo 已有可執行的驗證文件、fixtures 與 scripts 時直接沿用，補齊當前任務的缺口。
- 依環境契約逐項判定資源需求。僅需工具鏈的檢查記錄命令、必要設定及結果即可；下方產品啟動與操作迴圈只適用於需要產品環境的驗證。
- 首次準備驗證、缺少可重跑入口，或既有入口因程式／環境改動失效時，建立或更新專案專屬紀錄。預設使用 `docs/testing/verification.md`；有既定位置就引用，不另複製。
- 不按每票重建入口或全量盤點功能；一般開發只維護受影響路徑。使用者明確要求全面盤點時才覆蓋整張驗證地圖。

## 從 repo 取得答案

讀取實際 scripts、設定、CI、routes／CLI、測試與資料模型，找出使用者入口、啟動方式、驅動工具、空資料初始化、auth、證據及並行限制。可查事項自行查；影響需求或超出授權的操作才詢問。

基線無法 build／啟動時，先診斷並在已授權範圍內修復，或具體回報阻擋；不把猜測命令寫成已驗證的操作方式。空專案尚未有產品路徑時，可保留草稿與後續 owner，不能宣稱已具備完整驗證能力。

## 一份紀錄，五項責任

| 區段 | 必須包含的專案實值 |
| --- | --- |
| Launch | 準備／啟動命令、工作目錄、平台與必要設定名稱；migration／seed／測試 Project 的建立方式，以及可操作的就緒訊號 |
| Doctor | 唯讀命令：核對目前實例、版本／build、端口與資源所有權、auth 及業務前置條件；失敗能指出缺項 |
| Drive | 既有 harness、實際 UI locator／API／CLI 操作、預期結果與必要副作用，引用既有測試而非複製一份 |
| Evidence | 命令、SHA／未提交差異識別、環境、開始／完成時間、結果與證據位置；保存動作及結果，不只有最後畫面 |
| Cleanup | 正常及失敗後的清理命令、所有權判斷、共享實例的保留條件；證據目錄與可刪暫存資料分離 |

實際準備、隔離、快取重用與授權依 `docs/agents/environment-contract.md`；timeout／取消依 `docs/agents/test-execution.md`。此紀錄只填專案實值，不另定相衝突政策。

維護最小使用者路徑表：「行為／驗收項 → 實際入口 → 前置資料 → 測試或操作命令 → 預期可觀察結果 → 已驗證範圍／證據」。多入口功能分列，例如 Workspace 與 Workflow 聊天；一個入口通過不能代替另一個。資料缺失要修正準備方式，不能弱化 journey。

## 證明入口可用

1. 在目標隔離環境實跑 Launch → Doctor → 一條與本次工作相關的 Drive → Evidence → Cleanup；失敗後也執行清理。
2. 確認空白／可重建的資料狀態能完成初始化，而非只有服務 health check 成功。明確依賴已授權資料副本的專案，記錄副本及初始化條件，不假稱已證明全空資料啟動。
3. 清理後實際確認證據仍可讀，並核對程序及資料已按所有權處理。只驗證一條路徑代表入口可用，不代表全部功能或 spec 已驗收。
4. 以替代環境驗證時列出與真實目標的差異及未驗證步驟。未實跑的入口標草稿／受阻，不能作為已就緒交接。

## 異常與維護

- 初次操作、實例重啟或操作結果異常後先跑 Doctor。Doctor 通過但 UI 狀態卡死時，重設已知頁面／session 或重啟自有實例；不在未知狀態反覆點擊。
- 區分文件過期、harness 缺口、環境失效及產品缺陷。文件／harness 修正後重跑受影響路徑；產品缺陷交回當前 owner，不靠改預期結果消除錯誤。
- 單獨要求維護驗證入口時，修改限文件、fixtures 與 harness；產品修復另確認任務範圍。`implement-spec` owner 則依整票既有授權完成修復。
- 共享 live UI／瀏覽器 profile 由單一操作者控制；多 worker 必須先隔離 context、帳號、資料及相關 server 狀態，不能只靠「各自小心」。
